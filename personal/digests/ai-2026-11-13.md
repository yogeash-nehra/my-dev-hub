## 🏆 Repo of the Day

### GoogleChrome/modern-web-guidance-src — keeps coding agents current on modern web platform APIs
**Link:** github.com/GoogleChrome/modern-web-guidance-src | **Stars:** ~4.6k (↑ 1,875 today, from 2.7k yesterday) | **Language:** TypeScript | **License:** Apache-2.0 (code), CC-BY 4.0 (guides)

**The problem:** Coding agents default to what they were trained on — which means a lot of legacy code. Vanilla JS where `popover` now handles it natively, polyfills for things browsers resolved years ago, accessibility patterns that have better modern equivalents. The result: bloated, outdated output that passes unit tests and fails real-world checks.

**Why it's today's pick:** Yesterday it was a near-miss at 2.7k stars (rejected for "insufficient stars and no release tags"). In 24 hours it added 1,875 stars and climbed to 4.6k. The star acceleration is real and sustained — not a single-thread spike. More importantly: its own eval snapshot puts coding-agent task pass rates at 52–60% unguided vs 82–96% with the guides loaded, across Claude Code, Codex, and Antigravity. That's a large, concrete benchmark delta. It already has integrations in Claude Code's plugin marketplace, GitHub Copilot CLI, OpenAI Codex, Google Antigravity, Grok Build CLI, and Kimi Code. One note: the Claude Code built-in marketplace stopped updating this plugin; switch to the GoogleChrome marketplace to get updates.

**Try it in 60 seconds:**
```bash
# install once (or via your agent's plugin marketplace)
npx modern-web-guidance@latest install

# in a Claude Code / Codex / Copilot session, the agent calls:
npx modern-web-guidance@latest search "accessible tabs"
# → returns guide IDs
npx modern-web-guidance@latest retrieve <guide-id>
# → loads current patterns + browser-compat data into context
```
**Instead of:** Hoping the agent's training data has current web platform knowledge — it doesn't, consistently. `legacy-scan .` can flag outdated patterns in an existing codebase before you apply guides.

**Watch out for:** Versioned at `v0.0.194` on npm — still pre-1.0, with no GitHub Release tags (npm is the versioning surface). Coverage is web-platform-specific: it won't help with Node.js-only or backend agent work.

## [BREAKING] Breaking Changes

### [BREAKING] Claude Code v2.1.323 — MCP SDK v1 client removed; 1M context default for unrecognized models
**Source:** GitHub (anthropics/claude-code v2.1.323) | **Date:** 2026-11-12 | **Link:** https://github.com/anthropics/claude-code/releases/tag/v2.1.323
**What changed:** v2.1.322 → v2.1.323: `MCP_SDK_GENERATION=v1` no longer loads the v1 client — it now runs the v2 client in compatibility mode (v1 is removed). Separately, the default context window for model IDs Claude Code does not recognize changed from 200K to 1M tokens; `subagentStatusLine` setting is removed.
**TL;DR:** Claude Code v2.1.323 removes the MCP SDK v1 client and changes the default context window from 200K to 1M for unrecognized model IDs — two behavior changes requiring action before upgrading.
**Developer signal:** Three things to do before upgrading: (1) If you use `MCP_SDK_GENERATION=v1`, you are now on the v2 client in compatibility mode — test your MCP server integrations against the v2 protocol. (2) If you use third-party or custom model IDs that Claude Code doesn't recognize, they now assume 1M context; if the actual model has a smaller window, every turn could fail once context fills. Set `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` or run `/clear` proactively. (3) If your config sets `subagentStatusLine`, remove it — the setting is ignored and files still load, but it's dead config. Additionally: `--permission-mode auto` now starts in Manual mode when auto mode is unavailable, rather than a potentially more permissive mode — verify your CI and unattended workflows start in the expected mode.
**Affects you if:** You set `MCP_SDK_GENERATION=v1`; you run Claude Code against custom or third-party model IDs with context windows smaller than 1M; you rely on `subagentStatusLine` in your config; you run `--permission-mode auto` in CI.
**Adoption effort:** Moderate (audit MCP SDK generation setting, test custom model IDs, remove dead config)
**Primary source:** https://github.com/anthropics/claude-code/releases/tag/v2.1.323

### [BREAKING] E2B CLI v2.24.0 — `template list` JSON output shape changed; OAuth auth replaces API key in CLI
**Source:** GitHub (e2b-dev/E2B e2b@2.64.0) | **Date:** 2026-11-13 | **Link:** https://github.com/e2b-dev/E2B/releases/tag/e2b@2.64.0
**What changed:** Previously, `e2b template list` returned a JSON structure keyed on the old shape; v2.24.0 of the CLI changes that JSON output shape (breaking for scripts that parse it) and removes the "Created by" column. Separately, the CLI now authenticates using your login's access token instead of a stored API key, with automatic refresh; `E2B_API_KEY` still takes precedence.
**TL;DR:** E2B v2.64.0 breaks the JSON output shape of `e2b template list` and shifts CLI auth to OAuth access tokens; also adds OAuth to the SDK, resizable templates with configurable CPU counts, and `commands.run` with a custom shell option.
**Developer signal:** If you have scripts that parse `e2b template list --json`, update them for the new shape before upgrading the CLI. For CI: `E2B_API_KEY` still works and takes precedence, but the new recommended approach is `E2B_ACCESS_TOKEN` + `E2B_PROJECT_ID` for token-based auth. For resizable templates: build templates with `--max-cpu` and pass `--cpu` on sandbox create to pick the CPU count at runtime — useful for agent workloads with variable compute needs. The `commands.run` `shell` option lets you specify a custom shell (e.g., `zsh`, `fish`) for command execution instead of the default `sh`.
**Affects you if:** You parse `e2b template list --json` output in scripts; you manage E2B auth via CLI and need to migrate to access tokens for CI; you run agent sandboxes and want to vary compute allocation without rebuilding templates.
**Adoption effort:** Quick for most users (auth migration is automatic); Moderate for scripts that parse `template list` JSON (output shape changed)
**Primary source:** https://github.com/e2b-dev/E2B/releases/tag/e2b@2.64.0

## Trends & Emerging Tech

### Claude Code's security hardening in v2.1.323 reads like a production incident report — permission-bypass edge cases at scale
**Source:** GitHub (anthropics/claude-code v2.1.323) | **Date:** 2026-11-12 | **Link:** https://github.com/anthropics/claude-code/releases/tag/v2.1.323
**What's happening:** v2.1.323 fixes 15 distinct permission and sandbox boundary issues in a single release. The scope is unusually broad: Bash allow rules with wildcards skipped the prompt; combined `sudo` flags skipped the prompt; `Write`/`Edit` could write to paths covered by a `Read` deny rule; plan files with `plansDirectory` set could reference paths outside the project; the sandbox could switch off mid-session; `sandbox.excludedCommands` could let unnamed commands run outside the sandbox; project settings were readable through symlinks; `.mcp.json` approvals weren't enforcing exact name matches. The pattern is: edge cases discovered at scale in production deployments, not theoretical attack paths.
**Why watch this:** As Claude Code usage grows — particularly in team and CI environments — the gap between the permission model's intended behavior and its actual boundaries is narrowing. This release suggests Anthropic is now getting real-world feedback on where those boundaries break down. For teams running Claude Code in production: treat each of these fixes as a signal about where the previous boundary was ambiguous, and audit your allow/deny rules against the new behavior. The trend to track is whether future releases continue this pattern of reactive hardening, or whether the architecture shifts toward a more formally verified permission model.

**[OPEN QUESTION] Does Code Mode in Claude Code change the token economy of long agentic tasks?**
Code Mode (experimental, v2.1.323) has Claude write JavaScript to orchestrate its tool calls rather than making discrete, model-round-trip tool calls. The docs don't specify the token count implications, but the pattern is structurally similar to the difference between an LLM calling tools one at a time (each call = one round trip) versus writing a small program that batches the calls. If Code Mode reduces the number of model round trips for multi-step tool sequences, it could meaningfully change latency and cost profiles for long coding sessions. It could also change error propagation: a JavaScript error mid-program is different from a failed individual tool call. What's missing: any benchmark numbers on Code Mode's performance vs. standard tool-call mode. Worth watching the community benchmarks that will inevitably surface for this.
*Grounded in: Claude Code v2.1.323 Code Mode launch (this digest, Tooling); docs at https://code.claude.com/docs/en/code-mode (accessed via release notes)*

**[IF THIS CONTINUES] E2B's shift to per-sandbox CPU selection opens a pay-per-task compute model for agents**
E2B v2.64.0 adds resizable templates with configurable CPU counts: build a template with a `--max-cpu` ceiling, then each sandbox picks its CPU count at create time.
