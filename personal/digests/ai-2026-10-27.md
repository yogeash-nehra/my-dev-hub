## 🏆 Repo of the Day

Today's big story includes OpenHands v1.34.0 shipping per-conversation Docker runtimes — and with agents spinning up container environments per task, understanding what's actually inside those Docker images (and where the bloat is) becomes a production concern, not just a cleanup chore. Reaching into the watchlist for a pick that earns its spotlight today.

### wagoodman/dive — inspect Docker image layers and shrink container images before they bloat your agent runtimes
**Link:** github.com/wagoodman/dive | **Stars:** ~50k (steady long-term growth) | **Language:** Go | **License:** MIT
**The problem:** Docker images for agent runtimes accumulate invisible bloat — cached pip installs, APT metadata, build artifacts — spread across layers you can't easily see or diff. Trimming 500MB off a base image matters when you're spinning up containers per task at scale.
**Why it's today's pick:** OpenHands v1.34.0 adds per-conversation Docker runtimes, which means each conversation can now have its own isolated container. As you build out custom agent runtimes, you'll want to know which layers are expensive and whether your base image carries unnecessary weight. `dive` gives you a terminal UI that walks you through each layer with a side-by-side file tree view and a "wasted space" score — the quickest way to find what to cut before you ship a fat image to a registry.
**Try it in 60 seconds:**
```bash
# Install (macOS)
brew install dive

# Install (Linux)
wget https://github.com/wagoodman/dive/releases/latest/download/dive_linux_amd64.tar.gz && tar xf dive_linux_amd64.tar.gz && sudo mv dive /usr/local/bin/

# Inspect your agent runtime image layer by layer
dive your-agent-runtime:latest

# CI check: fail the build if wasted image space exceeds 10%
CI=true DIVE_CI_CONFIG=~/.dive-ci.yml dive your-agent-runtime:latest
```
**Instead of:** `docker history your-image` (shows sizes but not which files), or manually running `docker build --no-cache` and grepping layer diffs by hand.
**Watch out for:** dive is a read-only inspection tool, not a cleanup tool — it shows you where the waste is, but you still need to fix your Dockerfile to eliminate it. Also, the CI mode is strict by default; tune `lowestEfficiency` and `highestWastedBytes` in `.dive-ci.yml` to match your image's baseline before plugging it into CI.

## API & SDK Changes

### [MEDIUM] Pydantic AI v2.62.0 — Temporal child workflows for tool calls, background SubAgents, BatchModelRequests, and a broadcast branch order change for durable workflows
**Source:** GitHub Releases | **Date:** 2026-10-26 | **Link:** https://github.com/pydantic/pydantic-ai/releases/tag/v2.62.0
**What changed:** v2.62.0 ships four capability additions and one behavioral compatibility note. (1) Tool calls can now run as **Temporal child workflows** — enabling durable, fault-tolerant tool execution within Temporal orchestration. (2) `SubAgents` can delegate tasks as **background tasks** with `task_control`, allowing steering, answering, or cancelling delegations. (3) New `BatchModelRequests` capability for provider batch APIs (matches Anthropic's batch endpoint). (4) `AnthropicModel.compact_messages()` added for on-demand native message compaction. (5) `CodeMode` now takes `monty_sandbox=...` as a direct parameter, deprecating the old `monty_sandbox_url`. **Compatibility note:** `GraphBuilder` broadcast branches now start in `.to()` order — this can change replay behavior for durable workflows that were paused and persisted before this upgrade.
**TL;DR:** Pydantic AI v2.62.0 adds Temporal child workflows for durable tool execution, background SubAgent task delegations with steering, and provider batch API support.
**Developer signal:** **Temporal tool calls:** If you orchestrate Pydantic AI agents with Temporal, tool calls can now be Temporal child workflows — meaning tool execution gets Temporal's durability guarantees (retries, visibility, state persistence). This is a significant architectural option for long-running agent tasks that previously had to handle fault tolerance at the application layer. **Background SubAgents:** `task_control=True` lets a `SubAgent` run a delegation as a background Temporal task that you can steer, answer, or cancel mid-run — useful for parallel agent execution with human-in-the-loop controls. **Broadcast branch replay note:** If you have existing durable workflows using `GraphBuilder` that contain broadcast branches (fan-out to multiple parallel branches), and those workflows are currently paused/persisted in Temporal or another durable store, replay after upgrading to v2.62.0 may execute branches in a different order than they were originally run. Test replay against persisted workflow state before upgrading any live production workflows.
**Affects you if:** You build agents with Pydantic AI and Temporal; you use `GraphBuilder` with broadcast branches on persisted durable workflows; you call provider batch APIs; you run Claude models via Pydantic AI.
**Adoption effort:** Moderate (new features are opt-in; broadcast branch order change requires validating durable workflow replay if your workflows have persisted state).
**Primary source:** https://github.com/pydantic/pydantic-ai/releases/tag/v2.62.0

**Source:** GitHub Releases | **Date:** 2026-10-26 (21:51 UTC) | **Link:** https://github.com/anthropics/claude-code/releases/tag/v2.1.311

Key fixes: (1) subagents now have access to MCP tools from servers that connected after the subagent started; (2) `SubagentStop` hooks no longer run ~2×/min per subagent (now once); (3) background sessions in auto mode no longer start a new main turn on every scheduled wake; (4) `claude mcp add/remove` no longer targets the wrong project entry when run below a repo root; (5) the startup freeze caused by very long CLAUDE.md list items is fixed; (6) `claude -p` and SDK sessions no longer save messages out-of-order or retain retracted messages. **Affects you if:** You run multi-agent setups with subagents that use MCP tools; you use `SubagentStop` hooks; you run background sessions on a schedule; you manage MCP servers across multiple Claude Code projects; you use `ultrathink` and expect max effort.

## Trends & Emerging Tech

### Agent frameworks are converging on durable execution primitives
**Source:** GitHub Releases (pydantic/pydantic-ai v2.62.0, Oct 26, 2026) | **Date:** 2026-10-26 | **Link:** https://github.com/pydantic/pydantic-ai/releases/tag/v2.62.0
**What's happening:** Pydantic AI v2.62.0 adds the ability to run individual tool calls as Temporal child workflows, and SubAgent delegations as cancellable background tasks. This isn't a single-framework experiment — Temporal-based tool execution has been discussed in the LangGraph, CrewAI, and AutoGen communities for months. The pattern is: treat each tool call as a durable unit of work with its own retry budget, observability, and cancellation primitive, rather than as an ephemeral function call inside an agent turn. Pydantic AI is the first mainstream agent framework to ship this as a first-class feature.
**Why watch this:** If this pattern takes hold, the unit of reliability in an agent system shifts from "the agent session" (fragile, single-process) to "the tool call" (durable, Temporal-managed). That changes how you think about fault tolerance, observability, and cost attribution in multi-step agent workflows. The `task_control` flag for background SubAgents is also a first step toward human-in-the-loop controls at the delegation level — something currently only available at the top-level approval/rejection step in most frameworks.

**[OPEN QUESTION] What does "max effort" mean when ultrathink maps to xhigh?**

Claude Code v2.1.311 changes `ultrathink` from max to xhigh effort across all models via Anthropic's API. **[IF THIS CONTINUES] If per-conversation Docker runtimes become the default, agent cost models need to account for container lifecycle**

OpenHands v1.34.0 ships per-conversation Docker runtimes as an opt-in setting. If this pattern is adopted by default (not just opt-in), the economics of running OpenHands at scale change: instead of a shared runtime amortized across conversations, each conversation incurs its own container startup and teardown cost. Container startup on modern infrastructure is fast (~300ms for pre-pulled images), but it adds up at hundreds of concurrent conversations. The pattern also opens questions about state management — what does "memory" mean when each conversation starts with a fresh container? OpenHands doesn't currently have a native container-state persistence API. This is a pre-problem today (opt-in, low volume), but it becomes a pricing and architecture decision if per-conversation isolation becomes the default.
*Grounded in: OpenHands v1.34.0 per-conversation Docker runtime addition (#18436)*
