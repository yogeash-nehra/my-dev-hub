## 🏆 Repo of the Day

### usebruno/bruno — Git-friendly, offline-first API client that your whole team can actually use without a cloud account

**Link:** github.com/usebruno/bruno | **Stars:** ~32k (↑ steady growth through 2026) | **Language:** TypeScript / Rust | **License:** MIT

**The problem:** Postman and Insomnia store your API collections in the cloud, require account login for team sharing, and put important features behind paywalls. Bruno stores everything as plain files in your repo — no sync, no account, no subscription.

**Why it's today's pick:** A light day for trending dev tools makes this a good moment to reach into the watchlist. Bruno solves a problem every team running an API-centric stack has felt: collection drift between developers when API files live in Postman's cloud rather than in `git`. Bruno puts `.bru` files directly in your repo next to the code they test, so PRs that change an API endpoint can include the updated collection in the same commit. With ~32k stars and a dedicated open-source community, it has enough momentum to be production-viable — but it's still far less visible than Postman's 10M+ user base, which means most teams haven't evaluated it yet.

**Try it in 60 seconds:**
```bash
# Install (macOS)
brew install bruno

# Or on Linux (snap)
snap install bruno

# Or download the binary from usebruno.com/downloads

# Open a Bruno collection (once installed):
# File → Open Collection → point to a folder with .bru files
# Or create a new collection and save it to your repo root
```
**Instead of:** Postman's cloud-synced collections (account required, paywalled collaboration) or keeping a `.http` scratch file that never makes it into version control.

**Watch out for:** The collection format (`.bru`) is proprietary to Bruno — migration from Postman is one-way. The desktop app is the primary UX; the headless CLI (`@usebruno/cli`) lags the desktop slightly in feature coverage. Environment variables with secrets still need careful handling to avoid committing them.

## Model Releases

### [MEDIUM] Liquid AI LFM2.5-24B-A2B — largest LFM2.5 model, context window 4× expanded, purpose-built for on-device agents
**Source:** @liquidai (official X announcement) | **Date:** October 13, 2026 | **Link:** https://x.com/liquidai/status/2110055807194931348

**What changed:** LFM2.5 prior variants topped out at 32K context and ~17T pre-training tokens. LFM2.5-24B-A2B expands context to 131,072 tokens and scales pre-training to ~33T tokens. Vocabulary roughly doubled to 128K tokens. This is the first LFM2.5 model explicitly positioned for multi-step agent harness use rather than single-turn inference.

**TL;DR:** 24B-parameter MoE model, 2B active per token, 131K context (up from 32K), pre-trained on ~33T tokens; self-reported 184 tok/s on Apple M5 Max and >21K output tok/s on a single NVIDIA B300; scores 48.09 on LiveClaw vs. 38.19 for Qwen3.6-35B-A3B (a model with ~50% more total and active parameters); available now on HuggingFace under open weights.

**Developer signal:** LFM2.5-24B-A2B targets the on-device agent niche directly — private pipelines where you want a model running locally inside Ollama, llama.cpp, or LM Studio rather than calling a cloud API. The 131K context is the headline change: prior LFM2.5 variants ran out of window before most real agent trajectories finished. Day-one support was announced for several inference stacks; check the HuggingFace model card (`LiquidAI/LFM2.5-24B-A2B`) for the current list. To try it: `huggingface-cli download LiquidAI/LFM2.5-24B-A2B`. The LiveClaw benchmark lead over Qwen3.6-35B-A3B is Liquid's own reporting — treat it as directional until third-party evals appear. Liquid notes that the model trails on knowledge and coding benchmarks relative to its peers in the 24B tier, so validate on your specific task distribution before committing it to a pipeline. Inference speed (184 tok/s on M5 Max) is a meaningful signal for developers targeting Apple Silicon laptops as agent hosts.

**Affects you if:** You build agent pipelines that run locally (privacy-sensitive workloads, offline environments, cost-sensitive setups); you run models via Ollama, llama.cpp, or LM Studio; you evaluated prior LFM2.5 variants and found the 32K context too short for your agent trajectories.

**Adoption effort:** Quick (HuggingFace pull + drop into existing local inference stack); Moderate if you need to validate task-specific quality before replacing an existing model.

**Primary source:** https://x.com/liquidai/status/2110055807194931348 (liquid.ai DNS failure at scan time — confirmed via official @liquidai X post + 5+ corroborating secondary sources including huggingnews.com, orcarouter.ai, superpowerdaily.com)

## Tooling

### [MEDIUM] OpenHands v1.27.0 — browser video recording, key hold/release, DigitalOcean Managed Agents integration, OpenCode and Pi as built-in ACP agents
**Source:** OpenHands/OpenHands GitHub Releases | **Date:** October 12, 2026 | **Link:** https://github.com/OpenHands/OpenHands/releases/tag/v1.27.0

**What changed:** OpenHands v1.26.0 (Oct 8) added verify-openhands CLI controls and backend helpers. v1.27.0 expands the browser automation surface and adds two new runtime integrations: DigitalOcean Managed Agents (desktop + web) and built-in support for OpenCode and Pi as ACP agents. v1.27.1 (also Oct 12) is a same-day bug fix that copies MARS web bridge modules into the Docker image and fixes warning feedback theming.

**TL;DR:** OpenHands v1.27.0 ships browser video recording via `browser record`, keyboard key-hold primitives (`browser key down|up|release-all`), DigitalOcean Managed Agents integration, and OpenCode/Pi as out-of-the-box ACP agents — the most agent-runtime-focused release since the v1.25.x series.

**Developer signal:** The most immediately useful addition for developers running OpenHands as a test or automation agent is `browser record`: it generates a video of what the browser agent did during a session, which is a substantial debugging improvement over replaying transcripts. The `browser key down|up|release-all` commands enable interactions that require held modifier keys (Shift+Click, Ctrl+drag) — a common gap in prior browser agent implementations. The DigitalOcean Managed Agents integration (in `Agent Canvas`) means you can now connect OpenHands to a DigitalOcean-hosted execution environment without a local Docker setup. ACP model lists are now returned by the agent rather than hardcoded, which means you can configure an ACP backend without forking OpenHands to add model names. Update via your usual Docker pull or `pip install openhands-ai --upgrade`; if you run a customized Docker image, verify the MARS web bridge is included after upgrading to v1.27.1.

**Affects you if:** You run OpenHands for browser-based automation or web testing (video recording); you build multi-agent setups using ACP with OpenCode or Pi as sub-agents; you deploy OpenHands workloads on DigitalOcean.

**Adoption effort:** Quick (Docker pull or pip upgrade for most setups); Moderate if you have a custom image that needs the MARS web bridge fix from v1.27.1.

**Primary source:** https://github.com/OpenHands/OpenHands/releases/tag/v1.27.0

## Trends & Emerging Tech

### The on-device agent model category is consolidating around MoE architectures with RL-expanded training
**Source:** Liquid AI LFM2.5-24B-A2B (Oct 13); JetBrains Mellum2.1 (Oct 8, via Oct 12 digest) | **Date:** October 13, 2026 | **Link:** https://x.com/liquidai/status/2110055807194931348

**What's happening:** Two open-weight models explicitly built for local/on-device agent harnesses shipped within five days of each other: Mellum2.1 (12B MoE, 47% SWE-bench Verified, Apache 2.0) and LFM2.5-24B-A2B (24B MoE, 131K context, day-one Ollama/llama.cpp support). Both use Mixture-of-Experts architecture to hit high inference throughput at low active-parameter counts, and both frame themselves as sub-agents for coding pipelines rather than standalone assistants. The shared architecture is not coincidence — MoE with a small active-parameter footprint is the design pattern that makes local inference practical on consumer hardware.

**Why watch this:** If this pattern continues into Q1 2027, the on-device coding sub-agent slot in a pipeline will become a commodity: multiple capable open-weight MoE models competing at 12B–24B active-parameter scale, each with 100K+ context windows, running at hundreds of tokens per second on M-series Macs. The developer decision will shift from "which cloud API can I afford" to "which harness integrates cleanest with my local model stack." Benchmark incompatibility (Mellum2.1 uses Pi harness; LFM2.5 uses LiveClaw) makes direct comparison hard — the model selection question for local sub-agents will need to be answered on your own task distribution, not the published leaderboards.

**[OPEN QUESTION] Can a local MoE model at 2B active parameters actually sustain a long-horizon coding task — or does the 131K context come at a quality cost at that active-parameter count?**
LFM2.5-24B-A2B claims 184 tok/s throughput and 131K context, but the quality story is more complicated. Liquid explicitly notes the model trails on knowledge and coding benchmarks relative to 24B-tier peers, and the LiveClaw comparison (48.09 vs 38.19 for Qwen3.6-35B-A3B) is a proprietary benchmark without published methodology. Mellum2.1's 47% SWE-bench Verified score was strong for its size class, but came from a self-reported harness that doesn't map to the Scale harness used for frontier comparisons. The open question is whether 2B active parameters is fundamentally enough for the reasoning steps a real software engineering task requires at 100K+ context, or whether these models are better suited as retrieval/navigation sub-agents rather than reasoning engines.
*Grounded in: LFM2.5-24B-A2B (Oct 13, self-reported LiveClaw benchmark, "trails on knowledge and coding benchmarks"); Mellum2.1 (Oct 8, self-reported 47% SWE-bench Verified via Pi v0.73.1 harness)*

**[TENSION] The browser automation surface is expanding faster than testing infrastructure can validate it**
OpenHands v1.27.0 adds `browser record`, key-hold primitives, and DigitalOcean integration — in the same release, the team ran mock-LLM end-to-end behaviors driven on DeepSeek "with gaps mapped." That parenthetical is the tension: the capabilities shipped before the test coverage was complete. Browser-based agent automation (click sequences, keyboard interactions, video recording) has a combinatorial state space that's hard to test exhaustively, and the gap between "feature shipped" and "feature tested against the full browser surface" tends to widen with each release. Developers integrating OpenHands into CI pipelines that depend on browser behaviors should run regression tests after upgrading, not assume stability.
*Grounded in: OpenHands v1.27.0 (Oct 12, "Mock-LLM end-to-end behaviors driven on DeepSeek, with gaps mapped" — from release notes #18191)*

---

**[IF THIS CONTINUES] By early 2027, the on-device agent slot in a typical pipeline will require a different selection framework than cloud model selection**
Cloud model selection is currently benchmarks → latency → pricing → API compatibility. On-device model selection adds: active-parameter count → inference stack support → context quality at long range → hardware tier fit (M-series Mac vs. B300 vs. consumer GPU). LFM2.5-24B-A2B has three different performance specs depending on the hardware (M5 Max, B300, unspecified other). If the on-device model ecosystem reaches the density of the cloud API market in 12 months — which the current two-models-in-five-days pace suggests is plausible — developers will need tooling that evaluates models on their specific hardware + task combination, not a single public leaderboard. The hardware-aware eval framework is the gap in the current open-weight ecosystem.
*Grounded in: LFM2.5-24B-A2B (Oct 13, 184 tok/s on M5 Max vs >21K tok/s on B300 — an order-of-magnitude difference across hardware tiers); Mellum2.1 (Oct 8, "near-2x vs Qwen3.5-9B at high load on one H200")*

---

**[BUILDER'S ANGLE] If OpenHands' `browser record` is extended to capture structured event logs alongside video, it becomes the missing observability primitive for browser-agent debugging**
OpenHands v1.27.0 ships `browser record` as a video-capture feature. Video is a good start for human review, but a structured event log (DOM state at each step, element targeted, action taken, resulting URL/DOM change) would be far more useful for automated regression testing and failure diagnosis in CI. The capability gap is that current browser-agent tooling produces either opaque action sequences or hard-to-parse video — neither integrates cleanly into a test assertion framework. If a future OpenHands release adds structured event output alongside the video, it would enable the same kind of "replay and assert" testing patterns that Playwright and Cypress use for deterministic web tests, applied to agent-driven workflows.
*Grounded in: OpenHands v1.27.0 (Oct 12, `browser record` command via PR #18211)*
