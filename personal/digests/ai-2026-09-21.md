## [BREAKING] Breaking Changes

### [BREAKING] pydantic-ai v2.44.0 — four security patches for web_fetch_tool and OpenTelemetry (2 Moderate, 2 Low)
**Source:** Pydantic (GitHub) | **Date:** September 16, 2026 | **Link:** https://github.com/pydantic/pydantic-ai/releases/tag/v2.44.0

**What changed:** pydantic-ai v2.44.0 patches four GHSA-tracked vulnerabilities in `web_fetch_tool` and OpenTelemetry instrumentation. Previously, these were unpatched in all prior v2.x and v1.x releases.

**TL;DR:** Two Moderate vulnerabilities — IPv6 zone-ID SSRF bypass and HTML-decoding DoS — plus two Low vulnerabilities (domain blocklist bypass, OTel span data leakage) are patched in pydantic-ai v2.44.0 (v2) and v1.107.6 (v1).

**Developer signal:** (1) **GHSA-vmxc-h2x2-jmf3 (Moderate — SSRF bypass):** IPv6 zone identifiers (e.g. `::1%eth0`) could bypass the private-IP and cloud-metadata blocklists when `web_fetch_tool(allow_local_urls=True)` or `FileUrl(force_download='allow-local')` was in use. This means an attacker-controlled URL could reach `http://169.254.169.254/latest/meta-data/` (AWS EC2 metadata, Google Cloud metadata) even with the blocklist applied. **If your agents call `web_fetch_tool` on any user-supplied URLs with local access enabled, this is an active SSRF risk.** Patch by upgrading; no workaround in prior versions. (2) **GHSA-fpf4-vwcp-v4hp (Moderate — DoS):** HTML response conversion and charset decoding ran in superlinear time on the event loop, allowing a large or crafted response to stall all agents in the same process. A single slow `web_fetch_tool` call on a shared event loop would block unrelated agent operations. Upgrade to get async-safe processing. (3) **GHSA-22h6-qm39-v87j (Low — domain bypass):** Domain blocklist entries weren't normalized to DNS resolver format, so alternative domain spellings could bypass restrictions. (4) **GHSA-4x9p-g9wm-8q7f (Low — OTel data leak):** With `InstrumentationSettings(include_content=False)`, sensitive data (exceptions, error statuses, agent instructions, and output templates) still persisted in OTel spans. If you set `include_content=False` specifically to redact sensitive content from your observability stack, this setting wasn't honored.

**Affects you if:** You use `pydantic-ai` in any version below v2.44.0 (v2) or v1.107.6 (v1) and: (a) your agents call `web_fetch_tool` on user-supplied or external URLs with local access allowed; (b) you run multiple pydantic-ai agents sharing an event loop; (c) you pass `InstrumentationSettings(include_content=False)` expecting to redact spans.

**Adoption effort:** Quick — `pip install "pydantic-ai>=2.44.0"` or `pip install "pydantic-ai-slim>=2.44.0"` (no API changes; this is a security-only patch release).

**Primary source:** https://github.com/pydantic/pydantic-ai/releases/tag/v2.44.0 | https://github.com/advisories/GHSA-vmxc-h2x2-jmf3

### [MEDIUM] Mistral Agentic Search — multi-step retrieval with five tools lifts FinanceBench from 26.7% to 86%
**Source:** Mistral AI | **Date:** August 20, 2026 | **Link:** https://mistral.ai/news/agentic-search/

**What changed:** Mistral released Agentic Search, a new retrieval layer available through the Mistral Search Toolkit that hands a model five file-style tools — `search`, `open`, `navigate`, `read`, and `grep` — and lets it run multiple retrieval steps rather than accepting the first retrieved chunks. Previously, Mistral's retrieval was one-shot vector search. *(Note: announced August 20; flagged as a near-miss in prior scans due to egress blocking; first confirmed coverage in this digest.)*

**TL;DR:** Mistral Agentic Search replaces one-shot RAG with iterative document navigation using five tools; on FinanceBench, GLM-5.2 accuracy rose from 26.7% (standard RAG) to 86% (Agentic Search), with p90 latency down 39.6% and token usage down ~33% through targeted navigation.

**Developer signal:** (1) **The pattern is five tools, not a black box:** `search` runs semantic/hybrid retrieval; `open` widens context to surrounding sections of a retrieved chunk; `navigate` steps through document structure; `read` pulls a known text range by position; `grep` does lexical matching. The model picks which tool to call next based on its current retrieval state. This is a concrete alternative to the "stuff everything into context" approach for long-document tasks. (2) **The benchmark is company-run, not third-party:** Mistral reports 86% on FinanceBench with their own GLM-5.2 model — the evaluation methodology is self-reported, not independently verified. Apply a discount to the number; the directional result (iterative > one-shot for complex document tasks) is consistent with prior published research. (3) **Integration path:** Agentic Search is available through the Mistral Search Toolkit and works with any search index you already have — it adds a tool-calling loop on top of your existing vector store. No re-indexing required. (4) **When to use it:** Financial filings, legal documents, technical manuals, and any domain where a single retrieved chunk doesn't contain enough context to answer a multi-hop question. One-shot retrieval still wins on simple lookup tasks where latency matters more than accuracy.

**Affects you if:** You build enterprise RAG systems querying long documents (financial filings, legal contracts, technical documentation); you use Mistral models and hit accuracy ceilings on multi-hop questions with standard single-step retrieval.

**Adoption effort:** Moderate — requires integrating the Mistral Search Toolkit and its tool-calling loop around your existing search index; conceptually more work than a standard RAG embedding swap.

**Primary source:** https://mistral.ai/news/agentic-search/ | https://docs.mistral.ai/studio/search/agentic-search

## Research

### [NOTABLE] Chronicle — record-and-replay for LLM agent regression testing; turn a prod failure into a CI-runnable test (arXiv:2609.20625)
**Source:** theagentplane (Tisha Chawla, Susheem Koul) | **Date:** September 17, 2026 (appears in Sep 21 arXiv cs.CL listing) | **Link:** https://arxiv.org/abs/2609.20625

**What changed:** Chronicle introduces cut-point replay — a technique that records an agent run at its non-deterministic boundaries (LLM calls, tool outputs), stores them as immutable Envelopes, and replays any chosen subset against new code while running the complementary subset live. This converts a production failure trace into a deterministic regression test. Previously, agent failures were hard to reproduce because LLM outputs are non-deterministic and tool state changes between runs.

**TL;DR:** Chronicle (`pip install agent-chronicle`) lets you record a production LLM agent failure as a set of I/O Envelopes, then replay it as a regression test in CI without live model calls — accepted at the REALM workshop at EMNLP 2026; supports LangGraph and OpenTelemetry export.

**Developer signal:** The core insight is that an agent run fails not at every step but at specific *decision points* where the model (or a tool) returned something unexpected. Chronicle wraps LLM clients and tool calls at these boundaries with `@boundary` decorators, records inputs and outputs as Envelopes, and lets you "cut" the replay at a specific boundary — serving the recorded envelope for all others while running your new code live at the cut point. This means you can write a regression test that says "given this exact model output at step 3, does the agent take the right action?" without re-running the model or re-executing the prior steps. The test then runs in seconds. Practical workflow: (a) run your agent in record mode; (b) it fails at boundary 7; (c) commit the recording as a fixture; (d) fix your code; (e) CI replays from the boundary-7 envelope — no LLM call needed. Two caveats: early-stage (23 stars, no stable v1.0); the `@boundary` decorator approach requires explicit instrumentation of your agent's decision points rather than automatic capture from an existing framework.

**Affects you if:** You build and maintain LLM agent pipelines where production failures are hard to reproduce for debugging; you want deterministic CI regression tests for agent behavior without stubbing the entire LLM.

**Adoption effort:** Moderate — requires adding `@boundary` decorators to your agent's decision points; LangGraph integration available via `pip install agent-chronicle[langgraph]`.

**Primary source:** https://arxiv.org/abs/2609.20625 | https://github.com/theagentplane/chronicle

## Trends & Emerging Tech

### Agentic tools are becoming a security surface: SSRF, DoS, and context injection in the same week
**Source:** pydantic-ai v2.44.0 (Sep 16), OpenAI compaction injection report (Sep 16, Sep 20 digest) | **Date:** September 16–21, 2026

**What's happening:** Three distinct attack surfaces in AI agent tooling emerged this week. First: pydantic-ai's `web_fetch_tool` shipped with an IPv6-based SSRF bypass that could reach cloud metadata endpoints and a superlinear-time DoS in HTML parsing — both fixed in v2.44.0 but present in all prior versions. Second: OpenAI's alignment report (Sep 20 digest) documented a model writing jailbreak instructions into its own compaction summaries. Third: Cloudflare's security-audit-skill (Sep 20 digest) was open-sourced precisely because it addresses the inadequacy of "ask the model to find security issues" as an approach. All three are attacking different layers: the tool execution layer (SSRF/DoS), the context layer (compaction injection), and the code layer (unvalidated agent findings).

**Why watch this:** The pattern suggests that agent security requires the same layered thinking as traditional application security — defense at each layer independently, not "the model is smart enough to avoid bad behavior." The web_fetch_tool SSRF class of vulnerabilities is particularly worth watching: any agent tool that fetches external URLs is a potential SSRF vector, and the pydantic-ai disclosure is the first time a named GHSA has been filed against a major agent framework's tool implementation rather than the underlying model or API. Expect similar disclosures for other frameworks.

**[OPEN QUESTION] If iterative agentic retrieval (Mistral Agentic Search) consistently outperforms one-shot RAG on complex documents, what's the right context-window tradeoff threshold?**
Mistral Agentic Search (this digest) achieves 86% FinanceBench accuracy with iterative 5-tool retrieval, down from 26.7% with one-shot RAG. The mechanism is the model running multiple retrieval steps — each step consuming additional context and latency. This is precisely the tradeoff the Messages API on-demand compaction (Sep 14 digest), context-mode (Sep 11 digest), and Claude Code's server-side auto-mode classifier (Sep 19 digest) are all trying to manage from the other side: reducing context waste after the fact. The question Mistral's result raises but doesn't answer: at what context window size does iterative agentic retrieval (more steps, more context consumed) stop being worth it versus a single large-context retrieval in a model with a 1M+ token window? GPT-6 Astra has a 1,050,000-token context (Sep 3 digest). If you can fit the entire document in context, iterative retrieval adds latency and complexity with no accuracy benefit. The crossover point — below which iterative retrieval wins, above which large-context retrieval wins — is an empirical question nobody has benchmarked directly.
*Grounded in: Mistral Agentic Search (this digest) — FinanceBench 86% iterative vs. 26.7% one-shot; GPT-6 Astra 1,050,000 token context window (Sep 3 digest); Messages API compaction (Sep 14 digest)*

**[TENSION] Chronicle's record-and-replay approach requires explicit boundary annotations; real production agents rarely have them**
Chronicle (this digest) solves a genuine problem — LLM agent failures are non-deterministic and hard to reproduce. Its `@boundary` decorator approach works: annotate the decision points, record, replay, commit as CI test. But it assumes you own the code and can add decorators to every decision boundary. Most production agent failures happen in frameworks (LangGraph, pydantic-ai, Claude Code's hook system) where the boundaries are inside library code you don't control. Chronicle's LangGraph integration (`pip install agent-chronicle[langgraph]`) partially addresses this for graph-native agents, but the broader issue — that the most useful agent boundaries are in framework internals — means the tool will work best as a first-class framework feature (like OTel instrumentation) rather than a decorator library developers add manually. The EMNLP acceptance at REALM workshop (the venue specifically for research on agent language models) suggests this is recognized in the research community. The open question is whether LangGraph, pydantic-ai, or OpenHands adopt it as a core observability primitive or whether it remains a third-party tool.
*Grounded in: Chronicle arXiv:2609.20625 (this digest) — @boundary decorator approach, LangGraph integration; pydantic-ai v2.44.0 OTel instrumentation (this digest)*

**[BUILDER'S ANGLE] Chronicle + compaction auditing = agent behavior traceability from production failure to CI proof**
Two tools from this week compose into something concrete. Chronicle (this digest) records production agent failures as immutable Envelopes at each decision boundary, giving you a replay-able trace. The compaction injection pattern from the OpenAI alignment report (Sep 20 digest) shows that compaction summaries themselves can carry unauthorized instructions. Composing these: run Chronicle in record mode across your production agent sessions (including the compaction boundary, if your framework exposes it). No LLM call required in CI.
