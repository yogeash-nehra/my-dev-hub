### evilmartians/lefthook — language-agnostic git hooks that actually run fast
**Link:** github.com/evilmartians/lefthook | **Stars:** ~12k (↑ steady growth) | **Language:** Go | **License:** MIT
**The problem:** Husky only works in Node projects, pre-commit only works in Python projects, and raw `.git/hooks/` scripts break across machines — there's no fast, language-agnostic hook manager that works in any repo.
**Why it's today's pick:** Claude Code v2.1.309 ships a significant round of hooks fixes: PowerShell hooks that weren't blocking on exit code 2, hooks in worktrees not applying to compound `cd`+git commands, hooks modules nested too deep failing silently, and skills in `--add-dir` folders colliding with same-named hooks. If you're wiring Claude Code hooks to your git workflow (which most serious users are), having reliable hooks upstream matters. `lefthook` runs hooks in parallel, respects `.gitignore`, prints timing per hook, and uses a single `lefthook.yml` that commits alongside your code — so every contributor runs the same hooks without a Node or Python setup. It's also the fastest option in its class by raw benchmark.
**Try it in 60 seconds:**
```bash
# Install (macOS / Linux)
brew install lefthook
# or: npm install -D lefthook (Node projects), go install github.com/evilmartians/lefthook@latest

# Init in your repo
lefthook install

# lefthook.yml example — run in parallel before push
# pre-push:
#   parallel: true
#   commands:
#     tests: run: npm test
#     lint:  run: npm run lint
```
**Instead of:** Husky (Node-only, slows cold starts), pre-commit (Python-only, requires venv per machine), or raw shell scripts in `.git/hooks/` (not committed, diverge across devs).
**Watch out for:** Monorepo setups need explicit `lefthook.yml` at each package root (or a root config with `glob`-scoped commands). Windows support is solid, but `run:` commands use bash syntax by default — add `shell: pwsh` per command for PowerShell.

## [BREAKING] Breaking Changes

### [BREAKING] Claude Code v2.1.309 — `claude ultrareview` now requires workspace trust; `sed -i` no longer restored by /rewind
**Source:** GitHub Releases | **Date:** 2026-10-22 | **Link:** https://github.com/anthropics/claude-code/releases/tag/v2.1.309
**What changed:** Two behavioral changes that affect scripts and established workflows. (1) `claude ultrareview` now requires workspace trust: in a terminal it asks interactively; in a non-interactive or unattended session it refuses. Scripts must pass `--trust-workspace` (placed before a PR number or base branch) or set `CLAUDE_CODE_DISABLE_ULTRAREVIEW_TRUST_CHECK=1`. (2) `sed -i` now receives the standard Bash permission prompt and runs as written; like other Bash edits, it is **no longer undoable with `/rewind`**.
**TL;DR:** Unattended `claude ultrareview` calls fail without `--trust-workspace`, and `sed -i` edits are now permanent from a /rewind perspective.
**Developer signal:** Audit your CI/CD scripts and self-hosted runner startup scripts for bare `claude ultrareview` invocations — add `--trust-workspace` before your PR number argument (e.g. `claude ultrareview --trust-workspace 123`). For `sed -i` usage: if you relied on `/rewind` to roll back `sed -i` modifications during a session, you must now handle those rollbacks manually or avoid `sed -i` in contexts where a rewind might be needed. Neither change has a deprecation period — both take effect immediately on upgrade to v2.1.309.
**Affects you if:** You run `claude ultrareview` in a CI pipeline, self-hosted runner, or non-interactive script; you use `sed -i` in a workflow where you depended on `/rewind` to restore changes.
**Adoption effort:** Quick (add flag or env var to scripts); behavioral awareness needed for sed -i.
**Primary source:** https://github.com/anthropics/claude-code/releases/tag/v2.1.309

### [BREAKING] pydantic-ai v2.60.0 — BedrockConverseModel now defaults maxTokens to Claude's max; two deprecations start clocks
**Source:** GitHub Releases | **Date:** 2026-10-22 | **Link:** https://github.com/pydantic/pydantic-ai/releases/tag/v2.60.0
**What changed:** `BedrockConverseModel` now defaults `maxTokens` to Claude's maximum output when not explicitly set (#10845). Previously, not setting `maxTokens` sent no limit. This can increase costs and latency for Bedrock Claude callers who relied on the implicit no-limit default. Two deprecations also start their clocks: `RetryPromptPart` is deprecated in favor of `ToolReturnPart(outcome='retried')` + `RetryFeedbackPart`; `OpenAIDecisionsProvider` is deprecated and `OpenAIDecisionsModel` now accepts `OpenAIProvider` instead.
**TL;DR:** BedrockConverseModel silently sets a higher maxTokens default than before — check your Bedrock Claude usage costs after upgrading; migrate RetryPromptPart and OpenAIDecisionsProvider before they are removed.
**Developer signal:** If you use `BedrockConverseModel` without explicit `maxTokens`, add `max_tokens=<your_intended_limit>` before upgrading to prevent unexpected output and cost changes. For `RetryPromptPart`: replace `RetryPromptPart(content=...)` with `ToolReturnPart(outcome='retried', ...)` + `RetryFeedbackPart(...)`. For `OpenAIDecisionsProvider`: replace it with `OpenAIProvider` and pass that to `OpenAIDecisionsModel`. Both deprecations still work — the breaks come in a future major version — but start migration now while the surface is small.
**Affects you if:** You use `BedrockConverseModel` without explicit `max_tokens`; you use `RetryPromptPart` in agent retry logic; you use `OpenAIDecisionsProvider` for OpenAI Decisions API calls.
**Adoption effort:** Moderate (three separate migration paths; BedrockConverseModel requires immediate cost audit).
**Primary source:** https://github.com/pydantic/pydantic-ai/releases/tag/v2.60.0

**Source:** GitHub Releases | **Date:** 2026-10-23 | **Link:** https://github.com/anthropics/anthropic-sdk-python/releases/tag/v2.2.0

(2) Usage and cost reports by dimension: new reports endpoints let you query API usage and costs sliced by dimension (model, workspace, API key, etc.); older flat usage reports are now marked legacy. Also: the tool runner's `append_messages()` no longer modifies the runner's internal history after it's called — the caller now owns what was appended; several fixes to `set_messages_params()` callback behavior with `tools`, `betas`, `user_profile_id`, and `workspace_id`.
**TL;DR:** The Anthropic SDK v2.2.0 adds a threads resource for persistent conversation state and dimensional usage/cost reporting, both underdocumented — the SDK is ahead of the official changelog.

For usage/cost reports: if you query the usage API to attribute costs to teams, projects, or API keys, explore the new `reports.by_dimension` endpoint — the legacy flat reports still work but are now explicitly flagged for future removal. For the tool runner fix: if you call `append_messages()` and then inspect `runner.history`, the history no longer includes those appended messages (the caller owns them). Update any code that read from `runner.history` after `append_messages()`.
**Affects you if:** You build persistent multi-turn agents on the Anthropic API; you aggregate API costs across teams or workspaces; you use the tool runner's `append_messages()`.
**Adoption effort:** Moderate (threads are new API surface worth evaluating; usage report migration from legacy to dimensional is optional now, required later).

### [HIGH] pydantic-ai v2.60.0 — DockerSandbox, BoxLiteSandbox, RelevanceCompaction, SmartSearch, FileUnderstanding, TemporalDurability
**Source:** GitHub Releases | **Date:** 2026-10-22 | **Link:** https://github.com/pydantic/pydantic-ai/releases/tag/v2.60.0
**What changed:** The largest pydantic-ai feature release since the framework launched, shipping six new capabilities and a round of security/correctness fixes — the day after v2.59.0's DoS security patch. New execution substrates: **DockerSandbox** (#9341) runs the agent workspace in a local Docker or Podman container; **BoxLiteSandbox** (#10740) runs it in a local BoxLite micro-VM. New memory management: **RelevanceCompaction** (#11026) keeps, reduces, or drops older history steps based on a judge model's ranking — a step beyond simple truncation. New search: **SmartSearch** (#8977) provides plain-English code search with a pluggable judge model. New file handling: **FileUnderstanding** (#8453) adds a file comprehension capability. New durable execution: **TemporalDurability** (#7312) supports Temporal `continue-as-new` via a `continue_as_new` primitive. Other fixes: MCPToolset now accepts `auth` and `headers` as functions of the run context (#10846); `BrowserUse` keeps secrets on allowlisted sites and out of tool results (#10771); `FileSystem` patterns match case-insensitively and protect `.git` files (#10825).
**TL;DR:** pydantic-ai v2.60.0 adds two local sandbox execution substrates, judge-based history compaction, plain-English code search, and Temporal continue-as-new — the biggest single-release feature expansion the framework has shipped.
**Developer signal:** **DockerSandbox / BoxLiteSandbox**: if you're testing agent tool execution locally, these are worth exploring immediately — they let you run pydantic-ai agents in isolated containers without E2B or Daytona accounts. Check `#9341` and `#10740` in the pydantic-ai repo for install and usage. **RelevanceCompaction**: if your agents use long conversation histories and suffer from context drift or irrelevant history, configure `RelevanceCompaction` with a small judge model (e.g., Haiku) to prune history intelligently — this is more precise than truncation. **SmartSearch**: if you build coding agents that search their own codebases, `SmartSearch` can replace custom retrieval logic. **TemporalDurability**: if you run long-running agents on Temporal, `continue_as_new` now works natively — check `#7312` for migration from manual Temporal workflow management. **MCPToolset auth/headers as functions**: if you pass authentication headers to MCP servers, these can now be dynamic (e.g., per-user tokens from run context) rather than static at setup time.
**Affects you if:** You test pydantic-ai agents locally without a cloud sandbox; you build agents with long conversation histories; you run coding agents that need codebase search; you operate pydantic-ai on Temporal for durable execution; you use MCP servers that require per-user auth.
**Adoption effort:** Moderate (each feature requires explicit configuration; deprecation migrations for RetryPromptPart and OpenAIDecisionsProvider; BedrockConverseModel maxTokens audit needed).
**Primary source:** https://github.com/pydantic/pydantic-ai/releases/tag/v2.60.0

### SWE-DIVE — multi-turn coding agent evaluation is arriving as a proper benchmark category
**Source:** arXiv 2610.30047 | **Date:** 2026-10-23 | **Link:** https://arxiv.org/abs/2610.30047
**What's happening:** SWE-DIVE transforms existing one-shot software engineering benchmarks (like SWE-bench) into dynamic, multi-turn sessions by splitting tasks into incremental sub-tasks and using an LLM to simulate the user discovery process. It ships with a user simulator, a conversation validator, and a Task Completion Evaluator inside a Harbor orchestration environment. Two related papers — SWE-Together (2606.29957) and Dialogue SWE-Bench (2606.13995) — landed in the last ~60 days, suggesting a minor convergent moment: researchers are recognizing that one-shot coding benchmarks don't capture how real developers interact with coding agents in multi-turn sessions.
**Why watch this:** If SWE-DIVE (or a successor) becomes the canonical multi-turn coding benchmark, it will shift how coding agents are optimized — away from "solve in one shot" and toward "understand what the user wants across turns." For developers choosing between coding agents, multi-turn evaluation matters more than one-shot SWE-bench numbers because it matches real usage. For researchers building coding agents: this benchmark category is early enough that good scores on it would be differentiating today. No code repo confirmed in the 24h window — check arxiv.org/abs/2610.30047 for links.
