## [BREAKING] Breaking Changes

### [BREAKING] vLLM v0.26.0 Removes TeleChat, Persimmon, and Fuyu Models

**Source:** vLLM GitHub | **Date:** July 27, 2026 | **Link:** https://github.com/vllm-project/vllm/releases/tag/v0.26.0

**What changed:** Three model architectures — TeleChat, Persimmon, and Fuyu — are removed from the codebase in v0.26.0. Any vLLM deployment serving these models will fail to load after upgrading.

**TL;DR:** vLLM v0.26.0 (411 commits, 212 contributors) removes TeleChat, Persimmon, and Fuyu, adds Inkling (975B total / 41B active, full stack including CUDA graphs, Hopper FA4, speculative decoding, LoRA, NVFP4), and delivers 2.94% E2E TPOT improvement on DeepSeek-V4 via a new routing kernel.

**Developer signal:** (1) **Model removal**: if you serve TeleChat, Persimmon, or Fuyu — even for a minor use case — pin to v0.25.x before upgrading. There is no deprecation warning; the model classes are simply gone. (2) **DeepSeek-V4 users** get a free performance bump: the specialized routing kernel saves 2.94% E2E TPOT with no config changes; the `fused_topk_bias` kernel adds 1.5–2x speedup at the kernel level. (3) **Inkling support** is comprehensive and production-ready in this release: piecewise CUDA graphs, Hopper FA4 relative attention, speculative decoding, LoRA, and NVFP4 quantization are all included. (4) **KV offloading** matures substantially — tiered secondary storage with object-store support and CPU offloading are now stable, not experimental. (5) **Dependency updates** require attention: Transformers bumps to 5.13.0, FlashInfer to 0.6.14, nvidia-cutlass-dsl to 4.6.0. Test your environment before upgrading in production.

**Affects you if:** You are serving TeleChat, Persimmon, or Fuyu via vLLM; you depend on specific FlashAttention 3 behavior (now pinned to torch stable-ABI); you are running DeepSeek-V4 on vLLM and want the performance gains.

**Adoption effort:** Moderate — upgrade is straightforward for most, but requires immediate action if TeleChat/Persimmon/Fuyu are in your serving stack. Test dependency compatibility before deploying to production.

**Primary source:** https://github.com/vllm-project/vllm/releases/tag/v0.26.0

## Model Releases

### [HIGH] Kimi K3 Open Weights Live — 2.8T MoE, Modified-MIT, vLLM KDA Ships Simultaneously

**Source:** Moonshot AI (official HuggingFace org) | **Date:** July 27, 2026 | **Link:** https://huggingface.co/moonshotai/Kimi-K3

**What changed:** Kimi K3 moves from API-only (available since July 16) to publicly downloadable open weights under a Modified-MIT license. vLLM support for KDA (Kimi Delta Attention — the hybrid linear/full attention architecture) and prefix caching ships alongside the weights. The technical report publishes simultaneously.

**TL;DR:** Kimi K3 (2.8T total / ~50B active, 16-of-896 expert routing, 1M context ceiling) is live on HuggingFace at ~594GB MXFP4; it scores 76.8% on SWE-bench Verified (harness-independent), tops all models on Program Bench (77.8, +0.2 over GPT-5.6 Sol), and holds LMArena Frontend Code Arena #1 at 1,679 ELO.

**Developer signal:** The critical technical unlock is the simultaneous vLLM KDA support — without it, inference would require custom CUDA kernels, making K3 effectively unusable for most teams. With vLLM v0.26.0 (also released today), the full stack is available immediately. Three caveats to size your expectations: (1) **Hardware floor**: ~594GB MXFP4 safetensors (reported elsewhere as ~1.4TB including runtime buffers and KV cache at 128K context) — this is Blackwell-cluster territory, roughly a 16× H200 or equivalent Blackwell floor. CPU offloading is technically possible but impractical for production workloads. (2) **Harness mixing**: Moonshot's official benchmark table mixes KimiCode, Claude Code, Codex, and mini-SWE-agent harnesses; different harnesses can swing scores by 10–26 points on SWE-bench variants. The 76.8% SWE-bench Verified is the harness-neutral number; higher claims (up to 93.40% on some tables) reflect KimiCode-harness runs. The 77.8 on Program Bench and 42.0 on SWE Marathon appear consistent across secondary sources. (3) **LMArena ELO** of 1,486 (text, as of July 17) vs. 1,679 (Frontend Code Arena) shows a 200-point specialization gap — K3 is tuned for coding-agent work, not general chat. The license (Modified-MIT) permits fine-tuning and redistribution, making K3 the most liberally licensed frontier-class model ever released by parameter count.

**Affects you if:** You operate Blackwell-class GPU clusters and want to self-host a frontier-size open-weight model for agentic coding; you are evaluating K3 on the Kimi API and want to fine-tune or redistribute weights; you are running vLLM v0.26.0 and want to serve K3 with prefix caching.

**Adoption effort:** Significant — the hardware bar alone (Blackwell cluster, 594GB+ VRAM) limits self-hosting to a small subset of operators. Accessing K3 via the Kimi API remains the practical path for most teams.

**Primary source:** https://huggingface.co/moonshotai/Kimi-K3 | Technical report: published simultaneously at the HuggingFace model page

## Trends & Emerging Tech

### Molt — NVIDIA NeMo's PyTorch-Native Agentic RL Training Framework

**Source:** NVIDIA NeMo (arxiv 2607.21653) | **Date:** July 27, 2026 | **Link:** https://arxiv.org/abs/2607.21653

**What's happening:** NVIDIA NeMo Labs released Molt, an open-source agentic reinforcement learning training framework built around three components: Ray for orchestration, vLLM for rollout generation, and NVIDIA AutoModel + FSDP2 for training in pure PyTorch. The codebase is ~9.2K lines of RL code, intentionally compact to allow researchers (and AI coding assistants) to read and trace the full algorithm flow. It scales to 1T-class MoE models with tensor, expert, and context parallelism on A100 through GB200. The code is on GitHub (github.com/NVIDIA-NeMo/labs-molt).

**Why watch this:** Agentic RL training is currently fragmented across OpenRLHF, verl, and various Megatron-adjacent stacks — each with significant infrastructure overhead and opaque codebases. Molt's explicit design goal is researcher legibility at frontier MoE scale. The limitation: no published throughput comparison with Megatron or verl (the README claims "statistically comparable" without numbers, and the paper is too new for independent replication). Watch for the first independent benchmarks. If the throughput claims hold, Molt would lower the barrier to agentic RL research at 100B+ scale considerably — the current alternative requires deep Megatron expertise.

**[IF THIS CONTINUES] The open-weight hardware floor is rising faster than enterprise GPU availability — Modified-MIT licenses are becoming governance tokens, not access tokens**
Kimi K3 is the most liberally licensed frontier model ever released (Modified-MIT, fine-tuning permitted), yet its ~594GB MXFP4 footprint (plus runtime buffers) requires infrastructure that is simply unavailable to the vast majority of the open-source community. The previous generation of "large" open-weight releases (Llama 3.1 405B, Mistral Large) ran on 8-GPU A100/H100 nodes — expensive but achievable. K3 needs Blackwell-cluster-scale hardware that most research labs and mid-size companies cannot provision. If the parameter count of frontier open-weight releases keeps growing at this rate (2.8T today), the effective audience for self-hosting collapses to hyperscalers and national labs — the same organizations that already have API access. At that point, the "open" in open-weight refers primarily to auditability and fine-tuning rights, not deployment economics for most practitioners.

**[TENSION] vLLM removes model support without deprecation warnings — but the ecosystem assumes backward compatibility**
vLLM v0.26.0 removes TeleChat, Persimmon, and Fuyu with no prior deprecation notice in the release notes. This is a significant change in how the vLLM project manages compatibility: prior major versions typically gave at least one release cycle of deprecation notice before removing model support. The project's rationale is likely maintenance burden (three less-used architectures), but the precedent matters. If vLLM v0.27+ follows the same pattern for other architectures, operators who deploy vLLM in automated pipelines without pinned versions will face silent failures in production. The correct response is to pin vLLM versions tightly and treat every minor release as a potential breaking change — a shift from how inference servers have historically been managed (treated more like databases: stable, long-lived).
