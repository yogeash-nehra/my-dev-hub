## 🏆 Repo of the Day

### GoogleChrome/modern-web-guidance-src — feeds coding agents current web platform best practices instead of letting them default to 2019 patterns
**Link:** github.com/GoogleChrome/modern-web-guidance-src | **Stars:** ~10.2k (↑ ~4,400 this week) | **Language:** TypeScript/Node.js | **License:** Apache-2.0
**The problem:** Coding agents trained on historical data default to heavy polyfills and legacy APIs — `scroll-snap`, `dialog`, CSS nesting, `has()`, View Transitions — that browsers now handle natively, bloating bundles and creating maintenance debt.
**Why it's today's pick:** +4,400 stars this week is the strongest momentum on the weekly trending board for a genuinely developer-useful tool under 25k stars. This is the official Google Chrome team project, not a weekend experiment: it ships a curated guidance database searchable by feature, a `legacy-scan` CLI that flags legacy patterns in a codebase, and an MCP server so coding agents can retrieve relevant guides at task-start. It's Apache-2.0, runs on Node 22+, and installs in one npx command. The practical outcome: agents (Claude Code, Cursor, Codex) that load modern-web-guidance at the start of a session produce smaller, more correct web code — a compound benefit on every web-facing project.
**Try it in 60 seconds:**
```bash
# Scan a codebase for legacy patterns an agent should modernize
npx modern-web-guidance@latest legacy-scan .

# Or install the full toolkit (interactive wizard)
npx modern-web-guidance@latest install

# Search for guidance on a specific topic
npx modern-web-guidance@latest search "animate a dialog modal backdrop"
```
**Instead of:** Letting an agent use `scrollIntoView` polyfills, hand-rolled `<dialog>` implementations, or `classList.toggle` where `:has()` and CSS nesting now apply — patterns that were correct three years ago and are noisy today.
**Watch out for:** The guidance is curated for the Chrome team's web platform views — it's authoritative on cross-browser support but slightly Chrome-first in framing. Node 22+ requirement. ### [MEDIUM] Cline v4.1.27 + SDK v0.2.1 — read_files cap lifted to ~48k, session.resume, 7,621-model catalog, cloud tasks
**Source:** Cline GitHub Releases | **Date:** 2026-11-21 | **Link:** https://github.com/cline/cline/releases/tag/v4.1.27
**What changed:** `read_files` output cap raised from 8k characters to 2,000 lines / ~48k characters; SDK v0.2.1 adds `session.resume`, cloud task options (initial message, Git snapshot), `ux_verifier` tool, `publish_artifacts` tool, hub commands for provider/model/MCP management, and MCP tool annotation pass-through; model catalog expanded from 6,457 to 7,621 models (94 providers added from models.dev, Lilac and Tempr removed); security fix for two undici crash CVEs (7.30.1); CLI one-shot runs now default to yolo mode unless auto-approve is off or plan mode is saved.
**TL;DR:** Cline v4.1.27 / SDK v0.2.1 raises the `read_files` cap 6× (8k → ~48k), adds `session.resume` for programmatic agents, and ships the largest model catalog update in Cline history (6,457 → 7,621 providers).
**Developer signal:** (1) **`read_files` cap change**: The cap was 8k characters (truncated silently). It is now 2,000 lines / ~48k characters. Any automation or test that expected truncated output will get significantly more content — check for downstream issues in contexts where you rely on file reads being short. The SDK uses a 50k-char cap. (2) **`session.resume` in SDK v0.2.1**: Programmatic agents using the Cline SDK can now call `session.resume` to restart a saved session. This is a key primitive for long-running or fault-tolerant autonomous workflows — an agent that crashes or is cancelled mid-task no longer has to restart from scratch. (3) **Cloud task options**: SDK cloud tasks now accept an `initialMessage` and Git `snapshot` option — useful for seeding a task's starting state from a commit or branch without manual setup. (4) **Yolo mode default in CLI**: One-shot runs (`cline --act "..."`) now default to yolo (auto-approve all) unless `--no-auto-approve` is passed, a mode flag is specified, plan mode is saved, or the prompt is a `/team` prompt. If you use one-shot CLI runs in CI and do not want auto-approval, verify your invocation flags. (5) **Model default changes**: 67 providers now default to Kimi K3.1 Pro, Gemini 4 Neon, or DeepSeek V4.1 Flash 1017 — if you use a ClinePass subscription, check whether your preferred model is still the default. (6) **Security**: Upgrade to v4.1.27 / SDK v0.2.1 to get undici 7.30.1 (fixes two process-crash issues that affected the 7.x line). (7) **MCP tool annotations**: The SDK now passes `read-only` and other tool annotations from MCP servers through to clients — matching the UI badge added in the Desktop and CLI. If you build MCP servers, declare read-only annotations now; Cline clients render a badge and can gate approval behavior on them.
**Affects you if:** You use Cline in automation with `read_files` and expect short output; you build programmatic agents with the Cline SDK and need session persistence; you run one-shot CLI commands in CI; you have ClinePass and care about default model selection; you build MCP servers and want annotation support.
**Adoption effort:** Moderate (verify `read_files` consumers for the larger output; update CI invocation flags for yolo-mode change; update SDK usage to `session.resume` where relevant).
**Primary source:** https://github.com/cline/cline/releases/tag/v4.1.27 (fetched directly); SDK: https://github.com/cline/cline/releases (sdk/v0.2.1 atom feed entry)

**Source:** GitHub Trending (Nov 16-22, 2026) | **Date:** 2026-11-22 | **Link:** github.com/trending
**What's happening:** Two of the week's strongest-trending repos — GoogleChrome/modern-web-guidance-src (+4,400 stars this week) and kajisho5/ffmpeg-skill (+3,598 stars this week) — follow the same structural pattern: a curated knowledge layer plus a typed tool layer packaged together for coding agents. Teams building agents in specialized domains should watch for these packages before building their own.

**[PATTERN] The read_files cap lift signals a shift in how coding agents treat file I/O**
Cline v4.1.27 / SDK v0.2.1 raised the `read_files` cap from 8k to ~48-50k characters in both the CLI and SDK. This is a 6× increase. The practical implication: for a tool that serves 7,621 providers across millions of agent sessions, this is a deliberate architectural decision — not a default left over from an earlier era. The earlier 8k cap forced agents to read files in chunks and stitch context together manually; the new cap allows full reads of most real-world source files in one call. Combined with Claude Code's existing large context windows (128k max output, 1M token context on Fable 5.2), this represents a converging view across the agent tool ecosystem: file reading is now a first-class, high-bandwidth operation, not an edge case to be rationed.

**[OPEN QUESTION] At 7,621 providers, how do developers actually choose a model in Cline?**
Cline's model catalog expanded from 6,457 to 7,621 models in SDK v0.2.1 — a 1,164-model increase in a single release, mostly from models.dev integration. The selection problem becomes severe: even filtering to "capable of tool use, context > 128k, cost < $5/M input tokens" likely returns hundreds of options. Cline's answer so far is a "recommended" and "free" tier list, plus a "Default option" on the reasoning effort picker that clears saved settings. But this is UI papering over an epistemic problem: when the catalog grows this fast, provider quality signals don't scale with provider count. What's the right evaluation surface for a team that wants to adopt a new provider from models.dev? This question doesn't have a clear answer today.
*Grounded in: Cline SDK v0.2.1 model catalog 6,457→7,621, 94 providers added from models.dev (this digest); Cline v4.1.27 "Default option" for reasoning effort (this digest)*

**[BUILDER'S ANGLE] Cline's `session.resume` + cloud task options unlock a new agent error-recovery primitive**
SDK v0.2.1 ships `session.resume` for saved sessions and cloud task options including an `initialMessage` and Git `snapshot`. Together, these make a specific pattern possible: start an agent task with a Git snapshot of a known-good commit, run the agent, and if it goes wrong, call `session.resume` from the same snapshot state. The agent resumes with the same starting context, not a corrupted mid-task state. For CI agents (automated code review, test generation, refactoring sweeps), this creates a lightweight checkpoint-and-resume loop without full container re-provisioning. The gap: `session.resume` is a Cline SDK primitive, not a managed checkpoint system — if the cloud session is lost entirely (server restart, billing issue), the snapshot is what determines recoverability. Teams building production-grade agent pipelines should pair this with an external snapshot store.
*Grounded in: Cline SDK v0.2.1 session.resume, cloud task options (initialMessage, snapshot) (this digest)*

**[IF THIS CONTINUES] Domain-specific knowledge packages could become a standard pattern alongside MCP servers**
GoogleChrome/modern-web-guidance-src (+4,400 stars this week) and kajisho5/ffmpeg-skill (+3,598 stars this week) both follow the same structural pattern: curated domain knowledge + typed tool layer + MCP server. If this pattern continues, by mid-2027 the ecosystem could have 50+ domain packages covering web APIs, cloud provider resources, database schemas, legal/compliance rules, and accessibility standards — each exposable via MCP to any coding agent. The analogy is npm: a package registry of agent-compatible domain knowledge. What doesn't yet exist is the discovery layer (a "npm search for MCP knowledge packages") and the quality signal layer (how do you know a knowledge package is current and correct?). The gap between package-creation momentum and package-discovery infrastructure is likely where the next tooling opportunity sits.
*Grounded in: GoogleChrome/modern-web-guidance-src trending +4,400 stars this week (this digest); kajisho5/ffmpeg-skill trending +3,598 stars this week (this digest); MCP protocol 2026-07-28 spec (prior digests, not new this period)*

**[TENSION] Cline's yolo-mode default for one-shot CLI runs runs against the governance direction of LoopForge and enterprise Claude Code**
Cline CLI v3.0.75 (released Nov 21) defaults one-shot runs to yolo mode (auto-approve all) unless auto-approve is explicitly disabled. Claude Code v2.1.330 (Nov 20) shipped enterprise sign-in and stricter `rm` safety checks — moving toward requiring approval for risky operations. LoopForge (Nov 21 digest, Rising Dev Tools) adds human approval gates as a first-class governance primitive for multi-agent-CLI workflows. These three trends are in tension: Cline is making autonomous one-shot execution easier; Claude Code is tightening safety guardrails; LoopForge is adding governance infrastructure. All three are responding to the same underlying problem (agents doing unsafe things unattended) with opposite defaults. The likely resolution: one of these defaults wins as the community builds intuitions about what "unattended one-shot agent" should mean, and the others converge.
*Grounded in: Cline CLI v3.0.75 yolo mode default (this digest); Claude Code v2.1.330 stricter rm safety (Nov 21 digest); LoopForge approval gates (Nov 21 digest)*
