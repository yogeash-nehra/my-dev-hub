## 🏆 Repo of the Day

### dzhng/jevgrep — find code by asking what it does, not what it's named

**Link:** github.com/dzhng/jevgrep | **Stars:** ~1,670 (trending today) | **Language:** TypeScript | **License:** MIT

**The problem:** `grep`, `ripgrep`, and `glob` find code by exact text or filename — useless when you need to tell a coding agent "find the part that handles retries" or "find the auth middleware" and the codebase uses non-obvious naming conventions.

**Why it's today's pick:** Trending today at position 6 on the daily GitHub list with ~1,670 stars. The timing is sharp: DevDay just shipped the Agents API public beta, which brings new demand for reliable code-discovery tools that work well as coding-agent tool calls. jevgrep's stdout-first, excerpt-based output format is explicitly designed to be piped into agent context — it "prints the relevant files plus verbatim excerpts to stdout," making it drop-in composable with any agent that accepts shell output. No proprietary lock-in; it's a CLI you can vendor as a skill into Claude Code, Codex, or any agent that can call shell tools.

**Try it in 60 seconds:**
```bash
npm install -g jevgrep

# Ask what code does instead of what it's named:
jevgrep "retry logic for API calls"

# For coding agents — pipe directly into context:
jevgrep "authentication middleware" | head -100
```
**Instead of:** Writing elaborate `ripgrep` + `ast-grep` pipelines or manually constructing file-list context for your coding agent — jevgrep wraps Jev's semantic relevance judgment and returns clean, bounded excerpts.

**Watch out for:** Requires a Jev (TypeSafe) account for the relevance model calls — it's not purely local (the relevance scoring hits an external API). Still pre-1.0; the skill description trigger condition bug (Issue #29) means agents may not auto-load it without manual configuration.

## API & SDK Changes

### [HIGH] OpenAI Agents API — public beta with managed runtime, hosted computer use, MCP, and parallel subagents
**Source:** OpenAI DevDay 2026 | **Date:** September 29, 2026 | **Link:** https://openai.com/index/devday-2026-recap/

**What changed:** The Agents API graduates to public beta. Previously, developers had to build orchestration (sessions, context compaction, recovery) manually on top of the Responses API. The Agents API abstracts that infrastructure: OpenAI handles session lifecycle, orchestration, context compaction, and recovery; developers define tools and environments and get access to a hosted browser (computer use), MCP server connections, and parallel subagent dispatch.

**TL;DR:** OpenAI's Agents API public beta delivers a fully managed agent runtime — sessions, context compaction, computer use via hosted browser, MCP server connections, parallel subagents, and durable session state — so you supply tools and logic, not infrastructure.

**Developer signal:** This is the most significant developer-facing announcement from DevDay. Previously building an agent loop on OpenAI required you to manage sessions, handle context compaction manually, provision a browser environment for computer use, and write your own recovery logic. The Agents API public beta removes all of that: you declare tools, connect MCP servers, and spin up parallel subagents via the API; OpenAI's infrastructure handles the rest. Concretely: computer use now requires no separate browser provisioning (use the hosted browser via the API); MCP servers connect directly without a proxy layer; parallel subagents are a first-class primitive rather than a pattern you implement yourself. For teams currently running agent workloads on the Responses API with manual orchestration: this is worth evaluating for workloads where operational overhead (session recovery, compaction) is a pain point. The Agents API also underpins the new Codex multi-agent capabilities. AgentKit (Agents SDK + Responses API + Agents API) is the full bundle.

**Affects you if:** You build multi-step agent pipelines on OpenAI's API; you currently provision your own browser environment for computer use; you manually manage context compaction or session recovery in agent loops.

**Adoption effort:** Moderate — new API surface, migration from manual Responses API orchestration requires architectural review.

**Primary source:** https://openai.com/index/devday-2026-recap/ (full docs at developers.openai.com)
*Quality gate score: 8 (official OpenAI +3; concrete new API capabilities +2; primary release blog +2; published today +1)*

## Trends & Emerging Tech

### OpenAI bets on "ChatGPT as operating system" — plugin extensions, Connector Registry, and MCP Events are a platform play
**Source:** OpenAI DevDay 2026 | **Date:** September 29, 2026 | **Link:** https://openai.com/index/devday-2026-recap/

**What's happening:** Beneath the DevDay product announcements is a structural shift: plugin extensions (build full applications inside ChatGPT/Codex, distributed through OpenAI), the Connector Registry (unified admin panel for data sources across ChatGPT and API), and the proposed MCP Events specification (connected apps notify ChatGPT of changes, triggering automations while the user is away). Together these treat ChatGPT as a platform surface — not just a conversational interface — that third-party developers can build on and distribute through. MCP Events specifically proposes that connected apps can push events (new task, message, content change) that ChatGPT monitors and acts on autonomously.

**Why watch this:** The MCP Events spec is particularly significant for developers who already connect apps via MCP: if ratified, it moves MCP from a pull model (agent requests data when needed) to a push model (app triggers agent when something happens). That's a qualitatively different event-driven architecture for agents. Watch modelcontextprotocol/modelcontextprotocol for the Events spec PR. The plugin extensions distribution model is also new: if OpenAI distributes your agent-powered application to all ChatGPT users, that's a meaningful new channel — and distribution through OpenAI raises questions about discovery, approval, and lock-in.
