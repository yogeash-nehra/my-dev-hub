## API & SDK Changes

### [MEDIUM] Anthropic Console: Personal Keys and Service Account Keys Are Now Available
**Source:** Anthropic Platform Release Notes | **Date:** August 27, 2026 | **Link:** https://platform.claude.com/docs/en/release-notes/overview
**What changed:** The Claude Console now offers two new key types — personal keys (tied to a specific user account) and service account keys (tied to a service account) — alongside the existing workspace keys, which are now considered legacy. Personal keys stop working automatically when the linked account leaves the organization; service account keys stop working when the linked service account is removed. Both types can be scoped to a specific workspace or granted cross-workspace admin access.
**TL;DR:** Anthropic added identity-linked API keys (personal and service account) to replace anonymous workspace keys, so org admins can track per-user API usage and ensure keys auto-revoke when people leave.
**Developer signal:** If you currently use workspace API keys (the legacy option), you do not need to migrate immediately — they remain supported. However, for new integrations, prefer service account keys for production workloads (CI pipelines, agents, deployed services) and personal keys for individual development. The key benefit is automatic lifecycle management: when an employee leaves or a service account is decommissioned, its keys stop working without requiring manual revocation. To create these keys: go to **Settings → API keys** in the Claude Console, then select Personal Key or Service Account Key. For organizations already relying on workspace keys for shared pipelines, this is a good time to provision dedicated service account keys and update your key references — it improves your audit trail without requiring code changes (the key format and API usage are identical).
**Affects you if:** You manage API keys for a team or organization using Claude; you operate a CI pipeline or production agent service on Claude and currently share workspace keys; you are an org admin who needs per-user API usage visibility.
**Adoption effort:** Moderate — create new key type in Console, rotate into existing services/config; no API or code changes required.
**Primary source:** https://platform.claude.com/docs/en/release-notes/overview (August 27, 2026 entry)

### [NOTABLE] llama.cpp b10687 — OpenCL Adreno GPU Path Gets 25% Prefill Improvement on X2E, 9% on A7X
**Source:** ggml-org/llama.cpp GitHub Releases | **Date:** August 29, 2026 | **Link:** https://github.com/ggml-org/llama.cpp/releases/tag/b10687
**What changed:** The OpenCL backend's Adreno GPU matmul path was updated with two targeted routing changes: Adreno X2-90 (X2E) now defaults to the xmem GEMM kernel instead of the slower `kernel_mul_mm_f16_f32_l4_lm` kernel; Adreno 740/A7X now bypasses the tiled f32 GEMM for batched f32×f32 operations. Decode performance is unchanged — this is a prefill-only improvement.
**TL;DR:** llama.cpp b10687 delivers 25% faster prefill on Snapdragon X2-90 Adreno GPUs and 9% faster prefill on Adreno 740/A7X GPUs for models with f16 non-expert weights (confirmed on gpt-oss-20b and gemma-3n-E4B respectively).
**Developer signal:** If you run llama.cpp inference on Android devices with Adreno X2-90 or A7X GPUs (Snapdragon X Elite, Snapdragon 8 Gen 3/4-era SoCs), update to b10687. The 25% prefill improvement on X2E and 9% on A7X are meaningful for prompt-heavy workloads — RAG, long system prompts, or any scenario where the user waits on the model processing context. Decode speed (the time between tokens after prefill) is unaffected. No configuration changes needed; the new GEMM path is enabled by default. If you are building on-device inference pipelines targeting Android/Qualcomm hardware, this is worth benchmarking: prefill latency is often the dominant cost in agentic or tool-use patterns where each turn involves a large accumulated context.
**Affects you if:** You run llama.cpp on Android devices with Adreno X2-90 (Snapdragon X Elite) or Adreno 740 / A7X GPUs; you build on-device inference pipelines for Qualcomm Snapdragon hardware.
**Adoption effort:** Quick — update to b10687; no configuration changes.
**Primary source:** https://github.com/ggml-org/llama.cpp/releases/tag/b10687

### [NOTABLE] llama.cpp b10684 — SYCL --fit Algorithm Fixes VRAM Accounting for Intel Arc, Enables 262k Context on Arc b70
**Source:** ggml-org/llama.cpp GitHub Releases | **Date:** August 29, 2026 | **Link:** https://github.com/ggml-org/llama.cpp/releases/tag/b10684
**What changed:** The `--fit` algorithm in the SYCL backend was updated to use accurate peak VRAM calculations based on actual context size, replacing the previous overly conservative VRAM reservation approach. The prior algorithm effectively prevented larger context sizes on Arc GPUs even when VRAM was available.
**TL;DR:** llama.cpp b10684 fixes the SYCL backend's conservative VRAM accounting, enabling a confirmed 262,144-token context window with Qwen 3.8 Q4_K_XL on a single Intel Arc b70 GPU using q8_0 KV storage and `--fit-target 1`.
**Developer signal:** If you run llama.cpp on Intel Arc GPUs (Arc A-series, B-series, Intel integrated Xe2) with the SYCL backend and use `--fit` or `--fit-target` flags, update to b10684. The prior conservative accounting was silently capping usable context below what the VRAM could actually support. With this fix and the tested configuration (Arc b70, Qwen 3.8 Q4_K_XL, q8_0 KV, MTP enabled, 4k micro-batch, `--fit-target 1`), 262k context is achievable — a significant jump from what was practically reachable before. To reproduce: set `--context-size 0 --fit-target 1` and let the algorithm determine the maximum context the VRAM supports; you should see higher context ceilings than before. This is relevant for long-document workloads and code analysis on Intel hardware.
**Affects you if:** You run llama.cpp inference on Intel Arc GPUs (Arc b70, Arc A770, integrated Xe2) using the SYCL backend; you use `--fit` or `--fit-target` for context auto-sizing; you target Intel AI PC hardware.
**Adoption effort:** Quick — update to b10684; existing `--fit` flags work correctly with the fixed algorithm.
**Primary source:** https://github.com/ggml-org/llama.cpp/releases/tag/b10684
*Quality gate score: 9 (official repo +3, concrete result 262k tokens on Arc b70 +2, primary source +2, within window +1, technical +1)*

**[OPEN QUESTION] Will personal/service account keys fully replace workspace keys in Anthropic's model — and what does that signal about the Admin API's intended role?**
Anthropic's new personal keys and service account keys (this digest, API & SDK Changes) are explicitly positioned as replacing workspace keys ("workspace API keys remain supported as a legacy option"). This is the same pattern used when the Files API and Skills API graduated out of beta — mark the new thing as preferred, keep the old thing as legacy, eventually retire it. The more interesting question is the Admin API connection: service account keys tie into the Admin API's `service_accounts` endpoint, which shipped in SDK form on August 26 (this week). Together, these two changes suggest Anthropic is building toward a coherent enterprise identity model: a human logs in → their personal key reflects their permissions; a workload runs → its service account key reflects the workload's authorized scope; an org admin manages both → via the Admin API. If this trajectory holds, the next expected piece is *service account role scoping* — the ability to restrict a service account to specific tools or models. Worth watching the Admin API endpoints for `service_account_permissions` or `service_account_roles` in upcoming SDK releases.
*Grounded in: Anthropic personal/service account keys (this digest, API & SDK Changes); Anthropic Admin API in SDKs (Aug 26, platform.claude.com release notes)*

**[IF THIS CONTINUES] 256k+ context on a sub-$500 consumer GPU within one hardware generation**
llama.cpp b10684 confirms 262,144-token context on a single Intel Arc b70 GPU using Qwen 3.8 Q4_K_XL with the SYCL backend (this digest, Tooling). The Arc b70 is a $300–400 consumer card. Two hardware generations ago, getting 128k context locally on consumer hardware required careful quantization and Apple Silicon with unified memory. The trajectory here is: with accurate VRAM accounting and modern quantization, context limits on consumer hardware are increasingly a software problem, not a hardware one. If the next Arc generation doubles VRAM bandwidth (a plausible expectation given Intel's roadmap cadence), the ceiling rises further. For builders: a local inference setup that can handle 256k context without a data-center GPU is now reproducible today, not theoretical. The practical unlock is for use cases that were previously cloud-only: processing a full codebase in context, summarizing a book-length document, or running a long agent trace locally without chunking.
*Grounded in: llama.cpp b10684 Arc b70 262k context result (this digest, Tooling)*

**[TENSION] API key lifecycle management is maturing exactly as autonomous agents proliferate**
Anthropic's personal and service account keys (this digest, API & SDK Changes) introduce automatic key revocation on account removal — a security control designed for *human* identity management. But the concurrent trend in the Claude ecosystem is the proliferation of autonomous agent deployments: Claude Managed Agents sessions that run for hours, self-hosted sandboxes that mount memory stores, Cowork sessions that operate on behalf of users. These workloads are authenticated by service account keys today, but the service account abstraction is still sparse — there's no rate-limit-per-service-account, no tool-scope restriction per service account, no session budget tied to service account identity. The tension: the identity model is being tightened (keys auto-revoke, usage is attributable) at a time when the deployments are becoming more autonomous and longer-running. If a service account key is revoked mid-agentic-session (because the associated service account was decommissioned), how does an in-flight 48-hour agent session terminate gracefully? The answer from Anthropic's docs is not yet clear.
