You can write a migration test suite in `.bru`, commit it, run it in CI, and never leave VSCode. As today's breaking API changes require testing every integration, having a portable, git-commitable API client is immediately useful. Bruno has no backend sync, no cloud accounts, and no lock-in — everything is plain text on disk.

**Try it in 60 seconds:**
```bash

# In your project root, create a collection:
mkdir bruno-anthropic && cd bruno-anthropic

# Write a quick test against the new API version:
cat > test-messages.bru << 'EOF'
meta {
  name: Test 2026-10-21 API
  type: http
  seq: 1

  url: https://api.anthropic.com/v1/messages
  body: json
  auth: none
```

**Instead of:** Postman collections locked in the cloud, or curl scripts checked into a separate repo, or manually re-testing each SDK migration in an ad-hoc REPL.

## [BREAKING] Breaking Changes

### [BREAKING] Anthropic API version 2026-10-21 — sampling params removed, MessageParam types split, Admin API fields renamed, license to Apache 2.0
**Source:** Anthropic Platform Release Notes + Migration Guide | **Date:** 2026-10-21 | **Link:** https://platform.claude.com/docs/en/release-notes/overview

**What changed:** Anthropic shipped API version `2026-10-21` with four categories of breaking changes: (1) `temperature`, `top_p`, and `top_k` are removed from Messages API — sending any of them now returns 400, even at default values; (2) `document` blocks in `assistant` messages and `citations` on `text` blocks in `user` messages now return 400; (3) `MessageParam` is split into per-role union types across all SDKs, with concrete code changes required; (4) Admin API and Analytics API fields renamed (`roles→role_ids`, `group_id→rbac_group_id`, `name→display_name`, `workspace_id→scope`, `actor.email→actor.email_address`, `summaries→data`). The new major SDK versions (Python 2.0.0, TypeScript 1.0.0, C# 13.0.0, Go 2.0.0, Java 3.0.0, PHP 1.0.0, Ruby 2.0.0, `ant` CLI 2.0.0) all send `2026-10-21` by default and drop the removed parameters from their types. License changed from MIT to Apache 2.0 across all SDKs. On Amazon Bedrock, `2026-10-21` is only available for Claude 4.7 and later models — integrations calling older Bedrock models must stay on the prior SDK version.

**TL;DR:** Seven SDK major versions ship today; `temperature`/`top_p`/`top_k` return 400 on the new API version, and the Admin API drops several field names that must be updated in any dashboard or automation that reads them.

**Developer signal:** The most urgent change is the sampling parameters. If your code sends `temperature`, `top_p`, or `top_k` to the Messages API — which is nearly every production integration — remove all three before upgrading to the new SDK versions. Models like Claude 4.7 and later already ignore them internally; Claude Sonnet 4.6 and earlier will simply not accept non-default values through the new API version, so if you relied on a non-default temperature for consistency, you'll need to either stay on `2023-06-01` for those calls or accept the model's default sampling behavior. For the Admin API renames: search your codebase for `workspace_id` on API key responses, `group_id` on RBAC group member responses, `roles` on RBAC group responses, and `summaries` on Analytics API responses — each has a new name. For TypeScript: `MessageParam` is now `UserMessageParam | AssistantMessageParam | SystemMessageParam`; class extensions need to be changed to type intersections (`type StoredMessage = Anthropic.MessageParam & { id: string }`). For the `ant` CLI Go install path: change `go install 'github.com/anthropics/anthropic-cli/cmd/ant@latest'` to `go install 'github.com/anthropics/anthropic-cli/v2/cmd/ant@latest'`. Bedrock-specific: `2026-10-21` is only valid for Claude 4.7+ on Bedrock — don't upgrade older Bedrock model calls until you also migrate to Claude 4.7.

**Affects you if:** You call the Anthropic Messages API with `temperature`, `top_p`, or `top_k`; you read Admin API or Analytics API response fields listed in the rename table; you use the `anthropic` Python package, `@anthropic-ai/sdk` TypeScript package, or any other officially-supported Anthropic SDK; you use RBAC group management, API key management, or the Enterprise Analytics API in your tooling or dashboards; you run Bedrock integrations on pre-4.7 Claude models.

**Adoption effort:** Significant (remove sampling params from all requests, update SDK versions, fix renamed fields, update TypeScript types, update Go import paths — test thoroughly before releasing).

**Primary source:** https://platform.claude.com/docs/en/api/migration-2026-10-21

## API & SDK Changes

### [MEDIUM] Anthropic — User Profiles launched (Oct 20)
**Source:** Anthropic Platform Release Notes | **Date:** 2026-10-20 | **Link:** https://platform.claude.com/docs/en/release-notes/overview

**What changed:** New `/v1/user_profiles` endpoints are live. You can now tell Anthropic which end customer each API request is for by attaching a user profile ID. When Anthropic takes a safety enforcement action, it can target the specific end customer instead of your whole organization. User profiles also surface `enforcement_status` and `enforcement_actions` fields so you can query which profiles have an open restriction or ban.

**TL;DR:** New `/v1/user_profiles` Admin API endpoints let multi-tenant platforms map API calls to individual end customers, enabling scoped enforcement instead of org-wide suspension.

**Developer signal:** If you run a platform, gateway, or resell API access to end customers, this is the infrastructure change to adopt. Without user profiles, a safety action against one of your users risks your entire organization's API access. With them, Anthropic can restrict a single profile. Integrate: attach a `user_profile_id` parameter to each API request, and poll `enforcement_status[]` on list requests to build a monitoring pipeline that alerts you when a profile is restricted. The new SDK versions (Python 2.0.0, TypeScript 1.0.0) include typed support for the user profile endpoints — another reason to migrate to the new SDK versions today.

**Affects you if:** You build multi-tenant AI applications, operate an API gateway or reseller, or need per-end-customer compliance controls.

**Adoption effort:** Moderate (integrate user profile creation and ID attachment into your request pipeline; build monitoring against `enforcement_status`).

**Primary source:** https://platform.claude.com/docs/en/api/user_profiles
*Quality gate score: 8 (official Anthropic source +3; concrete new endpoints with typed fields +2; primary source link +2; within window — Oct 20 +1)*

### [MEDIUM] Anthropic — Organization Webhooks beta (Oct 20)
**Source:** Anthropic Platform Release Notes | **Date:** 2026-10-20 | **Link:** https://platform.claude.com/docs/en/release-notes/overview

**What changed:** Organization-level webhooks are available in beta via the `webhooks-2026-10-07` beta header and the new `/v1/organizations/webhooks` endpoints. Two event types are supported: (1) a user profile is restricted or banned, (2) that restriction or ban ends. Access requires contacting your Anthropic account team.

**TL;DR:** Anthropic Admin API now supports org-level webhooks (beta) for user profile enforcement events — get a push notification when Anthropic restricts or un-restricts one of your end customers.

**Developer signal:** Pair this with User Profiles (above). Instead of polling `enforcement_status` in a cron job, register a webhook endpoint and get push notification when a profile state changes. This is the right integration for compliance-sensitive platforms that need real-time response to enforcement events — for example, automatically suspending a customer's session or triggering an ops escalation. The beta header requirement and account team access gate suggest this is still in limited availability; contact your account team to request access now rather than waiting.

**Affects you if:** You build on the Admin API, run compliance-sensitive multi-tenant platforms, or need real-time enforcement event notification.

**Adoption effort:** Moderate (webhook endpoint implementation + account team access request).

**Primary source:** https://platform.claude.com/docs/en/api/beta/organization/webhooks

## Tooling

### [MEDIUM] Claude Code v2.1.305 — sandbox.allowNestedUserNamespaces, Vertex/Bedrock retry fix, allowedMcpServers behavior change
**Source:** GitHub Releases | **Date:** 2026-10-20 | **Link:** https://github.com/anthropics/claude-code/releases/tag/v2.1.305

**What changed:** Three notable changes: (1) New `sandbox.allowNestedUserNamespaces` setting lets sandboxed Linux commands create user namespaces — required for Chromium and rootless podman, but explicitly weakens file isolation; (2) Fixed a 2.1.304 regression where requests to Vertex, Bedrock, and other providers failed when the gateway rejected tool search — Claude Code now retries without it; (3) `allowedMcpServers` no longer filters `managed-mcp.json` stdio servers that use `${VAR}` only in `env` — a server your allowlist previously excluded may now load on upgrade. Also fixed: worktree bare repo handling, full-disk error messages, wrong model named after fallback, workflow resume re-running completed pipeline/parallel agents.

**TL;DR:** Claude Code v2.1.305 introduces a security-relevant sandbox toggle for nested user namespaces and fixes a Vertex/Bedrock tool-search regression from 2.1.304 that was breaking provider requests.

**Developer signal:** The Vertex/Bedrock regression fix is the most immediately actionable item — if you saw provider request failures after upgrading to 2.1.304, upgrade to 2.1.305 now. For the sandbox toggle: `sandbox.allowNestedUserNamespaces` defaults to off. Enable it only when you specifically need Chromium (for browser automation or Playwright inside a sandboxed session) or rootless podman. The release notes explicitly state that enabling it "lets sandboxed commands get around the sandbox's file protections" — this is a deliberate trade-off, not a safe default. For the allowedMcpServers change: after upgrading, check if any previously-excluded managed MCP servers now load that you don't want running. Use `deniedMcpServers` to explicitly block them going forward.

**Affects you if:** You use Claude Code on Vertex or Bedrock (regression fix); you run browser automation or container tools inside Claude Code's Linux sandbox; you have `allowedMcpServers` configured and use managed-mcp.json stdio servers.

**Adoption effort:** Quick for the Vertex/Bedrock fix (version upgrade). Moderate for sandbox and MCP changes (review config, set `deniedMcpServers` where needed).

**Primary source:** https://github.com/anthropics/claude-code/releases/tag/v2.1.305

### Anthropic's API consolidation signals a stable-API phase
**Source:** Anthropic Platform Release Notes + Migration Guide | **Date:** 2026-10-21 | **Link:** https://platform.claude.com/docs/en/api/migration-2026-10-21

**What's happening:** Today's API version bump is unusual in scope: seven SDK major versions, a license change (MIT → Apache 2.0), and breaking changes that remove longstanding API parameters entirely rather than deprecating them with a grace period. The sampling parameter removal is the clearest signal — `temperature`/`top_p`/`top_k` are gone, and Anthropic's note ("models that already accept only the defaults, such as Claude 4.7 and later models, sample as before") suggests these have been internalized into the model layer. The MessageParam type refactor is a similar consolidation: moving from a loose single type to role-specific unions is a "lock in the types now and don't change them again" move.

**Why watch this:** If Anthropic is moving sampling control into the model layer, the next question is whether future APIs expose more model-level sampling control (prompting-based or system-prompt-based) rather than raw API params. The Apache 2.0 license change makes the SDKs easier to embed in commercial products and distributions — a subtle signal about where Anthropic sees its SDK ecosystem going. The combination of stable types + license freedom + user-profile enforcement infrastructure reads as Anthropic building for a larger enterprise developer base.
