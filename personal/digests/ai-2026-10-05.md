## 🏆 Repo of the Day

### mvschwarz/openrig — Persistent multi-agent fleet manager for Claude Code, Codex, and Pi
**Link:** github.com/mvschwarz/openrig | **Stars:** ~5,200 | **Language:** TypeScript | **License:** Apache-2.0

**The problem:** Running more than two or three Claude Code or Codex agents at once turns into a mess of uncoordinated terminal sessions — no shared context, no topology view, no recovery when a seat crashes or clears.

**Why it's today's pick:** OpenRig v0.6.5 (released October 4) is the first mature open-source tool built specifically for persistent teams of coding agents. You define your agent topology in a YAML RigSpec (pods, edges, roles, continuity policies), `rig start`, and you get a TUI showing live seat status, a communication layer (`rig send`, broadcast, Slack threads), and snapshot/restore so your fleet survives a `/clear` or shutdown. v0.6.5 specifically fixed conversation continuity for Claude seats after `/clear` commands and added `effort` level control per seat (maps to `--effort` for Claude, `model_reasoning_effort` for Codex). At 5.2k stars with releases on Oct 2 and Oct 4, it's on an active trajectory — not a spike. It's the project that answers the "agent sprawl" problem before it becomes a household name.

**Try it in 60 seconds:**
```bash
# Install (requires Node.js 22+, tmux, macOS/Linux)
npm install -g @openrig/cli

# Dry-run setup to verify prerequisites
rig setup --dry-run

# Start a simple two-seat rig (once you have a rigspec.yaml)
rig start rigspec.yaml
```
**Instead of:** Managing 5+ `claude` terminal sessions manually, copy-pasting context between them, and losing everything on a crash.

**Watch out for:** Windows WSL2 is untested. Pre-1.0 — RigSpec YAML schema is still evolving between minor versions; pin your version in production and read the migration notes before upgrading. Requires tmux; optional herdr or cmux for workspace layout.

### [BREAKING] Google Antigravity Preview 05-2026 — Hard Shutdown Today; write_to_file Patch Format Required
**Source:** Google AI for Developers | **Date:** October 5, 2026 | **Link:** https://ai.google.dev/gemini-api/docs/models/antigravity-preview-05-2026

**What changed:** `antigravity-preview-05-2026` is now shut down. The September preview (`antigravity-preview-09-2026`) became the replacement when it shipped September 17, and the 18-day migration window closed today. Two completely different migration paths exist depending on how your integration works.

**TL;DR:** Any code calling `antigravity-preview-05-2026` with local tool execution is getting "version no longer supported" errors right now; remote-output-only callers may get a graceful redirect but should still migrate to avoid silent behavior changes.

**Developer signal:** Check which path applies to your integration before anything else. **Path 1 (remote sandbox, output_text or model_output only):** change the model string to `antigravity-preview-09-2026`. That's it — the server handles the rest, and you may already be getting a silent redirect. Still migrate explicitly to avoid relying on redirect behavior. **Path 2 (local_environment or parsing function_call yourself):** this is a breaking migration. The built-in tool schemas changed from snake_case to PascalCase arguments across the board, and the file-editing tool changed its fundamental behavior: `write_file` (full-text replacement) is now `write_to_file` with `StartLine`/`EndLine`/`NewContent` patch blocks; `read_file` → `view_file`; `list_files` → `list_dir`. Any code that deserializes tool arguments, routes on tool name, or processes file edits must be updated before it can call the September preview. An integration test against the new model ID in a staging environment is required — do not just swap the string and ship.

**Affects you if:** You call `antigravity-preview-05-2026` anywhere — in a production agent, a CI pipeline, a scheduled workflow, or a dev script; more specifically if your integration runs in `local_environment` or parses `function_call` outputs.

**Adoption effort:** Quick (remote-output-only: one string change) / **Significant (local tool execution: schema migration, rename all tool call handlers, update file-edit logic to patch format).**

**Primary source:** https://ai.google.dev/gemini-api/docs/models/antigravity-preview-05-2026

The fix is specific to configs with explicit `remote_env` keys — only those activate the allowlist that was filtering Windows system vars. If your Windows MCP servers were initializing but occasionally failing on file writes or temp-path operations, this is the root cause. No config changes needed — just update the package; the patch adds the three vars to the preserved set automatically.

**Affects you if:** You run Codex on macOS or Linux and launch remote stdio MCP servers on Windows hosts or Windows CI runners with explicit remote environment variables configured.

### [NOTABLE] E2B v2.52.1 — Two High-Severity urllib3 CVEs Patched in Desktop Python SDK
**Source:** GitHub Releases (e2b-dev/E2B) | **Date:** October 5, 2026 | **Link:** https://github.com/e2b-dev/E2B/releases/tag/e2b@2.52.1

**What changed:** `@e2b/desktop-python` now requires urllib3 ≥ 2.8.0, patching CVE-2026-97687 (CVSS High) and CVE-2026-97689 (CVSS High). Both CVEs are in urllib3 versions 1.26.0–2.7.x, where HTTPS proxy TLS configuration (proxy_ssl_context, proxy_assert_hostname, ssl_context, cert_reqs, verify_mode) is incorrectly applied to the target-server TLS handshake instead of the proxy connection, allowing a network-adjacent attacker to intercept data. Additional fixes in the broader release: JS SDK `.dockerignore` filtering aligned to BuildKit behavior (handles `**` patterns and emoji); 502 POST retry logic tightened to avoid retrying resource-creating operations that may have already executed.

**TL;DR:** E2B v2.52.1 patches two High urllib3 CVEs (CVSS High, proxy TLS misconfiguration) in the desktop Python SDK; update to urllib3 ≥ 2.8.0 immediately if you use `@e2b/desktop-python` in any non-isolated environment.

**Developer signal:** Run `pip install 'urllib3>=2.8.0'` or update your lockfile to pull in the fixed version, then re-pin `e2b-desktop-python==2.6.1`. The CVE risk is most relevant if your E2B desktop agents make HTTPS requests through an explicit proxy (`HTTPS_PROXY` env var set, or proxy_ssl_context configured) — in that scenario, target-server certs may have been validated against proxy TLS settings rather than the target's own cert. The 502 retry fix is less urgent but prevents double-execution of resource-creating POST calls (e.g. sandbox creation) when a transient 502 occurs mid-request.

**Affects you if:** You use `@e2b/desktop-python` for AI agent computer-use or desktop automation; you run desktop sandboxes through an HTTPS proxy.

**Adoption effort:** Quick (dependency bump to urllib3 ≥ 2.8.0 + `e2b-desktop-python==2.6.1`).

## Trends & Emerging Tech

### Agent Fleet Management Is Becoming a Product Category
**Source:** GitHub Trending (mvschwarz/openrig, weekly), agent tooling landscape October 2026

**What's happening:** OpenRig's traction and v0.6.5 feature set signal that "run multiple coding agents as a coordinated team" is transitioning from a bespoke script problem to a supported product category. Three converging pressures are driving this: (1) coding agents now accept `--effort` / `model_reasoning_effort` flags, creating a resource-allocation problem across a fleet; (2) Claude Code's mod API (v2.1.289 `agent.spawn`) makes agent-spawning a first-class operation; and (3) real deployments expose the state-management problem — agents that share a repo but not a context produce contradictory edits. OpenRig is the first tool to address all three with a single abstraction (RigSpec topology + persistent seats + Slack/tmux communication layer).

**Why watch this:** If fleet orchestration tools mature quickly (as Kubernetes did for containers), the next six months could see: richer scheduling (assign work based on seat idle state), cost-aware routing (route low-effort tasks to cheaper seats), and integration with CI/CD so a rig runs on every PR rather than a single agent. The bottleneck today is that RigSpec is pre-1.0 and Windows support is experimental — teams shipping production multi-agent pipelines are still writing custom orchestration. Watch when OpenRig hits v1.0 and whether Anthropic or OpenAI bless any orchestration layer in their official tooling docs.
