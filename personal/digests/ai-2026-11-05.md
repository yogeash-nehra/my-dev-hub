No vision model required — the agent picks an action based on element refs. **Try it in 60 seconds:**
```bash

agent-desktop status              # check platform support and permissions
agent-desktop permissions --guide # (macOS) grant Accessibility access
agent-desktop snapshot --app Finder -i  # see the full accessibility tree as JSON
agent-desktop click @<ref-from-snapshot>  # act on a stable element ref
agent-desktop snapshot --app Finder -i   # verify the action changed state
```
**Instead of:** Screenshot-based computer-use loops that break on resolution changes, retina displays, or dynamic UI updates.

**Watch out for:** LABS badge — this is Vercel Labs experimental work, not a stable production release. No formal GitHub Releases entries yet. ### [NOTABLE] Anthropic SDK Python v2.6.0 / TypeScript sdk-v1.6.0 — OTel sampling param suppression, ramp limit errors, sign-out support
**Source:** GitHub | **Date:** 2026-11-05 | **Link (Python):** https://github.com/anthropics/anthropic-sdk-python/releases/tag/v2.6.0 | **Link (TS):** https://github.com/anthropics/anthropic-sdk-typescript/releases/tag/sdk-v1.6.0
**What changed:** Both SDKs stop recording sampling parameters on OpenTelemetry spans; add error codes for ramp limit errors and External Key validation failures; add typed support for the new Admin API sign-out endpoint.
**TL;DR:** SDK v2.6.0/sdk-v1.6.0 (Nov 5) addresses the same OTel credential-exposure class as Pydantic AI's GHSA-jp94-mmr3-2pvv (Nov 4) — sampling parameters are no longer recorded in trace spans — and adds error codes for ramp limits and External Key validation.
**Developer signal:**
1. **OTel fix — upgrade now if you trace Claude API calls:** Sampling parameters (`temperature`, `top_p`, `top_k`, and related fields) were previously included in OTel span attributes. If you export traces to Datadog, Jaeger, Grafana Tempo, or any cloud trace provider, those parameters appeared in spans. Any secret inadvertently passed through these fields (e.g., via `extra_headers` or `extra_body` kwargs) would have been captured. After upgrading to v2.6.0 / sdk-v1.6.0, those sampling params are no longer recorded. No code changes required — just upgrade.
2. **Ramp limit errors:** New `RampLimitError` error code makes it possible to handle API throttling specifically caused by organizational ramp limits (distinct from per-minute/per-day rate limits). Useful for production retry logic that needs to differentiate rate-limit types.
3. **External Key validation errors:** Specific error codes for External Key validation failures — useful if your organization uses External Keys for access control.
4. **Bedrock fix (Python):** `bedrock_client.copy()` and `bedrock_client.with_options()` now correctly preserve the custom `http_client` and `aws_profile` on the copied client — a bug that could cause silent credential misconfiguration.
**Affects you if:** You use the Anthropic SDK with OpenTelemetry tracing enabled; you hit ramp limits and want to distinguish them from standard rate limits; you use Bedrock with a custom http_client and call `copy()` or `with_options()`.
**Adoption effort:** Quick (drop-in package upgrade; no code changes required for the OTel fix)
**Primary source (Python):** https://github.com/anthropics/anthropic-sdk-python/releases/tag/v2.6.0

### [MEDIUM] LangGraph 1.2.20 — interrupt IDs per call, opt-in strict resume mode, cancel_reason on Run
**Source:** GitHub | **Date:** 2026-11-05 | **Link:** https://github.com/langchain-ai/langgraph/releases/tag/1.2.20
**What changed:** Each `interrupt()` call in a task now gets its own unique ID (PR #9589); opt-in strict resume mode raises `UnknownInterruptError` on stale or invalid interrupt IDs (PR #9574); `cancel_reason` field added to `Run` in langgraph-sdk 0.4.13 (PR #9571); `select` option added to `threads.get_state` and `get_history` (PR #9568).
**TL;DR:** LangGraph 1.2.20 (Nov 5) replaces index-based interrupt tracking with per-call UUIDs and adds opt-in strict resume semantics — submitting a stale interrupt ID with `strict_resume=True` raises `UnknownInterruptError` instead of silently re-pausing the graph.
**Developer signal:**
1. **Interrupt IDs are now per-call:** Previously, multiple `interrupt()` calls in one task were tracked by index. Now each call gets a UUID. Code that reads interrupt IDs from graph state or the event stream should verify the ID it's using is still pending, not one from an earlier run of the same node.
2. **A retried node reuses earlier interrupt answers:** When a node is retried after a failure, its prior interrupt answers are replayed rather than re-asked. Test your retry paths in existing graphs — a node that previously re-asked the same human question on retry will now reuse the prior answer.
3. **Opt into strict resume:** Pass `strict_resume=True` to `client.runs.create(...)`, `client.runs.stream(...)`, or `client.runs.wait(...)`. When a stale, empty, or ambiguous interrupt answer is submitted, the graph raises `UnknownInterruptError` (with `reason`, `interrupt_ids`, and `pending_ids` fields) rather than silently re-pausing. The thread state is preserved — the graph didn't advance. This turns a hard-to-debug silent double-answer bug into a clear error.
4. **`cancel_reason` on `Run`:** `run.cancel_reason` is now populated when a run is cancelled. Use this to distinguish user cancellation from timeout or server-side error in monitoring dashboards.
5. **`select` on `threads.get_state` / `get_history`:** Narrow the state fields returned — reduces response payload size in multi-key graphs with large state objects.
6. **No breaking changes:** Strict resume is opt-in. Interrupt ID changes affect consumers of raw interrupt IDs from graph state; standard `Command(resume=value)` usage is unaffected.
**Affects you if:** You build multi-step human-in-the-loop workflows with LangGraph `interrupt()`; you use the LangGraph SDK runs API; you have retry logic in LangGraph nodes.
**Adoption effort:** Moderate (verify interrupt ID usage in existing code; enable `strict_resume=True` in staging first; test retried node behavior against saved checkpoints)
**Primary source:** https://github.com/langchain-ai/langgraph/releases/tag/1.2.20
*Quality gate score: 9 (official LangGraph release +3; concrete PR numbers with behavioral descriptions and use cases +2; GitHub releases.atom primary source +2; Nov 5 window +1; technical audience +1)*

If you export traces to any external service and use custom parameters on LLM calls, audit what your spans are recording now — before the advisory hits your stack.

**[OPEN QUESTION] IP allowlisting covers the agent control plane but not the agents themselves — what does that mean for multi-tenant agent services?**
The IP allowlisting docs explicitly state: "The allowlist covers requests to the Claude Managed Agents endpoints, not the agents themselves. It doesn't apply to any networking in the Claude Managed Agents runtime." For a multi-tenant agentic SaaS — where the developer's server calls the Managed Agents API and the agent then makes tool calls on behalf of end users — the allowlist protects the developer's control plane (can't call /agents or /sessions from outside their IP range) but does NOT restrict outbound agent networking. An agent running inside the sandbox can still reach arbitrary endpoints; that traffic is not IP-restricted. For teams building security-sensitive agent workflows, this is an important gap: IP allowlisting + Managed Agents gives you perimeter control on who can provision and start agents, but zero control over what a running agent fetches. That is a different problem, addressed instead by agent-level tool policies and MCP server allowlists.
*Grounded in: Anthropic IP allowlisting docs, Limitations section: "The allowlist covers requests to the Claude Managed Agents endpoints, not the agents themselves" (Nov 5)*
