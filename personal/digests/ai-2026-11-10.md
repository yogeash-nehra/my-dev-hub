### DIYgod/pinky — MCP-native phone control for AI agents, with gateway-enforced human-in-the-loop
**Link:** github.com/DIYgod/pinky | **Stars:** ~1.7k (GitHub Trending, Nov 10) | **Language:** Go + TypeScript | **License:** Apache-2.0
**The problem:** AI agents built for desktop work have no native path to operate a real phone — existing options require custom ADB scripts or brittle screenshot flows, with no approval mechanism when the agent touches payments, messages, or settings.
**Why it's today's pick:** Pinky appeared on GitHub Trending today and fills a gap that became real the moment Fable 5.2 made computer use a first-class API. It connects real iOS (17.4+) and Android (10–17) devices to any MCP client over stdio, so Claude Code, Claude Desktop, Codex, and Cursor can send taps, swipes, and input — but every risky action (payments, settings changes, app installs) requires a human approval click in Pinky's window, enforced by the gateway, not by an instruction to the model. The source has 947 commits and ships versioned releases for macOS (DMG + Homebrew), Windows, and Linux (deb/tar.gz).
**Try it in 60 seconds:**
```bash
# macOS via Homebrew
brew install --cask diygod/tap/pinky
# or download the .dmg from github.com/DIYgod/pinky/releases

# Connect your phone
# Android: enable USB debugging, plug in
# iPhone: enable Developer Mode, plug in, let Pinky install WebDriverAgent

# Add Pinky MCP to Claude Code
# In ~/.claude/settings.json, add under "mcpServers":
# "pinky": { "command": "pinkyctl", "args": ["mcp"] }

# Try a fake phone session first (no hardware needed)

```
**Instead of:** Hand-rolled ADB scripts, Appium configurations, or screenshot-pixel-matching agents operating phones with no human oversight or approval gate.
**Watch out for:** Pre-alpha. iOS setup requires Xcode and Apple's WebDriverAgent helper — first-time setup takes ~15 minutes. Android Wi-Fi pairing works but is slower than USB. No Windows phone support. The approval gateway is local-only (no remote/cloud-hosted mode yet).

## [BREAKING] Breaking Changes

### [BREAKING] Fable 5.2: forced tool_choice and explicit thinking type both return 400 errors
**Source:** Anthropic Platform Docs (What's New in Claude Fable 5.2) | **Date:** 2026-11-09 | **Link:** https://platform.claude.com/docs/en/models/fable-5-2/whats-new-fable-5-2
**What changed:** Two additional Fable 5.2 breaking changes not surfaced in yesterday's digest (from the same Nov 9 release):
1. **Forced tool use blocked:** `tool_choice: {"type": "any"}` or `tool_choice: {"type": "tool", "name": "..."}` returns a 400 `invalid_request_error` on Fable 5.2. Only `tool_choice: {"type": "auto"}` is accepted.
2. **Thinking type parameter invalid:** Sending `thinking: {"type": "enabled"}` with `budget_tokens`, or `thinking: {"type": "disabled"}`, returns a 400 error. Adaptive thinking is always on — omit `thinking` entirely or send `{"type": "adaptive"}` and use the `effort` parameter to control thinking depth.

**TL;DR:** Two more Fable 5.2 400-error conditions: forced `any`/`tool` tool_choice is gone, and the explicit `thinking` enable/disable toggle is gone — both are hard errors, not graceful fallbacks.
**Developer signal:** Before switching `model` to `claude-fable-5-2`, grep your codebase for `tool_choice` with `type: "any"` or `type: "tool"` and migrate to `{"type": "auto"}` with `strict: true` (strict tool use) for schema-valid output, or use JSON outputs mode. Also grep for `thinking: {type: "enabled"}` or `thinking: {type: "disabled"}` and remove those fields — on Fable 5.2, thinking depth is controlled via `effort: "low" | "medium" | "high" | "xhigh" | "max"` (API default: `high`). Teams migrating from Claude Fable 5 or Claude Opus models are most likely to hit these, since those models required explicit thinking toggles. Teams already on Fable 5.1 with neither pattern are unaffected. Note: CMEK (customer-managed encryption key) organizations cannot use structured outputs or strict tool use on Fable 5.2 — validate tool input manually in that case.
**Affects you if:** You set `tool_choice` to `any` or a specific named tool on any Fable model; you pass `thinking: {type: "enabled", budget_tokens: N}` or `thinking: {type: "disabled"}` in your request (common for Fable 5 or Claude Opus codepaths); you are on CMEK and use strict tool use or JSON outputs.
**Adoption effort:** Quick (grep-and-replace on tool_choice and thinking params) / Moderate (CMEK orgs need a workaround)
**Primary source:** https://platform.claude.com/docs/en/models/fable-5-2/whats-new-fable-5-2#thinking-and-tool-choice

## API & SDK Changes

### [MEDIUM] Fable 5.2 extended: server-side fallback for refusals (beta), account-bound thinking, fast mode on three more platforms
**Source:** Anthropic Platform Docs (What's New in Claude Fable 5.2) | **Date:** 2026-11-09 | **Link:** https://platform.claude.com/docs/en/models/fable-5-2/whats-new-fable-5-2
**What changed:** Additional Fable 5.2 API details not covered in yesterday's digest (all from the same Nov 9 release):
1. **Server-side fallback for refusals (beta):** Pass `fallbacks: "default"` to have a declined request automatically retried on Anthropic's recommended fallback model for that refusal category. For Fable 5.2, permitted fallback targets are Claude Opus 4.8 and Claude Opus 5. For categories with no recommended fallback (e.g., `reasoning_extraction`), the refusal stands.
2. **Thinking blocks are account-bound:** Thinking blocks produced by Fable 5.2/Mythos 5.2 work only in the account that produced them (or a linked account). Sending them from another account results in a silent drop, not a 400 error. With `thinking-binding-controls-2026-08-01` beta header, the response's `input_transformations` array reports the drop with `reason: "organization_binding_mismatch"`.
3. **Fast mode extended to three more platforms:** Fast mode for Fable 5.2 is now also available on Google Cloud (Anthropic managed), Google Cloud (Google managed), and Microsoft Foundry (as separate model `claude-fable-5-2-fast`). Previously only on the Claude API.
4. **New beta headers:** `compact-2026-09-04` (compaction on demand — control when older turns are summarized), `inline-tools-2026-09-15` (mid-conversation tool changes via `role: "system"` messages instead of editing `tools`), `thinking-binding-controls-2026-08-01` (get `input_transformations` on thinking block drops/mismatches).

**TL;DR:** Fable 5.2 adds a `fallbacks: "default"` parameter for automatic refusal fallback to Opus 4.8/Opus 5, account-bound thinking that drops silently cross-account, fast mode on three additional platforms, and three new beta headers for context management.
**Developer signal:** Add `fallbacks: "default"` to production Fable 5.2 requests if you want graceful handling of safety refusals — the API retries automatically on Opus 4.8 or Opus 5. If you're building multi-tenant systems that share thinking blocks across accounts, this will silently fail: thinking blocks must stay in the originating account's API calls. Enable `thinking-binding-controls-2026-08-01` during development to surface drops explicitly. If you use compaction (long agentic sessions that need to trim context without breaking the prefix check), `compact-2026-09-04` lets you trigger compaction at a point you choose rather than having the model decide. If you're on Google Cloud or Microsoft Foundry, fast mode is now available — use `speed: "fast"` or the `claude-fable-5-2-fast` model ID on Foundry.
**Affects you if:** You want auto-retry on refusals; you share thinking blocks across API accounts or orgs; you deploy on Google Cloud or Microsoft Foundry; you manage context windows in long agentic sessions.
**Adoption effort:** Quick (add `fallbacks: "default"` parameter) / Moderate (refactor multi-tenant thinking-block sharing)
**Primary source:** https://platform.claude.com/docs/en/models/fable-5-2/whats-new-fable-5-2

## Trends & Emerging Tech

### MCP as the universal agent control plane — now phones, desktops, and CI
**Source:** DIYgod/pinky (github.com/DIYgod/pinky) + vercel-labs/agent-desktop (Nov 9 digest) | **Date:** 2026-11-10
**What's happening:** In the span of two days, MCP-based tool servers have appeared for desktop UI automation (agent-desktop, Nov 9) and now physical phone control (pinky, Nov 10). Both enforce human-in-the-loop approvals at the gateway level — meaning the approval mechanism is structural rather than prompt-based, and can't be overridden by an adversarial instruction. The pattern: the agent sends a named MCP tool call, the gateway intercepts and either executes it or surfaces it for human approval, the result flows back to the agent.
**Why watch this:** The convergence of Fable 5.2's `computer_toolset_20260801`, MCP's growing adoption, and standalone gateway-enforcement tools is quietly assembling the primitives for a human-supervised agent execution layer. Developers building multi-step agents that touch production environments (databases, phones, production servers) now have a framework pattern: use MCP tool servers as the execution layer, embed approval gates in the server implementation, and keep the agent model stateless with respect to the approval flow. The open question: can these standalone MCP gateways compose (phone + desktop + browser + CI in one approval UI)?

**[OPEN QUESTION] Can gateway-enforced approval models scale to multi-agent pipelines?**
Both agent-desktop (Nov 9) and pinky (today) enforce approvals at the MCP gateway, not via model instruction. This is structurally superior for safety: a rogue or confused agent can't simply override the approval by telling itself "I have permission." But in a multi-agent pipeline — where a Fable 5.2 orchestrator spawns subagents — which gateway do approvals surface in? If the orchestrator delegates a phone action to a subagent, and the subagent has its own pinky MCP connection, the human sees an approval prompt from the subagent's session, with no context about the orchestrator's intent. Neither tool addresses this yet. The right model is probably a shared approval bus where all agents in a session route approvals through a single UI — this is unbuilt.
*Grounded in: DIYgod/pinky gateway enforcement description (this digest, Rising Dev Tools); vercel-labs/agent-desktop gateway model (Nov 9 digest, Rising Dev Tools); Fable 5.2 multi-agent subagent patterns (Nov 9 digest, model release)*

**[TENSION] Account-bound thinking blocks conflict with multi-tenant agent architectures**
Fable 5.2 thinking blocks work only in the account that produced them. This surfaces a real tension for teams building multi-tenant SaaS on Claude: if Tenant A's conversation generates thinking blocks and those blocks are stored (e.g., in a session replay system or a shared RAG store), replaying them against Tenant B's API credentials silently drops the thinking, producing a different model response from the same input. The drop is silent unless you opt into the `thinking-binding-controls-2026-08-01` beta header. Any architectural pattern that serializes and replays conversations across API credentials — multi-tenant proxy, debugging replay, A/B eval harness — now needs an explicit account-matching check before passing thinking blocks.
