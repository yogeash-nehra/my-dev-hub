## API & SDK Changes

### [HIGH] Anthropic SDK Python v0.124.0: Files + Skills APIs GA, Computer Use + Browser Use Toolsets
**Source:** Anthropic / GitHub | **Date:** August 19, 2026 | **Link:** https://github.com/anthropics/anthropic-sdk-python/releases/tag/v0.124.0
**What changed:** Files API and Skills API promoted from beta to GA; two new SDK-level toolsets (`computer_use` and `browser_use`) added as convenience wrappers replacing manual tool-array construction.
**TL;DR:** The Anthropic Python SDK v0.124.0 makes Files and Skills production-stable and adds pre-built toolset objects for computer automation and browser control, reducing boilerplate for agentic workflows.
**Developer signal:** If you were using Files or Skills APIs with a beta header, remove it — these are now GA and the beta header is no longer required. More importantly, the new toolsets (`computer_use_toolset` and `browser_use_toolset`) replace the pattern of manually constructing `{"type": "computer_20251124", ...}` arrays in your `tools` parameter. Import the toolset object from the SDK, pass it to your `client.messages.create()` call, and the correct tool definitions are injected automatically. This is especially useful if you're building agents that switch between computer use and other tools — you no longer maintain the tool list by hand. Computer use itself remains in beta (still requires the `computer-use-2025-11-24` header), but the SDK-level abstraction is stable.
**Affects you if:** You are using the Anthropic Python SDK and either (a) calling the Files API or Skills API with a beta header, or (b) building agents that use computer use or browser automation and currently define tools manually.
**Adoption effort:** Moderate — remove beta headers for Files/Skills, refactor tool-array construction to use the new toolset helpers.
**Primary source:** https://github.com/anthropics/anthropic-sdk-python/releases/tag/v0.124.0

### [MEDIUM] Anthropic Admin API: Claude Enterprise User Management Endpoints Now GA
**Source:** Anthropic Platform | **Date:** August 19, 2026 | **Link:** https://platform.claude.com/docs/en/release-notes/overview
**What changed:** Admin API user-management endpoints (members, invites, groups, custom roles) for Claude Enterprise (claude.ai) orgs promoted from beta to GA; the `anthropic-beta: ce-user-management-2026-07-13` header is no longer required on group and custom-role requests.
**TL;DR:** Group and custom-role management via the Admin API is now production-stable — no beta header needed on any user-management endpoint.
**Developer signal:** Audit your Admin API client code and remove `anthropic-beta: ce-user-management-2026-07-13` from headers on group and custom-role requests. Requests that still send it are accepted unchanged (backward compatible), but the header can be cleaned up. Member and invite endpoints already took no beta header, so those calls are unchanged. If you're using an Anthropic SDK version that set this header automatically (SDKs released between July 14 and today), update to the latest SDK which will drop it. The Admin API is now the stable, production path for Claude Enterprise org provisioning.
**Affects you if:** You are building admin tooling for a Claude Enterprise (claude.ai) organization and calling `PATCH /v1/organizations/{org_id}/groups/*` or custom-role endpoints with the beta header.
**Adoption effort:** Quick — remove the `anthropic-beta: ce-user-management-2026-07-13` header from affected calls.
**Primary source:** https://platform.claude.com/docs/en/manage-claude/user-management

## Tooling

### [NOTABLE] Anthropic Platform: Workbench Becomes Playground
**Source:** Anthropic Platform | **Date:** August 18, 2026 | **Link:** https://platform.claude.com/playground
**What changed:** The Claude Console Workbench (platform.claude.com/workbench) has been replaced by Playground (platform.claude.com/playground). Playground supports every Messages API parameter, shows the full SDK request and the raw API response for each run, and includes templates demonstrating API features like code execution and web search.
**TL;DR:** Playground replaces Workbench with full Messages API parameter coverage and live SDK-request/response inspection — a better API-exploration tool than its predecessor.
**Developer signal:** If you bookmarked platform.claude.com/workbench, update to platform.claude.com/playground. The old URL is retired (legacy Workbench access ended August 17). The "show SDK request" feature generates the exact Python/TypeScript SDK call for whatever you configure in the UI, including newer parameters like `effort`, `fallbacks`, and mid-conversation tool changes. If you relied on the experimental prompt tools APIs (`/v1/experimental/generate_prompt`, `/v1/experimental/improve_prompt`, `/v1/experimental/templatize_prompt`) that were retired with Workbench on August 17, there is no replacement in Playground — those endpoints are permanently gone.
**Affects you if:** You used platform.claude.com/workbench for prompt development, or if you were calling the experimental prompt generation/improvement endpoints.
**Adoption effort:** Quick — update bookmarks; note that experimental prompt endpoints are permanently retired.
**Primary source:** https://platform.claude.com/docs/en/release-notes/overview

**[BUILDER'S ANGLE] Ollama's model metadata cache (rc1) points at the next optimization frontier: per-request overhead, not just throughput**
Most inference optimization work in the past 6 months has focused on throughput (FlashAttention 4, FP8 KV cache in vLLM v0.27.0, prefix caching). Ollama v0.32.15-rc1's model metadata cache targets a different dimension: per-request overhead — the fixed cost paid before any inference begins. For use cases with many short, frequent requests (chatbots, function-calling loops, tool dispatch), per-request overhead can dominate the latency profile even when token throughput is excellent. If this cache lands in stable and shows measurable latency reduction on short-request workloads, it opens a question for the inference stack broadly: how much of "slow first-token time" in local inference is overhead vs. actual prefill computation? This is the kind of optimization that doesn't appear in standard benchmark setups (which typically measure sustained throughput, not cold-start overhead).
*Grounded in: Ollama v0.32.15-rc1 model metadata cache (this digest, Quick Hits); vLLM v0.27.0 FlashAttention 4 + FP8 KV cache (Aug 10–11 releases, referenced in Aug 18 digest Horizon)*
