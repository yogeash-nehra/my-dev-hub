With MCP config scanning built in — a genuinely new capability that no major scanner offered before — it lands at the right moment: MCP proliferation means more surfaces to audit, and Bumblebee is the only tool that covers npm, PyPI, Go modules, RubyGems, Composer, MCP configs, editor extensions, and browser extensions in a single read-only binary pass. The star curve has been climbing steadily since launch and accelerated after v0.1.1; still at 5k, well under the radar.
**Try it in 60 seconds:**
```bash
# Install (macOS or Linux, no runtime required)
brew install perplexityai/tap/bumblebee
# or download the binary directly:
curl -sL https://github.com/perplexityai/bumblebee/releases/latest/download/bumblebee-linux-amd64 -o bumblebee && chmod +x bumblebee

# Run a project scan (read-only — it inspects metadata, never executes code)
./bumblebee scan --profile project .
# Outputs: any package, extension, or MCP config matching known compromise advisories
```
**Instead of:** Manually grepping package.json / requirements.txt / go.mod against a CVE list, or waiting for Dependabot to flag a transitive dep. Unlike `npm audit`, Bumblebee covers cross-ecosystem in one pass and doesn't need `npm install` to run.
**Watch out for:** English-only advisory catalog for now (v0.1.x); MCP config scanning depth varies by spec version; Windows support is experimental. No CI integration out of the box — you'd run it as a pre-commit or periodic script yourself.

## API & SDK Changes

### [MEDIUM] GitHub Actions: New Runner Version Deprecation API + `vulnerability-alerts` Permission for GITHUB_TOKEN
**Source:** GitHub Changelog | **Date:** September 3, 2026 | **Link:** https://github.blog/changelog/2026-09-03-github-actions-early-september-2026-updates/
**What changed:** Two new capabilities shipped in GitHub Actions: (1) A new REST API endpoint — `GET /actions/runners/deprecations/{version}` at repo, org, or enterprise scope — returns the runner version's `runtime_deprecates_at` and `registration_deprecates_at` timestamps, so you can plan upgrades before GitHub starts auto-upgrading or refusing registrations. (2) The `vulnerability-alerts` permission is now supported in GITHUB_TOKEN grants, with `read` and `none` values — allowing workflows to query Dependabot alerts without needing broad `security-events: read` or a PAT.
**TL;DR:** GitHub Actions now exposes a runner deprecation timeline API (never be surprised by a forced runner upgrade again) and adds a scoped `vulnerability-alerts: read` permission so Dependabot-reading workflows can follow least-privilege without a PAT.
**Developer signal:** For the runner deprecation API: if your org manages self-hosted or custom-image runners, wire `GET /actions/runners/deprecations/{version}` into your runner maintenance workflow now. The response tells you exactly when GitHub will reject new registrations of that version and when existing runtime support ends — you can automate a pre-deprecation upgrade reminder instead of discovering it mid-pipeline. For the `vulnerability-alerts` permission: audit any workflow that reads Dependabot alerts (security dashboards, triage bots, merge-blocking checks). If it currently uses `security-events: read` or a PAT scoped wider than it needs, replace with `permissions: vulnerability-alerts: read` in the workflow file. This is the right permission shape for supply-chain security workflows going forward — GitHub is moving toward per-capability permissions rather than broad security scopes.
**Affects you if:** You manage runners (self-hosted or custom images) at org or enterprise level and want to avoid forced upgrade surprises; you have workflows that query Dependabot/vulnerability data and currently over-scope their permissions.
**Adoption effort:** Quick — add `permissions: vulnerability-alerts: read` to relevant workflow files; optionally wire the deprecation API into runner management scripts.
**Primary source:** https://github.blog/changelog/2026-09-03-github-actions-early-september-2026-updates/

## Tooling

### [MEDIUM] Claude Code v2.1.261 — `/skill-doctor`, 128K Inline Output Limit, Subagent System Prompt File
**Source:** Anthropic (Claude Code Changelog) | **Date:** September 4, 2026 | **Link:** https://code.claude.com/docs/en/changelog
**What changed:** v2.1.261 ships 67 changes: the headline additions are `/skill-doctor` (a new command that lists which loaded skills a session never called and the context cost each one consumed), `bashOutputMaxChars` and `taskOutputMaxChars` settings raised to a maximum of 128K characters (previously ~16K, keeping large command outputs inline rather than writing to a temp file), and `--append-subagent-system-prompt-file` (reads a subagent's system prompt from a file path, for prompts too large for the command line). `/status` and `claude doctor` now include an "Organization policy" line showing why a managed organization policy could not be loaded (e.g., a proxy not passing the config endpoint through). SDK and cloud sessions now honor Stop/interrupt signals sent immediately after the first prompt, so responses stop early instead of running to completion. Two breaking changes are included (minor CLI behavior changes affecting edge-case invocations).
**TL;DR:** Claude Code v2.1.261 raises inline command output from ~16K to 128K characters (keeping full context for large builds), adds `/skill-doctor` to audit unused system-prompt skills, and ships 46 bug fixes including subagent interrupt handling.
**Developer signal:** Three concrete things to update: (1) If your session system prompt includes many skills (CLAUDE.md loading several skill files), run `/skill-doctor` to see which are never called and their token cost — dropping unused skills directly reduces context window pressure and cost. A session with 5 loaded skills where 3 are unused may recover several thousand tokens per turn. (2) Add `bashOutputMaxChars: 65536` or higher to your Claude Code settings if you frequently run commands that produce large output (build logs, test suites, lint reports) — with the old 16K limit, Claude was silently reading a file instead of seeing the inline output, which reduced its ability to act on build failures without an extra tool call. (3) For scheduled or headless sessions: the Stop signal now works immediately after the first prompt fires, so canceling a hung session is more reliable. Check your interrupt/timeout logic if you had workarounds for the old behavior.
**Affects you if:** You load multiple skill files in your Claude Code session (skill-doctor helps you audit); you run commands with large output in Claude Code (128K limit matters); you run Claude Code in headless or SDK mode with interrupt signals.
**Adoption effort:** Quick — update Claude Code binary; `/skill-doctor` works immediately with no config changes.
**Primary source:** https://code.claude.com/docs/en/changelog
*Quality gate score: 9 (official Anthropic changelog +3, concrete feature set with specifics — 128K limit, /skill-doctor, --append-subagent-system-prompt-file +2, primary source +2, within window Sept 4 +1, technical audience +1)*

**[PATTERN] Hardware → Software Vertical Integration Is the Playbook Now**
NVIDIA acquiring Hugging Face follows the same logic as Google's TensorFlow+TPU co-evolution and Microsoft's GitHub+Copilot+Azure arc: owning the hardware layer is not enough when developers choose stacks based on software-layer convenience. NVIDIA's chip dominance is durable only as long as the model training and deployment ecosystem runs on CUDA. Hugging Face is where developers decide what to run — which means NVIDIA is buying influence over that decision, not just downstream inference. The pattern suggests cloud providers and other chip companies (AMD, Intel, Qualcomm, Groq) will face increasing pressure to acquire or deeply partner with developer-facing AI platforms that are currently independent.

**[OPEN QUESTION] What Does "Open Platform" Actually Mean Under Hardware-Company Ownership?**
NVIDIA's written commitment — "Hugging Face will remain an open platform; NVIDIA compute will not be required" — is meaningfully different from "NVIDIA will not advantage its own hardware on the platform." Even with full multi-cloud parity at the API level, GPU-specific features (faster inference API response times, cheaper inference pricing for NVIDIA hardware via NIM, priority SLAs on Spaces) could functionally bias the platform without violating the letter of the commitment. The question every developer team building on Hugging Face infrastructure should have on their radar: does the inference API's pricing and performance stay hardware-neutral after the acquisition closes? Watch the H100 vs. AMD MI300X pricing differential on Hugging Face Inference Endpoints over the next 6–12 months.
*Grounded in: NVIDIA acquisition commitments (this digest); Hugging Face Inference Endpoints current multi-accelerator pricing*

**[BUILDER'S ANGLE] `/skill-doctor` Is a Prototype for What Every Agentic Framework Needs**
Claude Code's `/skill-doctor` command (this digest) reports which loaded skills were never called and their context token cost, letting you trim system-prompt bloat. This pattern — a "profiler" for your agent's system prompt — is missing from every major agentic framework today. LangChain, LlamaIndex, CrewAI, and AutoGen all allow you to load tools and instructions, but none surface unused-tool or unused-instruction cost at runtime. If `/skill-doctor` proves useful in practice (watch community feedback over the next few weeks), expect framework maintainers to add analogous introspection: "your agent loaded 12 tools, called 3, and spent 8,400 context tokens on the other 9." Applied to production agentic workflows, this could reduce the common pattern of over-loading tool definitions "just in case" and measurably lower per-turn cost.
*Grounded in: Claude Code v2.1.261 /skill-doctor (this digest)*

**[TENSION] Supply Chain Scanning Becomes Necessary Just as MCP Proliferates**
Bumblebee (this digest) covers MCP config files as a first-class scan target — the first scanner to do so. This timing is not accidental: MCP server configs point to arbitrary external processes that run with developer-level permissions. As the MCP ecosystem grows (hundreds of community servers, many without formal security audits), MCP configs become as much a supply-chain risk surface as npm's node_modules. The tension: the MCP ecosystem's value proposition is frictionless tool integration (any server, any capability, add to config in 5 minutes). Its security posture is the opposite of that frictionless promise. Bumblebee's MCP scanning is a first step, but it's advisory-catalog-based (known bad packages/extensions), not behavioral (detecting a new MCP server that exfiltrates data). The gap between "scan for known bad" and "detect novel malicious behavior" in MCP configs is wide and currently unaddressed.
*Grounded in: perplexityai/bumblebee MCP scanning capability (this digest); MCP ecosystem growth patterns (background context)*
