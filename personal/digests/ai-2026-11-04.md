## 🏆 Repo of the Day

### max-sixty/worktrunk — ergonomic Git worktree management for parallel AI agent workflows
**Link:** github.com/max-sixty/worktrunk | **Stars:** ~10.9k (↑ 749 this week) | **Language:** Rust | **License:** MIT OR Apache-2.0
**The problem:** Running N Claude Code or Codex instances in parallel requires N git worktrees — but the native git worktree UX forces you to type the branch name three times per worktree and manage paths by hand.
**Why it's today's pick:** Claude Code v2.1.318 ships improved background subagent handling and AWS per-developer cost attribution — meaning parallel multi-agent workflows are becoming a production concern, not just a local experiment. worktrunk is the matching git layer: it addresses worktrees by branch name, computes paths from a configurable template, and ships a one-liner to create a worktree and spawn an AI agent in it. It released at the start of 2026 and climbed to 10.9k stars with sustained weekly growth (+749 this week) — real momentum, not a spike.
**Try it in 60 seconds:**
```bash
# Install (Homebrew)
brew install worktrunk && wt config shell install

# Or via Cargo
cargo install worktrunk && wt config shell install

# Create a worktree and spawn Claude Code in it
wt switch -x claude -c feature-auth -- 'Add user authentication'

# List all worktrees with status
wt list

# Merge (squash + rebase + merge + cleanup)
wt merge main
```
**Instead of:** `git worktree add ../feature-auth -b feature-auth && cd ../feature-auth && claude` — plus managing all those paths manually across a fleet of agent sessions.
**Watch out for:** The shell integration step (`wt config shell install`) is required for directory-switching to work. Without it, `wt switch` can't change your terminal's directory. One third-party skill audit flagged a "CRITICAL" security concern in the accompanying agent skill listing — use the CLI directly and not third-party skill wrappers until that is resolved.

### [NOTABLE] E2B v2.63.0 — Strict pause semantics for unresponsive sandboxes
**Source:** GitHub | **Date:** 2026-11-04 | **Link:** https://github.com/e2b-dev/E2B/releases
**What changed:** `pause()` gains a `strict` option (default `false`). With `strict=True`, pausing is refused with `ServiceBusyError` while the guest agent (`envd`) is unresponsive — the sandbox keeps running rather than taking a potentially corrupted snapshot. With `strict=False` (default), the snapshot is taken but marked `envd_unresponsive_at_pause`. Resuming a marked sandbox without `on_resume="reboot"` now raises `GuestUnresponsiveError`.
**TL;DR:** E2B v2.63.0 (Nov 4) adds explicit error types for the case where a sandbox's guest agent is unresponsive at pause time — previously a silent failure path that could produce corrupted or unresumable snapshots.
**Developer signal:** If you pause sandboxes and resume them later (a common pattern for long-running agentic tasks), you should now handle `GuestUnresponsiveError` on resume — it means the sandbox was paused while `envd` was unresponsive. Pass `on_resume="reboot"` to force a clean restart, or handle the error and provision a fresh sandbox. For high-reliability workloads, consider using `strict=True` on pause — the sandbox stays running if `envd` is unresponsive, so you don't create a corrupt snapshot. Update your sandbox exception handling in both the JS SDK (`e2b@2.63.0`) and Python SDK (`@e2b/python-sdk@2.63.0`).
**Affects you if:** You pause and resume E2B sandboxes in long-running agent workflows; you use E2B in production where sandbox reliability matters.
**Adoption effort:** Quick (handle `GuestUnresponsiveError` and `ServiceBusyError` in exception handlers; optionally set `strict=True` for high-reliability pause semantics)
**Primary source:** https://github.com/e2b-dev/E2B/releases
