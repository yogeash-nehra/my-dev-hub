## 🏆 Repo of the Day

Today's Anthropic API breaking change (removing `temperature`/`top_p`/`top_k`, changing the `Authorization` header scheme) is exactly the kind of API-level change that takes down integrations when discovered at runtime rather than during testing. A good API client — one that's git-friendly, runs offline, and shows you exactly what you're sending — is the fastest way to verify your migration before deploying. Reaching into the watchlist for a pick that earns its spotlight today.

### usebruno/bruno — git-friendly, offline-first API client that replaces Postman for team workflows
**Link:** github.com/usebruno/bruno | **Stars:** ~28k (↑ steady growth, no single-spike pattern) | **Language:** JavaScript/TypeScript | **License:** MIT
**The problem:** Postman stores your collections in the cloud, syncs state across devices in ways your team doesn't control, and requires an account login — making it awkward to commit API tests alongside code or run them reproducibly in CI.
**Why it's today's pick:** The Anthropic API `2026-10-21` migration requires you to remove `temperature`/`top_p`/`top_k` from requests and potentially update your `Authorization` header format. Bruno stores every request as a `.bru` file in your repo — you can write a `/v1/messages` collection with the new API version header, commit it, and every team member (and CI) tests the migration from the same source of truth. It also runs fully offline and doesn't require an account. With major API breaking changes like today's, having a reproducible, version-controlled test suite matters more than usual.
**Try it in 60 seconds:**
```bash
# Install (macOS)
brew install bruno

# Install (Linux / Windows)
# Download from https://www.usebruno.com/downloads

# Create a new collection and test the new API version
# File: claude-api-migration/messages.bru
# post https://api.anthropic.com/v1/messages
# headers {
#   anthropic-version: 2026-10-21
#   content-type: application/json
# }
```
**Instead of:** Postman (cloud-synced, account-required, hard to diff in git) or raw `curl` one-liners that get lost in shell history after a session.
**Watch out for:** Bruno is under active development — some advanced Postman features (scripting, monitors, mock servers) are still being built. For straightforward REST/HTTP request collections, it's production-ready and fast.

## [BREAKING] Breaking Changes

### [BREAKING] Anthropic API 2026-10-21 — temperature/top_p/top_k removed from all requests; SDK major versions; MIT→Apache 2.0
**Source:** Anthropic Platform Release Notes | **Date:** 2026-10-21 | **Link:** https://platform.claude.com/docs/en/api/migration-2026-10-21
**What changed:** API version `2026-10-21` removes three long-standing sampling parameters (`temperature`, `top_p`, `top_k`) — requests that include any of these now return 400 errors, even when set to the default value. New SDK major versions that default to `2026-10-21` shipped the same day: Python 2.0.0, TypeScript 1.0.0, C# 13.0.0, Go 2.0.0, Java 3.0.0, PHP 1.0.0, Ruby 2.0.0, `ant` CLI 2.0.0. All new major versions are **Apache 2.0** (previously MIT). The `MessageParam` type in Python and TypeScript is now a union of role-specific types — calling `MessageParam()` directly now raises a `TypeError`. Two additional API-level breaks: `document` blocks in assistant messages and `citations` arrays in user-message text blocks now return 400 errors. Admin API field renames: `roles`→`role_ids`, `group_id`→`rbac_group_id`, `name`→`display_name`, `group_type`→`group.type`, `workspace_id`→`scope`. Analytics API renames: `actor.email`→`actor.email_address`, `summaries`→`data`. On Amazon Bedrock, `2026-10-21` is available only for Claude 4.7+ models — older Bedrock callers must stay pinned to their current SDK version.
**TL;DR:** The largest breaking change to the Claude API since 2023: `temperature`, `top_p`, and `top_k` are removed across all models, all SDK major versions jumped, and the license moved to Apache 2.0 — this slipped prior scan cycles and shipped October 21.
**Developer signal:** **If you have NOT upgraded your SDK:** Pin to your current SDK version before upgrading and read the [full migration guide](https://platform.claude.com/docs/en/api/migration-2026-10-21) before moving. **If you already upgraded:** Check every place you pass `temperature`, `top_p`, or `top_k` — remove them. Without those parameters, the API samples with `temperature=1.0` (the default); for models that previously accepted lower values (e.g., Claude Sonnet 4.6 with `temperature=0`), you now have no replacement for deterministic-style outputs — the migration guide explicitly says "No other setting replaces it; if a request relies on a non-default value, keep that request on `2023-06-01`." Separately: update `MessageParam` constructor calls to dict literals (`{"role": "user", "content": "..."}` instead of `MessageParam(role="user", ...)`). For TypeScript: the `@anthropic-ai/bedrock-sdk`, `@anthropic-ai/vertex-sdk`, `@anthropic-ai/foundry-sdk` packages each need their own v1 upgrade to match — mixing old and new versions installs a second SDK copy. Go users: update import paths to include `/v2` (`github.com/anthropics/anthropic-sdk-go/v2`). License change to Apache 2.0 may require legal review in some enterprise / open-source projects.
**Affects you if:** You call the Anthropic Messages API with `temperature`, `top_p`, or `top_k`; you upgraded to Python SDK 2.0.0 or TypeScript SDK 1.0.0; you use `MessageParam()` as a constructor; you call the Admin API or Analytics API and read the renamed fields; you use Bedrock with pre-4.7 Claude models.
**Adoption effort:** Significant (audit all API call sites for removed parameters; migrate MessageParam usage; review license implications; test against 2026-10-21 before deploying).
**Primary source:** https://platform.claude.com/docs/en/api/migration-2026-10-21

## API & SDK Changes

### [MEDIUM] Claude API now available via Google Cloud (Anthropic-managed)
**Source:** Anthropic Platform Release Notes | **Date:** 2026-10-22 | **Link:** https://platform.claude.com/docs/en/release-notes/overview
**What changed:** Anthropic launched direct Google Cloud delivery of the Claude API: Claude is now served through GCP infrastructure, billed through Google Cloud Marketplace, and access-controlled by Google Cloud IAM — without going through the Anthropic console. Previously, GCP access required the Vertex AI SDK with Google's own auth stack; this is a separate Anthropic-managed path using the same API interface but IAM + Marketplace billing.
**TL;DR:** Claude API is now available natively on Google Cloud with IAM auth and Cloud Marketplace billing — a separate track from Vertex AI, operated by Anthropic.
**Developer signal:** If your infrastructure already runs on GCP and you want to use the Claude API with IAM-controlled access (service accounts, Workload Identity Federation) rather than Anthropic console API keys, this gives you that path without adopting the Vertex AI SDK. Billing goes through Google Cloud Marketplace, which means you can consolidate AI spend under your existing GCP committed use discounts and budget alerts. The TypeScript SDK `@anthropic-ai/google-cloud-sdk` supports this (update to v1 alongside the main SDK). This is distinct from Vertex AI access — it's Anthropic-managed, meaning the model versions and rollout are controlled by Anthropic, not Google's model garden schedule.
**Affects you if:** You run workloads on GCP and want IAM-controlled Claude API access; you want to consolidate Claude API billing under Google Cloud Marketplace; you build multi-cloud apps where GCP is the primary cloud.
**Adoption effort:** Moderate (set up GCP project + IAM; update to `@anthropic-ai/google-cloud-sdk@1.x` or Python SDK 2.0.0 with Google Cloud auth).
**Primary source:** https://platform.claude.com/docs/en/release-notes/overview

### [NOTABLE] E2B v2.60.0 + v2.61.0 — retry logic with Should-Retry headers, CVE fix, sandbox idempotency keys
**Source:** GitHub Releases | **Date:** 2026-10-26 | **Link:** https://github.com/e2b-dev/E2B/releases
**What changed:** Two releases shipped today. v2.60.0: Control-plane API errors now retry when the response includes `Should-Retry: true` or returns 429/502/503/504 without that header; `Should-Retry: false` is always final. Post-send network errors no longer retry, but connection failures still do. A high-severity CVE fix: bumped `undici` to ^8.12.2 to address CVE-2026-109869 (GHSA-xjj6-f33q-929c), a DoS vulnerability in the HTTP/1.1 client. v2.61.0: `Sandbox.create` now accepts an optional idempotency key (`idempotencyKey` / `idempotency_key`), sent as an `Idempotency-Key` header — useful for retrying sandbox creation without creating duplicate sandboxes on network failures.
**TL;DR:** E2B sandboxes now handle transient API failures with server-directed retry logic, fix a high-severity HTTP client CVE, and support idempotent sandbox creation.
**Developer signal:** **CVE fix (high priority):** Update to E2B v2.60.0+ to patch the `undici` CVE — if you run E2B in a network-accessible environment, this is worth a same-day upgrade. **Idempotency key:** If your agent creates sandboxes in a retry loop (e.g., when a network call to `Sandbox.create` times out before you get a response), add an idempotency key to avoid spinning up duplicate sandboxes: `await Sandbox.create({ idempotencyKey: "my-task-id" })`. Re-sending the same key within the idempotency window returns the existing sandbox rather than creating a new one. **Retry behavior:** The new server-directed retry model means `429` responses from E2B will now back off and retry automatically — if you built manual retry loops around E2B, check whether they still behave as expected with the new automatic retries in place.
**Affects you if:** You create E2B sandboxes at scale or in retry-prone network conditions; you run E2B JavaScript SDK in any network-accessible context (CVE).
**Adoption effort:** Quick (update package version; optionally add idempotency keys to sandbox creation calls).
**Primary source:** https://github.com/e2b-dev/E2B/releases

**[PATTERN] Anthropic's API surface is converging toward model-as-pure-function: no sampling parameters, no mutable defaults**

The removal of `temperature`, `top_p`, and `top_k` in API version `2026-10-21` completes a trajectory that started with Claude 4.7 (those models already accepted only the defaults). The direction is clear: Anthropic is moving the API toward a model that takes input and returns output, with no caller-side sampling knobs. The reasoning offered in the migration guide is minimal ("no other setting replaces it"), which suggests the intent is architectural, not a temporary constraint. This pattern is consistent with how they've handled extended thinking (you enable it or disable it; you don't tune the sampling temperature of the thinking process). If this continues, the Claude API is becoming more opinionated about *how* models generate — and less configurable by API callers.
*Grounded in: Anthropic API 2026-10-21 migration guide (Oct 21, 2026); platform release notes noting Claude 4.7+ models already didn't accept non-default sampling values*

**[TENSION] The Apache 2.0 license change arrives just as Anthropic files its S-1**

The SDK and CLI license changed from MIT to Apache 2.0 in the major version release on October 21. Five days later, Anthropic filed an S-1. Apache 2.0 is more permissive in some ways (explicit patent grant) but also more explicit about attribution requirements and the boundaries of derivative works. For enterprise legal teams reviewing Claude API adoption, this timing matters: the company that owns the SDK just entered a public IPO process with a license change in hand. Apache 2.0 is widely accepted in enterprise environments (Kubernetes, TensorFlow, Spark are all Apache 2.0), so this is unlikely to block adoption — but the combination of IPO + license change in the same week is the kind of thing enterprise procurement asks about.
*Grounded in: Anthropic Platform Release Notes Oct 21 (MIT→Apache 2.0 for all SDKs and CLI); Anthropic S-1 filing Oct 26 (anthropic.com/news)*

**[OPEN QUESTION] If temperature is gone from the API, where does stochasticity control move?**

Claude API version `2026-10-21` removes `temperature`, `top_p`, and `top_k` with no replacement. The migration guide explicitly says there is no substitute for callers who needed non-default values for models like Sonnet 4.6 — they should stay on `2023-06-01`. This works in the short term (old API version remains supported), but raises a design question: for use cases that genuinely need lower temperature (deterministic extraction, constrained output, automated test generation), what does the next chapter look like? The trajectory of adaptive thinking (you set an effort level, not a budget) and structured output (you supply a JSON schema) suggests Anthropic may be moving toward capability-level controls rather than parameter-level controls. But the migration guide doesn't say this — it just says the parameters are gone.
*Grounded in: Anthropic API 2026-10-21 migration guide, section "Sampling parameters are removed"*
