## API & SDK Changes

### [MEDIUM] Anthropic SDK — `speed` parameter lands in Messages API; fast mode is now a first-class SDK citizen across 8 languages
**Source:** anthropics/anthropic-sdk-python GitHub Releases | **Date:** October 15, 2026 | **Link:** https://github.com/anthropics/anthropic-sdk-python/releases/tag/v1.15.0

**What changed:** Previously, fast mode required manually setting the `fast-mode-2026-02-01` beta header in HTTP requests — there was no SDK-level parameter. As of Python SDK v1.15.0 and TypeScript SDK v0.135.0 (both Oct 15), `speed="fast"` is a first-class top-level parameter on `messages.create()`, and the response's `usage` object now includes a `speed` field (`"fast"` or `"standard"`) that lets you verify which tier actually ran.

**TL;DR:** Anthropic SDK (Python v1.15.0, TypeScript v0.135.0) — Oct 15 — adds `speed="fast"` to Messages API across 8 SDK languages; Opus 5.5 needs no beta header, Opus 5 and 4.8 still do; pricing is 2x standard ($8/$40 per MTok for Opus 5.5); prompt cache is not shared between fast and standard speed requests.

**Developer signal:** For Claude Opus 5.5 (now GA in fast mode), just add `speed="fast"` to your `messages.create()` call — no beta header needed:
```python
response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=4096,
    speed="fast",
    messages=[{"role": "user", "content": "..."}],
)
print(response.usage.speed)  # "fast" or "standard"
```
For Claude Opus 5 and Opus 4.8, still send `anthropic-beta: fast-mode-2026-02-01` alongside the `speed` parameter. **Critical cache gotcha:** fast and standard speed requests do NOT share prompt cache prefixes — if you have a large cached system prompt and switch between `speed: "fast"` and standard (e.g., in a fallback), you'll take a cache miss. Design your fallback pattern with this in mind. Rate limits for fast mode are separate from standard Opus rate limits and have their own set of response headers (`anthropic-fast-input-tokens-limit`, etc.). Fast mode is NOT available on the Batch API, Priority Tier, or Claude Platform on AWS.

**Affects you if:** You use Claude Opus 5.5, Opus 5, or Opus 4.8 and want to reduce output latency; you build latency-sensitive agent steps; you have existing fast mode code using the beta header that you want to modernize.

**Adoption effort:** Quick (add `speed="fast"` to existing calls; header approach still works). Moderate if you also update fallback logic for cache-miss considerations.

**Primary source:** https://github.com/anthropics/anthropic-sdk-python/releases/tag/v1.15.0 | TypeScript: https://github.com/anthropics/anthropic-sdk-typescript/releases/tag/sdk-v0.135.0 | Docs: https://platform.claude.com/docs/en/build-with-claude/fast-mode

### [NOTABLE] Anthropic SDK — OTel tracing now auto-activates on SDK upgrade if a global tracer provider is registered (behavior change)
**Source:** anthropics/anthropic-sdk-python GitHub Releases | **Date:** October 15, 2026 | **Link:** https://github.com/anthropics/anthropic-sdk-python/releases/tag/v1.14.0

**What changed:** Python SDK v1.14.0 and TypeScript SDK v0.134.0 (Oct 15, 09:48 UTC) add native OpenTelemetry tracing. This is a **behavior change**: if your application already registers a global OTel tracer provider, upgrading the SDK immediately causes `anthropic.messages.create` spans to be emitted and forwarded to your observability backend — no configuration required. The opt-out is explicit.

**TL;DR:** Upgrading to anthropic-sdk-python v1.14.0+ or @anthropic-ai/sdk v0.134.0+ automatically emits OTel spans if you have a global tracer provider; opt out with `Anthropic(open_telemetry=False)` or `ANTHROPIC_OPEN_TELEMETRY=false`; supported in Claude API, Bedrock, Vertex, Google Cloud, Foundry, and AWS SDKs.

**Developer signal:** Before upgrading in any environment that already uses OpenTelemetry, audit whether you want Claude spans going to your current OTel backend. If not, pin the opt-out immediately:
```python
# Python — opt out
client = Anthropic(open_telemetry=False)

# TypeScript — opt out
const client = new Anthropic({ openTelemetry: false });
```
If you DO want traces, the default content mode is `metadata_only` (no prompts or responses in spans) — to include content, set `traces.content_mode = "content"`. The same SDK update also adds `execution_identity` to Managed Agents and telemetry destination management to the Admin API. This SDK change covers all cloud variants: Bedrock, Vertex, Google Cloud, Foundry, and AWS SDKs all received the same OTel update in the same batch.

**Affects you if:** You use the Anthropic Python or TypeScript SDK (or any cloud SDK variant) in a production service that already registers a global OTel tracer provider; you upgrade dependencies automatically (Dependabot, Renovate) without reviewing behavior changes.

**Adoption effort:** Quick (add `open_telemetry=False` if you don't want spans; review your OTel pipeline if you do).

**Primary source:** https://github.com/anthropics/anthropic-sdk-python/releases/tag/v1.14.0 | TypeScript: https://github.com/anthropics/anthropic-sdk-typescript/releases/tag/sdk-v0.134.0 | SDK docs: https://platform.claude.com/docs/en/manage-claude/opentelemetry/sdk

### SDK capability discovery is replacing hardcoded feature flags in agent code
**Source:** anthropics/anthropic-sdk-python, anthropic-sdk-typescript | **Date:** October 15, 2026 | **Link:** https://github.com/anthropics/anthropic-sdk-python/releases/tag/v1.15.0

**What's happening:** The Oct 15 SDK releases added `between_tools` to thinking types in model capabilities — a formal declaration that a model supports interleaved thinking (reasoning between individual tool calls, not just at the start). This is part of a broader pattern: the SDK now exposes model capabilities as queryable properties rather than requiring developers to maintain external capability matrices. The `speed` parameter addition is the same pattern applied to fast mode. Neither requires the developer to know model-specific rules ahead of time.

**Why watch this:** As Anthropic's model lineup grows (Opus 5.5, Opus 5, Opus 4.8, Sonnet 5.5, Haiku 5.5, and counting), maintaining hardcoded capability maps in agent code becomes fragile. A model that returns its own capability declarations — "I support `between_tools` thinking," "I can run at `fast` speed" — lets agents adapt their behavior at runtime without code changes when new models ship. This could significantly reduce "which model supports what" maintenance burden in agent frameworks.

**[OPEN QUESTION] Will `ApprovalReviewer` in pydantic-ai v2.57.0 become the standard pattern for tiered human-in-the-loop, or is it too model-dependent to generalize?**
pydantic-ai's new `ApprovalReviewer` harness uses a model to pre-screen tool calls before a human reviewer sees them, routing only high-risk or uncertain calls to a person. The core assumption is that a reviewer model can reliably classify "low-risk" tool calls well enough to skip human review without accumulating risk. That assumption is unverified for production deployments — it depends on the quality of the reviewer model's judgment, which varies by tool type. For file reads or API lookups, an automated reviewer probably does well. For git pushes, payments, or email sends, the failure mode of a wrong "safe" classification is severe. The open question: will this pattern catch on as a standard HiTL tier, or will teams find the reviewer model's error rate unacceptable for anything beyond low-stakes tools?

**[TENSION] Fast mode pricing and cache-invalidation combine in a way that could surprise teams migrating to `speed: "fast"`**
Fast mode for Opus 5.5 is 2x standard pricing ($8/$40 per MTok vs $4/$20). That multiplier is widely understood. The less-obvious gotcha is that fast and standard speed requests do not share prompt cache prefixes — switching from standard to `speed: "fast"` on a call with a large cached system prompt (common in agent pipelines) takes a cache miss, adding the full cost of re-reading that prefix at fast-mode rates. For a 100k-token system prompt, that cache miss at Opus 5.5 fast mode costs $0.80 per occurrence. Teams that design a "fast for output, standard for setup" pattern — caching the system prompt under standard speed and running inference steps at fast speed — will pay more than expected if they haven't accounted for this. The docs mention it in a warning, but it's not prominently surfaced.
