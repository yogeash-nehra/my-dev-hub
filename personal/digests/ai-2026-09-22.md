## 🏆 Repo of the Day

### google/ax — Kubernetes-native declarative runtime for autonomous agent workloads

**Link:** github.com/google/ax | **Stars:** ~7.4k (↑ +2,324 today) | **Language:** Go | **License:** Apache 2.0

**The problem:** Running agents as long-lived Kubernetes workloads requires solving isolation, workspace pre-wiring (git repos, MCP servers, packages), outbound network fencing, and cost-bounding — none of which the standard Kubernetes primitives handle out of the box.

**Why it's today's pick:** Google released AX at its Google I/O developer stream on September 18, and it's now trending #2 overall with +2,324 stars today — the discovery curve is still climbing. AX introduces four small declarative primitives (Task, Workspace, Gateway, Model) that map directly to the four problems agents introduce as workloads: execution isolation, pre-configured environment, network access control, and LLM provider credentials. It runs on top of Agent Substrate (agent-substrate/substrate, also trending today at #7), which handles the actual sandboxing. The combination is the first credible answer to "how do I run agents the same way I run containers" — suspend/resume, SSH debug access, kubectl-style CLI, and resource limits all included. Previous digests have covered Claude Code (Anthropic), Codex (OpenAI), Gemini CLI (Google), and OpenHands for the *coding agent* layer; AX addresses the *infra* layer those agents run on.

**Try it in 60 seconds:**
```bash
go install github.com/google/ax/cmd/ax@latest

# Define a task declaratively
cat > task.yaml << 'EOF'
apiVersion: ax.google.com/v1
kind: Task
metadata:
  name: my-agent-task
spec:
  model:
    provider: anthropic
    name: claude-opus-5-5
  workspace:
    repos:
      - url: https://github.com/myorg/myrepo
        branch: main
  gateway:
    allowlist:
      - api.anthropic.com
      - github.com
EOF

ax apply -f task.yaml
ax watch my-agent-task
```

**Instead of:** Manually managing Docker containers, writing custom Kubernetes operators for agent isolation, and hand-rolling network policy CRDs every time you need to fence an agent's outbound traffic.

**Watch out for:** Marked as explicitly early-stage with expected breaking changes before stable release. Requires an existing Kubernetes cluster and the Agent Substrate control plane installed — not a standalone tool. Suspend/resume relies on Substrate's checkpoint mechanism, which is also pre-stable. Stars spiked at I/O launch (Sep 18) but today's +2,324 suggests the curve is sustained, not already flattened.

## [BREAKING] Breaking Changes

### [BREAKING] Claude Opus 5.5 — three API changes required when migrating from Opus 5 or earlier models
**Source:** Anthropic Platform Release Notes | **Date:** September 22, 2026 | **Link:** https://platform.claude.com/docs/en/release-notes/overview

**What changed:** Claude Opus 5.5 introduces three behavioral changes that return HTTP 400 errors for request patterns that previously worked on Opus 5 and earlier models. These apply only when using `claude-opus-5-5`; existing code targeting other Claude models is unaffected.

**TL;DR:** Disabling thinking, non-`auto` tool_choice modes, and the legacy `computer_20251124` tool all return 400 errors on Opus 5.5 — three separate code paths to audit before migrating.

**Developer signal:** (1) **Thinking cannot be disabled.** `thinking: {"type": "disabled"}` returns a 400 error. Opus 5.5 uses always-on adaptive thinking; use the `effort` parameter to control depth instead. If you previously passed `thinking: disabled` to reduce cost or latency, remove that parameter and tune `effort` to the appropriate level. (2) **`tool_choice` types `any` and `tool` return 400.** Pass `tool_choice: {"type": "auto"}` with strict tool-use settings instead. The `auto` type with a strict schema enforces the same behavior — check your tool call construction if you relied on `any` for guaranteed tool invocation. (3) **`computer_20251124` tool returns 400 on Claude API and Google Cloud.** Migrate to the `computer_toolset_20260801` toolset. **Exception:** `computer_20251124` continues working on Amazon Bedrock — do not remove it from Bedrock-targeted code until AWS publishes a separate deprecation notice. Audit all three changes before switching a pipeline to `claude-opus-5-5`.

**Affects you if:** You call the Claude API or Google Cloud AI with any of: `thinking: {"type": "disabled"}`; `tool_choice: {"type": "any"}` or `{"type": "tool"}`; the `computer_20251124` tool type.

**Adoption effort:** Moderate — three distinct parameter changes; straightforward but requires systematic audit of every request construction path in your codebase.

**Primary source:** https://platform.claude.com/docs/en/release-notes/overview

**Affects you if:** You use `anthropic` Python ≥ any version below v1.8.0 or TypeScript SDK below v0.128.0; you run multi-turn agent sessions where tool availability changes; you use Python 3.13 with streaming.

**Adoption effort:** Quick — `pip install "anthropic>=1.8.0"` or `npm install @anthropic-ai/sdk@^0.128.0`; inline tools require beta header and request structure changes.

## Research

### [HIGH] Devin factors RSA-260 — agent builds GPU GNFS siever in 9 hours; 1,024-bit RSA now estimable at ~$30M
**Source:** Cognition (Eric Lu) | **Date:** September 2026 | **Link:** https://cognition.com/blog/factoring-rsa-260

**What changed:** Cognition engineer Eric Lu directed Devin to build a GPU-accelerated lattice siever for CADO-NFS (the open-source General Number Field Sieve implementation), then used it to factor RSA-260 — a 260-digit, 862-bit number from the RSA Factoring Challenge that had stood since February 2020, making it the largest number ever publicly factored from that challenge.

**TL;DR:** Devin produced a working GPU siever (named glas) that beat the CPU baseline in ~9 hours from a single prompt on August 13, 2026; total computation was ~4,900 GPU-days; Eric Lu estimates a hyperscaler could factor 1,024-bit RSA for ~$30M at current market GPU prices.

**Developer signal:** (1) **1,024-bit RSA is now in-scope for well-funded actors.** The $30M estimate is for current market GPU pricing with the optimizations Devin built; with further optimization or bulk GPU pricing, the effective cost is likely lower. If any service you build or maintain uses 1,024-bit RSA keys for anything longer-lived than a session (TLS certs, signing keys, stored secrets), plan a migration to 2,048-bit RSA or an ECC equivalent. (2) **RSA-2048 is not affected.** The GNFS algorithm's sub-exponential complexity still makes 2,048-bit RSA infeasible at any current-generation GPU scale. (3) **The developer angle is the agent story, not the math.** Devin was given a single GPU and a prompt ("build me a drop-in GPU replacement for the CPU lattice siever in CADO-NFS") and produced a working implementation 9 hours later that beat the CPU baseline. Lu then directed optimization over the following week. This is the most significant public demonstration of an agent solving an open research problem from a standing start rather than executing a pre-specified implementation. (4) **The GNFS pipeline Devin built is open.** CADO-NFS is MIT-licensed and the GPU siever (glas) will be contributed upstream per Lu's post — developers interested in applied cryptography or GPU numerical methods can examine the agent-generated code directly.

**Affects you if:** You maintain any system using 1,024-bit RSA keys; you build cryptographic tooling; you're evaluating what long-horizon agentic coding can accomplish on novel technical problems.

**Adoption effort:** Quick (key migration) — update key length in key generation tooling; Significant if you manage long-lived signed data (certificates, tokens, stored secrets with HSM-backed keys).

**Primary source:** https://cognition.com/blog/factoring-rsa-260 | https://postquantum.com/security-pqc/sa-260-factored-gpu-devin/

## Trends & Emerging Tech

### Jev / System One Models — TypeSafe AI ships a new category: structured decision models that are not text generators
**Source:** TypeSafe AI (typesafe.ai) | **Date:** September 21, 2026 | **Link:** https://typesafe.ai/blog/introducing-system-one-models-and-jev

**What's happening:** TypeSafe AI announced "System One models" with Jev, their first public release. Unlike an LLM, Jev doesn't generate text — it evaluates a state object (string, array, or name-value pairs) and returns typed answers to structured questions (Choice, Score, or Boolean types). Outputs are constrained to defined schemas, so hallucinated values or invalid types are mathematically impossible. On a 4-workflow classification/routing benchmark it hits ~68% accuracy, comparable to mid-tier LLMs, but at $0.042/M input tokens (cheaper than GPT-5 Nano at $0.05/M) and 40–400x less cost per decision than a standard LLM call. Simon Willison posted analysis on September 21. pydantic-ai v2.47.0 (released the same day) ships first-class TypeSafeModel integration.

**Why watch this:** The "decision model" category targets the large class of agent tasks that are actually routing, classification, scoring, or filtering decisions — not text generation. If your agent does things like "classify this support ticket into 5 categories" or "score this document chunk for relevance (1–5)", replacing an LLM call with Jev cuts cost by 100–400x with no accuracy regression. The pydantic-ai integration means you can drop it into a pydantic-ai agent today without writing a custom provider. The deeper architectural question: if decision-heavy workflows move to specialized decision models and text-generation stays with LLMs, multi-model agent pipelines become the norm rather than the exception.
