## 🏆 Repo of the Day

### akitaonrails/ai-memory — cross-vendor long-term memory for AI coding agents
**Link:** github.com/akitaonrails/ai-memory | **Stars:** ~11,211 (↑ 666 today) | **Language:** Rust | **License:** MIT

**The problem:** When you switch between AI coding agents (Claude Code, Codex, Gemini CLI) or hand a task to a teammate, the agent's built-in memory stays behind — you lose context on what was tried, what failed, and what the architecture decisions were.

**Why it's today's pick:** ai-memory solves the cross-agent handoff problem that becomes unavoidable the moment you use more than one coding tool. The 666-star gain today reflects genuine developer awareness: v3.1.1 shipped just two days ago (Oct 17), and the project now supports 20+ agent harnesses with first-party plugins for Claude Code and Codex. The storage model is clever — a git-backed markdown wiki as the source of truth, with a rebuildable SQLite index, so memory is version-controlled and diff-able. You can edit it directly, which matters when an agent writes something wrong. At 4,105 commits and a v3.x line, this is past the vaporware stage.

**Try it in 60 seconds:**
```bash
# Linux/macOS — checksum-verified install:
curl -sSL https://raw.githubusercontent.com/akitaonrails/ai-memory/main/install.sh | bash
ai-memory setup          # auto-detects installed agents and wires hooks

# Claude Code plugin install (if you prefer the plugin route):
claude plugin install ai-memory

# Start a coding session with shared memory:
ai-memory run claude     # launches Claude Code with memory context loaded
# When switching to Codex mid-task:
ai-memory run codex      # picks up where Claude left off
```
**Instead of:** Re-explaining your project architecture, failed approaches, and open questions every time you switch tools or start a new session — or keeping a manual `CONTEXT.md` that never stays current.

**Watch out for:** Native Windows support is marked "Experimental." The LLM-driven "dream consolidation" pass (background memory cleanup) and some aging features are off by default until they pass Anthropic's evaluation threshold. Team/shared-server mode requires self-hosting. Star-history.com was DNS-blocked this scan, so the momentum curve couldn't be validated directly — the 666-star day is confirmed from GitHub Trending, but whether it's a sustained climb or a spike needs re-checking in 48h.

### [MEDIUM] OpenHands v1.28.0 — in-conversation secret injection, Azure DevOps all-org listing, Mars bridge default
**Source:** GitHub Releases | **Date:** 2026-10-19 | **Link:** https://github.com/OpenHands/OpenHands/releases/tag/v1.28.0
**What changed:** Agents can now request secrets via an inline chat modal (not just a separate settings page). Azure DevOps integration now lists repos from all organizations, not just the first one. Mars web bridge is mounted by default (`MARS_WEB=1` opt-in removed). Word-by-word fade-in streaming added.
**TL;DR:** OpenHands 1.28 ships four developer-facing improvements: mid-task secret requests, Azure DevOps full org listing, default Mars bridge, and smoother chat streaming.
**Developer signal:** The in-conversation secret modal is the most impactful change for production use. Previously, if an agent hit a credential it needed (an API key, a database password), the workflow would break — the user had to go to settings, add it, and restart. Now the agent surfaces a secure inline modal in the chat thread, the user enters the value once, and the run continues without interruption. If you're running OpenHands for multi-step agentic tasks that touch external services, this removes one of the most common workflow interruptions. The Azure DevOps fix is worth calling out separately: if your organization has multiple Azure DevOps orgs, OpenHands was silently missing repos from orgs other than the first one — update to get full repo visibility. For self-hosted deployments: `MARS_WEB=1` is now the default and the env var is removed; if you had any Compose configs or deployment scripts that explicitly set `MARS_WEB=1` to enable the bridge, that setting is now a no-op and can be cleaned up. If you deliberately had the bridge *off* (by not setting the flag), note that it is now on by default.
**Affects you if:** You run OpenHands for multi-step agentic tasks that need credentials; you use OpenHands with Azure DevOps multi-org setups; you self-host OpenHands and manage environment variable configs.
**Adoption effort:** Quick (upgrade the package; MARS_WEB cleanup is optional housekeeping).
**Primary source:** https://github.com/OpenHands/OpenHands/releases/tag/v1.28.0

## Trends & Emerging Tech

### Agentic secret management is becoming a first-class UX problem
**Source:** OpenHands v1.28.0 release notes | **Date:** 2026-10-19 | **Link:** https://github.com/OpenHands/OpenHands/releases/tag/v1.28.0
**What's happening:** OpenHands shipping an inline secret-request modal in v1.28.0 is a signal, not just a feature: as agentic tasks grow longer and touch more external services, the "where does this agent get credentials it needs mid-task" problem is becoming unavoidable. The current industry pattern is either pre-injecting everything into the environment (fragile, over-permissive) or breaking the workflow when something's missing (bad UX). OpenHands' approach — agent surfaces a request inline, user enters it once, task continues — mirrors what BeeAI and a handful of other frameworks have been building separately. The pieces are converging toward a de facto pattern.
**Why watch this:** In the next few months, watch for this pattern to appear in Claude Code, Cursor, and Codex as coding agents take on longer-running tasks that need API keys and auth tokens they didn't start with. The open question is whether a standard protocol for agent credential requests (analogous to OAuth's authorization flow) emerges, or whether every agent harness invents its own UX. An MCP server that wraps secrets management (1Password, Vault, AWS Secrets Manager) would be a natural complement — nobody has shipped this cleanly yet.

**[OPEN QUESTION] Whose responsibility is agent memory — the harness, the model, or an external service?**
`akitaonrails/ai-memory` takes the position that memory is an external, git-backed service that all harnesses plug into. Anthropic's position (via in-context memory and claude.ai Projects) is that memory lives in the model's context window and is managed by the product. OpenAI's Codex and ChatGPT take yet another approach: memories are model-managed, user-visible, and stored per-account. These are three different answers to the same question, and they're not compatible: a cross-vendor handoff requires the external-service approach, but that introduces trust, auth, and correctness problems (the agent wrote something wrong, now it persists across tools). The right answer is probably different depending on task horizon (single session vs. weeks-long project vs. institutional knowledge) — but the ecosystem hasn't settled.
*Grounded in: akitaonrails/ai-memory architecture (git-backed markdown wiki, 20+ agent integrations) in this digest*

**[BUILDER'S ANGLE] If agent secret-request becomes a standard protocol, it unlocks authenticated multi-agent pipelines**
OpenHands' inline secret request today is a harness-specific UX pattern. But the underlying mechanism — agent signals "I need credential X for service Y" → user provides it once → task continues with that credential scoped appropriately — is generalizable to a multi-agent scenario. An orchestrator could intercept such requests, route them to a secrets manager (1Password, AWS Secrets Manager, HashiCorp Vault), fulfill them transparently, and return the result to the worker agent — without any human in the loop, and without pre-injecting all credentials into every agent's environment. No one has shipped this as an MCP server or agent middleware yet. The building blocks are: OpenHands' request pattern, an MCP secrets server wrapping a vault, and an orchestrator that routes the credential flow. This is a concrete gap in the current agent toolchain.
