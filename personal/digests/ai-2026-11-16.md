### [MEDIUM] Anthropic text watermark extended to Opus 4.6, Opus 4.5, Sonnet 4.5, and Haiku 4.5
**Source:** Anthropic Platform Release Notes | **Date:** November 16, 2026 | **Link:** https://platform.claude.com/docs/en/release-notes/overview

**What changed:** Four additional Claude models — Opus 4.6, Opus 4.5, Sonnet 4.5, and Haiku 4.5 — now carry Anthropic's text watermark on supported platforms. Previously (November 3), watermarking was live only on Mythos 5, Opus 4.7, and Sonnet 4.6. This more than doubles the set of watermarked models.

**TL;DR:** Text output from Claude Opus 4.6, Opus 4.5, Sonnet 4.5, and Haiku 4.5 on supported platforms now embeds a machine-readable watermark; non-default `temperature`, `top_p`, or `top_k` values may suppress it.

**Developer signal:** If your application relies on detecting or attributing Claude-generated text — content moderation pipelines, compliance logging, provenance tracking — you should update your tooling to expect watermarks from these four model IDs. The key caveat: watermarking may not be applied when `temperature`, `top_p`, or `top_k` are set to non-default values. If your sampling parameters vary per-request, don't rely on watermark presence as a guarantee of model identity. The "supported platforms" language is unchanged from earlier entries — Claude API, Claude Platform on AWS, Anthropic-managed Google Cloud, and Microsoft Foundry, based on prior release note framing; check the docs for the definitive platform list.

**Affects you if:** You use Claude Opus 4.6, Opus 4.5, Sonnet 4.5, or Haiku 4.5 on supported platforms; you have downstream pipelines that detect, log, or rely on model provenance; you use non-default sampling parameters and expected watermarks.

**Adoption effort:** Quick — no code changes unless you're actively reading or depending on watermark absence.

**Primary source:** https://platform.claude.com/docs/en/release-notes/overview (November 16, 2026 entry)

### [MEDIUM] anthropic-sdk-python v2.9.0 + sdk-typescript v1.9.0 — seven beta headers deprecated, grep/file tool security hardening
**Source:** GitHub (anthropics/anthropic-sdk-python, anthropics/anthropic-sdk-typescript) | **Date:** November 16, 2026 | **Links:** https://github.com/anthropics/anthropic-sdk-python/releases/tag/v2.9.0 | https://github.com/anthropics/anthropic-sdk-typescript/releases/tag/sdk-v1.9.0

**What changed:** Both SDKs deprecate seven legacy `anthropic-beta` header values and remove the automatic `message-batches-2024-09-24` header from batch requests. Security hardening was applied to the grep, file, and memory tools — `rg`, `tar`, and `unzip` no longer receive `ANTHROPIC_*` environment variables, and symlink handling tightened. New: Update Bundle endpoint and RBAC Role endpoints return error codes.

**TL;DR:** Seven beta headers deprecated across Python v2.9.0 and TypeScript v1.9.0 — the API still accepts them, but a future SDK release will hard-remove them; `message-batches-2024-09-24` is already gone from batch requests.

**Developer signal:** Run a codebase search now for any of these string values — they're the headers to remove:
- `prompt-caching-2024-07-31`
- `pdfs-2024-09-25`
- `token-counting-2024-11-01`
- `token-efficient-tools-2025-02-19`
- `extended-cache-ttl-2025-04-11`
- `cache-diagnosis-2026-04-07`
- `ce-user-management-2026-07-13`

Do **not** remove `files-api-2025-04-14` or `skills-2025-10-02` until you've followed the Files API and Skills migration guides — these two still select beta response shapes and removing them changes what the API returns. If you set `message-batches-2024-09-24` manually in your batch requests, delete it. **C# users:** `AnthropicBeta` enum member numbers changed — rebuild any code compiled against v2.8.x to avoid sending wrong header values silently. The grep tool security changes (no longer inherits `ANTHROPIC_*` env vars, only reads `rg` from absolute PATH entries) are fixes that do not require code changes but may affect custom tool setups that relied on environment forwarding.

**Affects you if:** You send any of the seven deprecated beta headers in SDK or raw API requests; you use the Python SDK on Windows with Python ≤ 3.12 and hit credential file bugs; you use C# and compile against the `AnthropicBeta` enum; you rely on the Message Batches API without pinning your own beta header.

**Adoption effort:** Moderate — search and remove deprecated headers; validate Files API and Skills API migration before touching `files-api` and `skills` headers; rebuild C# bindings.

**Primary source:** https://github.com/anthropics/anthropic-sdk-python/releases/tag/v2.9.0

**[OPEN QUESTION] What do text watermarks mean for agentic output chains where one Claude model feeds another?**
Today's expansion covers Opus 4.6, Opus 4.5, Sonnet 4.5, and Haiku 4.5. The watermark is on output text. In a multi-agent setup where a Fable 5.2 orchestrator sends task output to a Sonnet 4.5 subagent as input, the Sonnet 4.5's output is watermarked — but the input it received may also be watermarked Claude output from upstream. Does the watermark survive being embedded in another model's context? Can detection tooling tell the difference between a Claude model writing watermarked text and a Claude model *reproducing* text that another model watermarked? The release notes give no guidance on this case. For compliance pipelines, the question isn't academic — if you're using watermark presence to verify model provenance, an agentic pipeline that passes Claude output through multiple Claude models creates ambiguity.

**[TENSION] NVIDIA is building the skills evaluation layer while Anthropic is tightening the runtime security layer — but they're not coordinated**
NVIDIA/SkillEvaluator's Tier 1 checks safety, format, and harness compatibility. Anthropic's SDK v2.9.0 hardened the runtime (grep tool, file tools, symlink handling). These are two sides of the same security model: static validation of what a skill claims vs. runtime enforcement of what a skill can actually do.
