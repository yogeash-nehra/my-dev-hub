## API & SDK Changes

### [HIGH] MCP 2026-07-28 Specification — Stateless Core Finalized, SDK Betas Live

**Source:** Model Context Protocol Blog | **Date:** July 28, 2026 | **Link:** https://blog.modelcontextprotocol.io/posts/2026-07-28/

**What changed:** The 2026-07-28 MCP specification transitions the protocol from a bidirectional stateful architecture to a stateless request/response model. The `initialize`/`initialized` handshake is removed. `Mcp-Session-Id` is eliminated. Two new required HTTP headers — `Mcp-Method` and `Mcp-Protocol-Version: 2026-07-28` — are mandatory on every Streamable HTTP request. Tier 1 SDK betas for Python, TypeScript, Go, C#, and Rust (beta) ship today as the migration path.

**TL;DR:** MCP is now stateless — no more session IDs or init handshake; two new required HTTP headers per request; Multi Round-Trip Requests (MRTR) replace server-initiated sampling/elicitation/roots flows; Tier 1 SDK betas landed today; Tasks move to an extension; Roots, Sampling, and Logging deprecated with 12-month offramp.

**Developer signal:** This is the forcing function: the spec is now final. (1) **Remove session logic**: strip any server-side code that relies on `initialize`, `initialized`, or `Mcp-Session-Id`. Each request must now be self-describing via `_meta`, carrying protocol version, client identity, and capabilities inline. (2) **Add required headers**: every Streamable HTTP request must include `Mcp-Protocol-Version: 2026-07-28`, `Mcp-Method`, and `Mcp-Name`. Missing headers will cause routing failures with compliant clients. (3) **Adopt Multi Round-Trip Requests (MRTR)**: the server-initiated patterns for `elicitation/create`, `sampling/createMessage`, and `roots/list` — all of which required open streams — are replaced by a poll-based flow: return `resultType: "input_required"` with the data you need, and the client retries the original call with answers in `inputResponses`. (4) **Update Tasks**: `tasks/*` moves out of the experimental core and into the `io.modelcontextprotocol/tasks` extension (poll-based `tasks/get` + new `tasks/update`). (5) **Authorization hardening**: RFC 9207 issuer validation is now required; validate `iss` before redeeming authorization codes; Dynamic Client Registration is deprecated in favor of Client ID Metadata Documents (CIMD). (6) **Timeline**: Tier 1 SDK betas are today's migration path. GA is expected around October 2026 after the 10-week validation window. You do not have to migrate today, but the spec is final and new servers should target it.

**Affects you if:** You operate an MCP server that uses session state or the initialize handshake; you are building a new MCP client or server and want to be compliant; you are using Roots, Sampling, or Logging features (12-month deprecation window); you handle Tasks in the experimental core (must migrate to extension).

**Adoption effort:** Significant — removing session initialization, adding new HTTP headers, replacing server-initiated flows with MRTR, and migrating Tasks are non-trivial changes. The SDK betas provide the migration path; Tier 1 SDK adoption removes most of the manual work, but you must still audit your server logic for session dependencies.

**Primary source:** https://blog.modelcontextprotocol.io/posts/2026-07-28/ | SDK betas blog: https://blog.modelcontextprotocol.io/posts/sdk-betas-2026-07-28/

## Tooling

### [MEDIUM] llama.cpp b10171 — Adreno GPU Multi-Stream Batch Corruption Fixed

**Source:** ggml-org/llama.cpp GitHub Releases | **Date:** July 28, 2026 | **Link:** https://github.com/ggml-org/llama.cpp/releases/tag/b10171

**What changed:** Multi-stream batches on Adreno GPUs (Snapdragon SoCs) were producing corrupted outputs silently — no error returned, just wrong model outputs. Perplexity scores measured at 1817 (vs. the expected ~15) on affected hardware. The fix routes problematic multi-stream batches to the general processing path, restoring correct output.

**TL;DR:** Silent output corruption on Adreno/Snapdragon hardware fixed in b10171 — perplexity recovers from 1817 to 15.61 on affected multi-stream batches; no API changes, drop-in upgrade.

**Developer signal:** If you are running llama.cpp on any Snapdragon-based device (Android phones/tablets, Snapdragon X Elite laptops) or Adreno GPU hardware with multi-stream batch inference, your outputs prior to b10171 may have been silently corrupted. There is no error logged — the model just returns wrong tokens. Upgrade to b10171 immediately and re-validate any outputs produced on Adreno hardware since multi-stream batching was introduced. Single-stream batches on Adreno were not affected. Desktop GPU inference (CUDA, Metal, ROCm) is unaffected. If you are building mobile inference pipelines on Android using llama.cpp's Vulkan or OpenCL backends over Adreno, this is a critical fix.

**Affects you if:** You run llama.cpp on Snapdragon-based Android devices, Snapdragon X Elite / X Plus laptops, or any hardware with an Adreno GPU using multi-stream batch mode.

**Adoption effort:** Quick — drop-in build upgrade, no API or configuration changes required.

**Primary source:** https://github.com/ggml-org/llama.cpp/releases/tag/b10171

## Trends & Emerging Tech

### MCP Goes Serverless — What the Stateless Core Actually Unlocks

**Source:** Model Context Protocol Blog + GitHub MCP Server changelog (July 23) | **Date:** July 28, 2026 | **Link:** https://blog.modelcontextprotocol.io/posts/2026-07-28/

**What's happening:** With today's spec finalization, MCP servers can now run behind standard round-robin load balancers without shared storage. The GitHub MCP Server (updated July 23 ahead of the spec) already removed its Redis session dependency — "database writes on initialize are gone, database reads are gone from every call." Each step is a separate stateless HTTP request. The entire MCP ecosystem shifts from a connection-oriented model (requiring persistent infra) to a request/response model compatible with serverless and edge deployments. Tier 1 SDK betas are the first phase; GA follows around October 2026.

**Why watch this:** The practical implication is that MCP servers can now be hosted on AWS Lambda, Cloudflare Workers, Vercel Edge, or any function-as-a-service platform without session affinity or sticky routing. The friction for building and hosting MCP servers drops considerably. Expect a wave of new MCP server projects in Q3/Q4 2026 targeting edge deployment patterns — and a corresponding pressure on existing stateful server operators to migrate. Teams building enterprise MCP deployments on Kubernetes or serverless today should design for stateless from day one rather than retrofitting.

**[OPEN QUESTION] The Adreno corruption bug ran silently — how many other hardware-specific inference bugs are producing wrong outputs in production today?**
llama.cpp b10171 fixed a bug where Adreno GPU multi-stream batches returned plausible-looking tokens at perplexity 1817 — completely wrong, but the inference pipeline never errored. No exception, no warning, no NaN check. The bug existed on Adreno hardware running multi-stream batches since that feature was introduced. For developers running llama.cpp on Snapdragon mobile or Snapdragon X Elite laptop hardware, outputs from that window are unreliable and there is no automated way to know which runs were affected. This raises a broader question: hardware-specific silent corruption is extremely difficult to catch without running identical inputs on a reference backend and comparing perplexity — a test most production pipelines don't run. The number of undiscovered hardware-specific corruption bugs currently in production llama.cpp deployments across Vulkan, WebGPU, HIP, and Metal is unknown. The same build that fixed Adreno (b10171) also addressed WebGPU binding issues and Vulkan quantization gaps (b10165, b10172), suggesting this is not a unique occurrence.

**[TENSION] The MCP stateless transition benefits greenfield deployments but creates a two-class ecosystem during the transition window**
The 2026-07-28 spec is final and new servers should target it. But Tier 1 SDKs are still in beta, GA is ~10 weeks away, and the vast majority of the 10,000+ production MCP servers in the ecosystem (per MCP project stats cited in yesterday's digest) are running stateful session logic. During the October window, a new compliant client will speak stateless; an old server will expect initialize. The MCP spec RC blog (July 2026) noted that Tier 1 SDKs "preserved backwards compatibility" in their betas, but that compatibility shim has a lifespan. The practical question: what happens in month 3 when a compliant client upgrades to the GA SDK and drops the backwards-compatible shim, but the server hasn't migrated? There is no centralized compatibility matrix or server-side version negotiation mechanism in the new stateless spec — version is declared by the client in the `MCP-Protocol-Version` header, not negotiated. An incompatible server just fails.

**[BUILDER'S ANGLE] Stateless MCP + serverless = per-request MCP tool calls at edge latency — the missing piece for real-time agentic UX**
Prior to 2026-07-28, MCP's initialize handshake meant every cold-start MCP connection incurred a round-trip before the first tool call. For serverless deployments (Lambda, Workers, Vercel Edge), this meant a persistent connection requirement that killed cold-start performance. With the stateless core, each tool call is an independent HTTP request: no handshake, no warm-up, no sticky routing needed. The implication: an agentic workflow running on Cloudflare Workers can now call a dozen MCP tools in parallel, each as a stateless HTTPS request, at edge latency globally — something that was architecturally impossible under the old protocol. The first interesting build pattern to watch: MCP servers deployed as Cloudflare Workers or Lambda@Edge that serve tool calls at <50ms globally, enabling agentic UX patterns that feel synchronous rather than asynchronous. The GitHub MCP Server's Redis removal ("database reads gone from every call — things are snappier") is a preview of what this latency profile looks like at scale.
