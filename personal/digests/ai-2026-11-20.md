## 🏆 Repo of the Day

### CelestoAI/celesto — disposable and persistent microVM sandboxes for coding agents, CI, and RL training
**Link:** github.com/CelestoAI/celesto | **Stars:** ~1.7k (5 releases in Nov) | **Language:** Python | **License:** Apache-2.0
**The problem:** Running agent-generated code safely at scale requires microVM isolation, but every available option is either a managed cloud service (E2B, Daytona, Modal) or a heavyweight Kubernetes setup — there's no self-hostable, open-source microVM SDK with a clean Python API and built-in CI inspection.
**Why it's today's pick:** Five releases shipped in November (v0.1.11 through v0.1.14, plus v0.1.15 pre-release on Nov 17), all focused on production hardening: Linux 7.3 kernel upgrades (backporting a security fix for CVE-2026-98432), QEMU confinement hardening, WAL for VM inventory to eliminate database-lock errors, and a new `celesto ci` CLI command for inspecting CI job logs and runner sizes. Teams pushing coding agents into CI pipelines now have a Firecracker-backed sandbox option that is both self-hostable and actively maintained at this star count.
**Try it in 60 seconds:**
```bash
pip install celesto

# Spin up a disposable sandbox and run a command
celesto run --disposable "python3 -c 'print(\"hello from sandbox\")'"

# Inspect CI jobs (requires CI configured)
celesto ci jobs
```
**Instead of:** Depending on E2B, Daytona, or Modal for local or self-hosted agent code execution when you need Firecracker-level isolation without a managed service.
**Watch out for:** Pre-1.0 (`v0.1.14` stable) — expect breaking CLI and API changes between minor versions. The lower-level library (`smolvm` on PyPI) and the higher-level `celesto` package have overlapping documentation that can cause confusion. Star-history momentum couldn't be validated via star-history.com in this scan environment (DNS blocked) — verify sustained growth on GitHub before committing to production use.

## Model Releases

### [HIGH] Gemini 4 Neon — $3/$15 per million tokens, 1M context, four thinking levels
**Source:** Google Blog | **Date:** 2026-11-18 | **Link:** https://blog.google/innovation-and-ai/models-and-research/gemini-models/introducing-gemini-4-neon/
**What changed:** Google added Neon as a new entry in the Gemini 4 family below Carbon: four thinking levels (low/medium/high/xhigh), a 1M-token shared context window, and $3 input / $15 output per million token pricing — approximately half the per-task cost of Carbon at comparable quality per third-party benchmarks.
**TL;DR:** Gemini 4 Neon scores ~60 on the Artificial Analysis Intelligence Index at the default `high` thinking level — below Fable 5.2 (65) and GPT-6.2 Astra (62) but priced at $3/$15 per million tokens versus Astra's $8/$40, making it the most cost-competitive thinking model for mid-complexity agentic tasks.
**Developer signal:** The model ID is `gemini-4-neon` via the Gemini API (`generateContent` and Interactions API). Access is on the paid tier in Google AI Studio and Android Studio — not on the Free tier. The four thinking levels are configured via the same `thinkingConfig` parameter used for Gemini 4 Carbon; the API call pattern is identical, so the migration is a model ID swap only. Implicit caching is supported at $0.15/million for cached input; explicit caching is NOT supported. The 1M-token context window is shared across input, thinking tokens, and output — synchronous responses cap at ~65k output tokens, while long-decode can extend output up to 1M tokens. For cost-sensitive agentic pipelines currently running on Carbon or Carbon Flash, benchmark Neon at `high` thinking level (the API default) on your tasks — third-party data puts it at roughly half the per-task cost for mid-complexity workflows at similar quality. For simple tasks, consider dropping to `low` or `medium` thinking levels to reduce latency and thinking token costs.
**Affects you if:** You build agentic pipelines on the Gemini API and are sensitive to per-task inference cost; you need 1M-context thinking capabilities without Carbon-tier pricing; you're evaluating Gemini's thinking model tier for coding agents.
**Adoption effort:** Quick (model ID swap from `gemini-4-carbon` to `gemini-4-neon`; `thinkingConfig` parameter unchanged; note: explicit cache users need to remove that configuration, as it's unsupported).
**Primary source:** https://blog.google/innovation-and-ai/models-and-research/gemini-models/introducing-gemini-4-neon/

## Tooling

### [MEDIUM] Claude Code v2.1.329 — /tasks manager, OpenTelemetry in Code Mode, max_tokens auto-retry removed
**Source:** Claude Code Changelog | **Date:** 2026-11-19 | **Link:** https://code.claude.com/docs/en/changelog
**What changed:** v2.1.329 follows v2.1.328 (yesterday's digest) as a same-day second release with its own full set of features and 91 bug fixes: `/tasks` command now lists all background tasks (scheduled, loop wakeups, goals, forks) with one-key stop controls; Code Mode adds OpenTelemetry support with per-tool-call events; the `max_tokens` automatic retry introduced in v2.1.326 is removed.
**TL;DR:** Claude Code v2.1.329 ships a `/tasks` task manager (press `x` to stop any background task), OpenTelemetry tracing for Code Mode tool calls, and removes the `max_tokens` auto-retry — plus 91 bug fixes including a macOS Keychain sign-out loop and `.claude.json` reset during network stalls.
**Developer signal:** (1) **`max_tokens` auto-retry removed** — this is the most disruptive change. v2.1.326 silently retried requests that hit gateway output token limits; that behavior is now gone. If you deploy Claude Code on a gateway with a lower output token cap (Bedrock, GCP, Foundry, etc.), set `CLAUDE_CODE_MAX_OUTPUT_TOKENS` as an environment variable to match the gateway's limit. Without it, your requests will fail at the limit with no automatic recovery. Check your gateway's current output token configuration before updating. (2) **`/tasks` command** — press `x` on any listed background task to stop it after a confirmation prompt. This covers scheduled routines, loop wakeups, goals, and conversation forks in one view. Previously, stopping a background task required knowing its session ID and using CLI flags. (3) **OpenTelemetry in Code Mode** — if you have an OTEL exporter endpoint configured (`CLAUDE_CODE_OTEL_ENDPOINT`), Code Mode tool calls now emit trace events. Useful for observability on automated agent pipelines. (4) **Hook trust dialog** — a new warning shows which file a folder's hooks are declared in before the user accepts. If you author Claude Code plugins with hooks, test that your hook file paths are clearly attributable. (5) **Code Mode PreToolUse hook behavior** — Code Mode no longer refuses a script's tool call when a PreToolUse hook errors, unless you explicitly set `"onFailure": "block"`. If you rely on hook errors to block tool calls in Code Mode, add this flag to your hook definitions.
**Affects you if:** You deploy Claude Code on a gateway with an output token limit lower than Claude's default; you run scheduled tasks or loop routines in Claude Code sessions; you use OpenTelemetry; you author PreToolUse hooks in Code Mode.
**Adoption effort:** Moderate (audit gateway deployments for the max_tokens change and set `CLAUDE_CODE_MAX_OUTPUT_TOKENS`; update PreToolUse hooks if you relied on error-means-block behavior; `/tasks` is additive).
**Primary source:** https://code.claude.com/docs/en/changelog (v2.1.329, Nov 19 entry — fetched directly)

**[TENSION] Operational telemetry in Claude Code (OpenTelemetry in Code Mode) vs. the trust/privacy model of autonomous agents**

For teams running Claude Code on sensitive codebases, the OTEL endpoint in `CLAUDE_CODE_OTEL_ENDPOINT` deserves the same access control review as the agent's filesystem permissions. This is the natural price of observability — worth calling out explicitly as Code Mode tool call observability becomes the default for agentic CI setups.

**[BUILDER'S ANGLE] Gemini 4 Neon's four thinking levels as a prompt-routing primitive**

Neon's four explicit thinking levels (low/medium/high/xhigh), combined with its 1M context, create an interesting primitive: within a single model, you can dynamically adjust reasoning depth per task step without switching models or paying for a new context bootstrap.
