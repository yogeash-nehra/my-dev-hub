## 🏆 Repo of the Day

### mvschwarz/openrig — persistent, organized teams of AI coding agents from Claude Code, Codex, and Pi
**Link:** github.com/mvschwarz/openrig | **Stars:** ~6,091 (↑ +2,912 this week) | **Language:** TypeScript | **License:** Apache 2.0

**The problem:** Managing multiple AI coding agent sessions is terminal sprawl — sessions don't survive reboots, have no shared context, and require constant manual restarting and permission re-approval.

**Why it's today's pick:** OpenRig is the only open-source tool this week that addresses multi-agent coding session management as a first-class infrastructure problem. Rather than scripting a wrapper, it gives you a persistent daemon, a TUI, a CLI, and a built-in MCP server backed by SQLite and tmux. The key concept is a *seat* — a stable role address like `dev-build@starter` that survives restarts, can receive messages, and holds a place in a RigSpec YAML team definition. At +2,912 stars this week it's the strongest momentum signal among qualifying tools in this scan. v0.6.7 is the latest stable release (Apache 2.0, macOS/Linux, Node 22+).

**Try it in 60 seconds:**
```bash
# Install
npm install -g @openrig/cli

# Preview what the starter team will set up in your repo
cd /path/to/your/repository
rig setup --dry-run
rig specs preview starter --kind rig

# Launch the team
rig up starter --cwd .

# Assign a task to the build agent
rig send dev-build@starter 'Implement <one useful change>.'

# Open the operator TUI
rig tui
```
**Instead of:** Maintaining 4+ unrelated terminal sessions with no shared state, manually re-approving permissions after each restart, and losing context on system reboots.

**Watch out for:** `rig setup` writes provider hooks, trust settings, and workspace files — back up those files before first use as the README recommends. The project is pre-1.0 and the Releases tab is not populated (v0.6.7 referenced in install scripts). Pi/Oh My Pi support uses RPC runners that may not be stable on all platforms yet.

## [BREAKING] Breaking Changes

### [BREAKING] Anthropic Managed Agents: three web-access security hardening changes
**Source:** Anthropic Platform Release Notes | **Date:** October 7, 2026 | **Link:** https://platform.claude.com/docs/en/release-notes/overview

**What changed:** Three simultaneous breaking behavior changes to Managed Agents with `limited` networking, none of which were covered in yesterday's digest:

1. **`web_fetch` restricted to URLs already present in the session.** The `web_fetch` tool now only fetches URLs that appeared in the session before the call — in user message text, web_search results, or prior `web_fetch` results. URLs from Claude's own output, the system prompt, attached documents, or other tool outputs (bash, read, MCP) are not eligible. Calls for ineligible URLs return `url_not_in_prior_context`.

2. **`allowed_hosts` now governs the `web_search` and `web_fetch` tools.** In `limited` networking, the same `allowed_hosts` list that gates network access now also filters web tool output: `web_fetch` calls to unlisted hosts return `url_not_allowed`; `web_search` omits results from unlisted hosts.

3. **Session creation now fails if `allowed_domains` contains entries not covered by `allowed_hosts`.** With `limited` networking, creating or updating a session with a web tool's `allowed_domains` entry that isn't in `allowed_hosts` returns a 400 error. Note that `docs.example.com` is NOT within `["example.com"]` — each host must be listed exactly unless using a `*.` wildcard prefix.

**TL;DR:** Three Managed Agents web-access restrictions shipped Oct 7 — `web_fetch` now only reaches URLs already seen in-session, `allowed_hosts` governs web tool output, and mismatched `allowed_domains`/`allowed_hosts` configs fail at session creation time.

**Developer signal:** Audit Managed Agent integrations in this order: (1) **`web_fetch` calls**: any agent that fetches URLs it generates itself (e.g., constructing a URL from tool output and fetching it) will now get `url_not_in_prior_context` errors — send those URLs in a user message instead, or use a `web_search` step first to get the URL into context. (2) **`allowed_hosts` vs `allowed_domains`**: if your agent's web tools have `allowed_domains` entries, verify each is also in `allowed_hosts` or session creation will fail with a 400. Watch for exact-match vs wildcard semantics — `example.com` does not cover `docs.example.com`. (3) **Impact on agentic loops**: agents that used `web_fetch` for data exfiltration defense bypasses (i.e., constructing URLs in-flight) are now stopped at the platform level — this is the stated intent. Adjust agent prompts and tool configurations accordingly.

**Affects you if:** You build with Managed Agents using `limited` networking; you have agents that call `web_fetch` on URLs they generate themselves; you have `allowed_domains` entries on web tools.

**Adoption effort:** Moderate — requires auditing agent web_fetch call patterns, regenerating session configs that set allowed_domains, and updating agent prompts to pass fetchable URLs in user messages.

**Primary source:** https://platform.claude.com/docs/en/release-notes/overview

## API & SDK Changes

### [HIGH] Claude Code v2.1.295 — hooks `onFailure: "block"`, MCP descriptions 16K chars, gateway models list, mod notifications
**Source:** GitHub Releases (anthropics/claude-code) | **Date:** October 8, 2026 | **Link:** https://github.com/anthropics/claude-code/releases/tag/v2.1.295

**What changed:** A ~100-item release. Key changes by category:

**Hooks (new reliability control):** `onFailure: "block"` added to command and HTTP hooks — when a hook can't start, times out, or exits with an unexpected code, the action is now blocked rather than let through. Also fixed: a mod hook receiving deeply nested tool input that was silently truncated (allowing guard bypass), async hook JSON output being ignored when printed over multiple lines, and variables written to `CLAUDE_ENV_FILE` by a SessionStart hook not reaching Bash after an in-app `/resume` or `/branch`.

**MCP (major limit increase):** Tool description character limit raised from **2,048 to 16,384** — an 8× increase. Claude.ai connectors now negotiate **MCP protocol version 2026-07-28** by default; `MCP_PROTOCOL_NEGOTIATION=legacy` opts out. Remote servers back off on repeated drops up to 30s. CSS, JS, XML from MCP tools no longer saved as `.bin`. Permission prompts now show tool by readable name instead of `mcp__server__tool`.

**Gateway:** `timeouts.upstream_ttfb_ms` per upstream limits how long a stream may take to start before failover or 502. A `models` list per upstream restricts which models are routed there (use `*` as wildcard). Background requests now use Haiku 4.5 as default. Bedrock token counts now use AWS `CountTokens` (requires `bedrock:CountTokens` permission).

**Mod API:** `$.ui.notify` raises a native notification through the user's notification setting. `Button` children now accept strings and `Text` nodes (chip/dim detail inside a pressable row). `config.set` hooks now fire on `/model`, `/fast`, `/output-style`, and auto-update channel changes in `/config`.

**Subagents:** Preload at most **32 skills** per subagent. `CLAUDE_AUTO_BACKGROUND_TASKS` no longer backgrounds a subagent while an edit or shell command is pending.

**VS Code:** Click a sent file's name in chat to open it in the editor. Fixed "Fork conversation from here" and Rewind failing with "Message not found in session." Tab keyboard shortcuts no longer switch permission mode.

**TL;DR:** Claude Code v2.1.295 adds `onFailure: "block"` for hooks (actions blocked when a hook fails, not silently passed), raises MCP tool descriptions to 16,384 chars, and adds a per-upstream `models` list for gateway routing — update immediately if you use hooks for security controls or run long MCP tool descriptions.

**Developer signal:** Three changes demand attention before updating production Claude Code deployments: (1) **`onFailure: "block"` changes hook semantics**: previously, a hook that failed to start or timed out let the underlying action through. Now it blocks. If you have hooks that occasionally fail or time out (flaky HTTP endpoints, slow commands), those actions will now fail instead of proceeding. Audit hook reliability before deploying. (2) **MCP tool descriptions now 16,384 chars**: if you maintain MCP servers with rich tool descriptions that were previously silently truncated at 2,048 chars, update and re-test — Claude now receives the full description, which may change behavior. (3) **Gateway `models` list**: if you self-host a gateway, add a `models` list to each upstream to control which models route there; without it, any model request goes to any upstream (existing behavior unchanged, but now opt-in granularity is available). Mod developers: `$.ui.notify` is the new notification primitive — use it instead of custom toast workarounds.

**Affects you if:** You use Claude Code hooks for security controls or automation; you maintain MCP servers with descriptions >2,048 chars; you operate a Claude apps gateway; you build Claude Code mods.

**Adoption effort:** Quick (version update) — audit hook `onFailure` semantics before deploying to production if hooks guard security-critical actions.

**Primary source:** https://github.com/anthropics/claude-code/releases/tag/v2.1.295

## Trends & Emerging Tech

### The agent security layer is consolidating — from external policy to runtime enforcement
**Source:** Multiple (Anthropic Platform Release Notes Oct 7-8; Anthropic 2026 Usage Policy; Claude Code v2.1.295; github.com/mvschwarz/openrig) | **Date:** October 8, 2026

**What's happening:** Three independent signals this week point to agent security shifting from documented policy to runtime enforcement. Claude Code v2.1.295's `onFailure: "block"` for hooks changes hooks from "best-effort guardrails" to "blocking checkpoints." Managed Agents' `web_fetch` URL restriction moves data exfiltration prevention from "developer responsibility" to "platform-enforced." The usage policy update's physical-action hardware requirements are the first formal specification of what a safely-integrated agent needs to guarantee at the hardware level. These aren't docs changes — they're behavioral changes.

**Why watch this:** The pattern is enforcement moving down the stack: what was a policy or a best-practice recommendation in 2025 is now a runtime guarantee or a 400 error in 2026. For developers, this means two things. Short term: existing agent codebases that relied on previous "permissive by default" behaviors need auditing — specifically Managed Agents web_fetch call patterns and hook failure modes. Longer term: as enforcement densifies at the platform level, the agent security layer starts looking more like a runtime (fail-closed, auditable, policy-as-code) and less like a set of guidelines. OpenRig's `onFailure` hook pattern and MCP server integration fit this emerging model well — tools that treat agent behavior as infrastructure are better positioned as enforcement tightens.

**[TENSION] Anthropic's OSS Scanner (>90% TP, no human review) vs. OSS maintainer bandwidth**
The OSS Scanner ships model-generated vulnerability reports without human review, with an expected true-positive rate above 90%. The flip side: a 10% false-positive rate on an automated scanner means roughly 1 in 10 reports is wrong in severity or classification. For a widely-used project receiving even 10 reports per scan, 1 spurious critical-severity PoC report per cycle will create maintainer churn. Anthropic offers human-verified disclosures for "projects without capacity to handle the volume" — but the threshold for that opt-in is undefined. The tension: the same automation that makes OSS Scanner free and scalable is the source of the FP risk. What to watch: early adopter reports from the first cohort of enrolled projects, particularly around PoC quality and severity calibration. A high-profile false-positive will pressure Anthropic to clarify the human-review opt-in criteria.
