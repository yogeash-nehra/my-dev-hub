```bash

# Then, in any Claude Code / compatible coding agent session:
# /security-audit run
# (The skill activates on trigger phrases like "audit for security issues", "run security scan", etc.)
```
**Instead of:** Manual code review, point-in-time SAST tools (Semgrep, Snyk) run outside the agent loop, or ad-hoc "check this for security issues" prompts with no structured verifier pass.

## [BREAKING] Breaking Changes

### [BREAKING] Pydantic AI v2.58.0 — two security advisories: MCP credential leak and tool execution without model request
**Source:** GitHub Releases | **Date:** 2026-10-19 | **Link:** https://github.com/pydantic/pydantic-ai/releases/tag/v2.58.0

**What changed:** Two GHSA-numbered security vulnerabilities patched. (1) GHSA-xv4x-g8mx-ch56: provider-native MCP config exposed server URLs, auth tokens, and custom header values in OpenTelemetry request traces, even with `include_content=False`. URL-based MCP identifiers could also surface an embedded credential. (2) GHSA-5pfm-2g3g-gh85: with non-empty server-side `message_history` and the default `manage_system_prompt='server'`, the Vercel AI and AG-UI adapters could run an available (non-approval-required) tool with client-chosen arguments without a model request. v1 is unaffected by the second advisory.

**TL;DR:** Upgrade immediately: pydantic-ai 2.58.0 patches a MCP credential leak into OTel traces and an unauthorized tool-execution path in Vercel AI / AG-UI adapters.

**Developer signal:** For the MCP advisory (GHSA-xv4x-g8mx-ch56): if you use provider-native MCP config with pydantic-ai *and* export traces to OpenTelemetry, your MCP server URLs, auth tokens, and custom headers may be in historical trace data. Upgrade to v2.58.0 now, restrict access to your trace storage retroactively, and rotate any exposed credentials. If you use Temporal and have MCP in in-flight workflows, hold off on adding explicit `id=` to MCP until those workflows finish — changing the activity name will break them. For the UI adapter advisory (GHSA-5pfm-2g3g-gh85): if you expose Vercel AI or AG-UI adapters with server-side `message_history` set (non-empty) and the default `manage_system_prompt='server'`, a client could have constructed requests that triggered available tool calls without a model decision. Check audit logs for unexpected tool invocations before and after upgrading. Approval-required tools were not affected. v1 is safe. Fix: upgrade to v2.58.0 (also in v1.107.8 for the MCP advisory).

**Affects you if:** You use pydantic-ai with provider-native MCP connections and OpenTelemetry trace export; you expose pydantic-ai Vercel AI or AG-UI adapters with server-side `message_history`.

**Adoption effort:** Quick (upgrade + credential rotation for MCP advisory; audit log review for adapter advisory).

**Primary source:** https://github.com/pydantic/pydantic-ai/releases/tag/v2.58.0

### [MEDIUM] Claude Code v2.1.304 — fork subagents on by default, /auto-mode-setup everywhere, managed-agents security check
**Source:** GitHub Releases | **Date:** 2026-10-19 21:34 UTC | **Link:** https://github.com/anthropics/claude-code/releases/tag/v2.1.304

**What changed:** Fork subagents are now enabled by default in `claude -p`, the Agent SDK, Claude desktop, and VS Code (previously opt-in). `/auto-mode-setup` expanded to Bedrock, Vertex, Foundry, the Claude apps gateway, and telemetry-disabled sessions (was direct API only). New `/claude-api managed-agents-secure` command compares your Managed Agents config against Anthropic's security guide without making changes. Mod hook API additions: `decider: "person"` and `e.isReadOnly`. Code Review adds Quick/Standard/Deep levels configurable per org or repo.

**TL;DR:** Fork subagents ship as the default across all Claude Code surfaces — the most impactful behavior change — alongside a new Managed Agents security audit command and Code Review granularity settings.

**Developer signal:** The fork subagent default is the change to act on first. In previous releases, fork subagents were opt-in. Now they're on by default in `claude -p`, the Agent SDK, desktop app, and VS Code. Fork subagents share the parent's conversation cache but keep their tool output out of the parent's context, which improves context efficiency in multi-agent workflows. If your existing scripts or integrations in `claude -p` or the Agent SDK depend on the prior non-fork subagent behavior (e.g., you post-process tool output that would now be isolated), set `CLAUDE_CODE_FORK_SUBAGENT=0` to restore the old behavior. For teams using Managed Agents: run `/claude-api managed-agents-secure` before your next production deployment — it reports misconfigurations read-only, so it's safe to run at any time. On the Linux sandbox side: the bracket glob bug in `sandbox.filesystem.denyRead` patterns (e.g., `[user-id]` was causing commands to fail) is fixed — upgrade if you use deny rules.

**Affects you if:** You run `claude -p` or use the Agent SDK in scripts (fork subagent default); you build mods/plugins that use `tool.check` hooks; you use Managed Agents in production; you run Claude Code on Linux with `sandbox.filesystem.denyRead` glob patterns.

**Adoption effort:** Quick (upgrade + check `CLAUDE_CODE_FORK_SUBAGENT` if needed).

**Primary source:** https://github.com/anthropics/claude-code/releases/tag/v2.1.304

### [NOTABLE] E2B v2.57.0 + v2.58.0 — streaming terminal input for PTY sessions, TLS egress proxy, Python 3.10 dropped
**Source:** GitHub Releases | **Date:** 2026-10-20 | **Link:** https://github.com/e2b-dev/E2B/releases

**What changed:** `streamInput` / `stream_input` added for commands and PTY sessions in both JS and Python SDKs, enabling ordered input over a persistent stream. TLS configuration option added to the egress proxy. Python 3.10 compatibility shims removed.

**TL;DR:** E2B now supports streaming terminal input to sandbox PTY sessions — useful for driving interactive processes like REPLs or test runners from an agent, rather than batching input requests.

**Developer signal:** Before this, driving an interactive process inside an E2B sandbox required batching input requests on a fixed schedule (the CLI sent one per 10ms). `streamInput` replaces that with a single persistent stream: in JS it returns a `CommandInputHandle`; in Python the async variant returns a handle, and the sync variant takes an iterable. Useful when your agent needs to run an interactive REPL, navigate a wizard installer, or control a test runner with stdin. For the egress proxy: the new `tls` option lets you pass CA and certificate config for environments where outbound sandbox traffic goes through an enterprise proxy with custom TLS. **Python 3.10 deprecation:** `@e2b/python-sdk@2.58.0` and related packages dropped Python 3.10 compatibility shims. If your environment uses Python 3.10 and you need the `tls` egress option (from v2.57.0), that version is still 3.10-compatible.

**Affects you if:** You build agents that interact with long-running terminal processes in E2B sandboxes; you route E2B egress through an enterprise TLS proxy; your E2B integration targets Python 3.10.

**Adoption effort:** Quick (upgrade; moderate if you need to migrate from Python 3.10 to 3.11+).

**Primary source:** https://github.com/e2b-dev/E2B/releases

**[OPEN QUESTION] What does a security-hardened MCP deployment look like, and does the spec address it?**
The pydantic-ai MCP telemetry advisory exposes a gap: when you add OpenTelemetry instrumentation to a framework that uses MCP connections, the observability layer becomes a credential-exfiltration path — even with `include_content=False`, which most security-conscious teams would have set. The MCP spec (last stable release: 2026-07-28) doesn't specify what fields implementations must scrub before logging or tracing. Cloudflare's security-audit-skill covers "prompt injection and agent/tool risks in LLM-backed apps" as an attack class, but it doesn't (yet) audit the instrumentation layer. The open question: is this a framework bug (pydantic-ai's to fix, as they did), or is it a protocol-level gap that the MCP spec should address with a normative "must not serialize auth credentials" clause? If the latter, every MCP-compatible framework is independently vulnerable to the same pattern.

**[BUILDER'S ANGLE] A verifier-as-sub-agent pattern is generalizeable beyond security audits**
Cloudflare's security-audit-skill uses a specific architectural pattern: a primary agent generates findings candidates, and an independent verifier sub-agent tries to *disprove* each one before it's reported. The result is labeled `confirmed`, `needs_validation`, or `rejected`. This pattern — generate → verify adversarially → filter — isn't unique to security. It applies to code review (generate suggestions → verify they don't break tests), documentation (generate explanations → verify against the source code), and test generation (generate tests → verify they actually catch the bugs they claim to). None of these domains currently have a packaged "verifier sub-agent skill" beyond security. The first framework to make this a first-class primitive (a `verify_agent` that any orchestrator can attach to any other agent) would cover a large surface.
