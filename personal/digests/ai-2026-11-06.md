### max-sixty/worktrunk — git worktree management CLI built for parallel AI agent workflows
**Link:** github.com/max-sixty/worktrunk | **Stars:** ~11,800 (↑ ~1,802 this week) | **Language:** Rust | **License:** MIT OR Apache-2.0

**The problem:** Running multiple AI coding agents in parallel requires a separate git worktree per agent, but the native `git worktree` UX is clunky — you type the branch name three times to start, paths are hard to reference, and merging back requires leaving your working directory.

**Why it's today's pick:** worktrunk makes worktrees first-class: they're addressable by branch name, paths are computed from a configurable template, and v0.81.0 (Oct 20) adds `wt merge --branch` — merge another worktree's branch *without* leaving your current one, running commit/squash/rebase in the source worktree and auto-cleaning up after. With Claude Code v2.1.319 today shipping MCP task background mode and improved subagent support, the git worktree UX is the natural next friction point for teams running parallel Claude Code instances. worktrunk is the cleanest solution in this space at under 12k stars — still early enough to catch before it becomes ubiquitous.

**Try it in 60 seconds:**
```bash
# macOS
brew install worktrunk
wt config shell install          # adds `wt` alias and shell completion
wt switch --create feature/my-branch  # creates worktree at a computed path
wt list                          # see all active worktrees with status
wt merge --branch feature/my-branch   # merge from another worktree without cd-ing to it
```
**Instead of:** `git worktree add ../branch-name branch-name && cd ../branch-name && git merge ... && cd - && git worktree remove ../branch-name`

## [BREAKING] Breaking Changes

### [BREAKING] Claude Code v2.1.319 — auto mode behavior without telemetry, `claude -p` exit code, proxy settings
**Source:** GitHub | **Date:** 2026-11-06 | **Link:** https://github.com/anthropics/claude-code/releases/tag/v2.1.319
**What changed:** Three behaviors changed in v2.1.319 without backward compatibility: (1) auto mode without telemetry/feature flags no longer falls back to the built-in classifier; (2) `claude -p` in auto mode now exits 1 (was 0) on refused actions; (3) `CLAUDE_CODE_PROXY_RESOLVES_HOSTS` can no longer be set in settings files.
**TL;DR:** Claude Code v2.1.319 (Nov 6) changes auto mode's fallback path behind LLM gateways from silent classifier to ask/deny, flips `claude -p` exit code from 0 to 1 on refusal, and bans `CLAUDE_CODE_PROXY_RESOLVES_HOSTS` from settings files — three changes requiring action from teams running Claude Code in automated or gateway environments.
**Developer signal:**
1. **Auto mode behind LLM gateways:** Set `CLAUDE_CODE_AUTO_MODE_SERVER=0` to restore the built-in classifier fallback if your auto mode workflows break after upgrading behind an enterprise proxy or LLM gateway. Bedrock, Vertex, and Foundry are unchanged.
2. **`claude -p` exit code:** Update CI scripts that check `exit 0` for success — `exit 1` now means tool calls were refused, not that the command itself failed. Add a handler or pipe the exit code if downstream logic branches on it.
3. **`CLAUDE_CODE_PROXY_RESOLVES_HOSTS`:** Move this from your `.claude/settings.json` to the process environment (shell profile, Docker env vars, CI env vars).
4. **Also audit:** Nested skills below the starting directory no longer auto-load; self-paced `/loop` ends on a completed turn (set `CLAUDE_CODE_LOOP_KEEPALIVE=1` for old behavior); session ask rules now deny (not prompt) when a broader deny rule covers the command.
**Affects you if:** You run Claude Code in auto mode behind an enterprise LLM gateway or proxy without telemetry; you have CI/CD scripts that check `claude -p` exit codes; you set `CLAUDE_CODE_PROXY_RESOLVES_HOSTS` in settings files; you use self-paced `/loop` for unattended workflows.
**Adoption effort:** Moderate (gateway users: set env var immediately; CI scripts: audit exit code handling; proxy settings: move to env; loop users: check if keepalive flag is needed)
**Primary source:** https://github.com/anthropics/claude-code/releases/tag/v2.1.319

### [HIGH] Claude Code v2.1.319 — four security fixes, MCP task background mode, permissions.denyInsteadOfPrompting
**Source:** GitHub | **Date:** 2026-11-06 | **Link:** https://github.com/anthropics/claude-code/releases/tag/v2.1.319
**What changed:** Four separate permission-check bypass vulnerabilities patched in one release (Bash crafted env prefix, sandbox escape from worktree creation, `sed` command bypass, quoted-word bypass in deny/ask rules), plus MCP tasks now run in the background in the terminal (non-blocking), `permissions.denyInsteadOfPrompting` setting, and `/claude-api latency-optimize` command.
**TL;DR:** Claude Code v2.1.319 (Nov 6) patches four permission-bypass paths across Bash, sandbox, and file-edit workflows, makes MCP tool calls non-blocking in the terminal, and adds a new `denyInsteadOfPrompting` permission mode that fails fast instead of pausing on unknown tool calls.
**Developer signal:**
1. **Security — upgrade immediately if running in auto mode or as a subagent:** The four patched paths are: (a) a crafted environment prefix in a Bash command could hide part of the command from the permission checker; (b) creating a worktree could escape the sandbox; (c) a `sed` command could skip the permission check in accept-edits and auto mode; (d) commands written with quoted words slipped through Bash deny and ask rules. Any of these would let a malicious tool call or instruction bypass your configured allow/deny rules. Update now — `npm i -g @anthropic-ai/claude-code@latest`.
2. **MCP tasks go background:** When an MCP server runs a tool as a task, Claude Code now moves it to the background immediately and reports the result when finished, instead of blocking the turn. Claude can continue processing while the tool runs. This is on by default in the terminal; use `CLAUDE_CODE_DISABLE_MCP_TASK_BACKGROUND` to restore blocking behavior, or `CLAUDE_CODE_DISABLE_MCP_TASKS=1` to turn MCP tasks off entirely.
3. **`permissions.denyInsteadOfPrompting`:** A new setting in `settings.json`. When set, tool calls that would otherwise pause and wait for a permission prompt are **denied** and the turn continues. Use this in subagent and teammate contexts where you want fail-fast behavior rather than interactive pauses.
4. **`/claude-api latency-optimize`:** New slash command that finds where your Claude API code makes users wait and tries faster settings against your eval. Useful for tuning streaming, timeout, and model selection parameters when user-facing latency matters.
5. **Gateway auto mode change:** See Breaking Changes section. If you run Claude Code behind an LLM gateway without telemetry, action is required.
6. **`/tasks` session history:** The `/tasks` command gained an "Earlier in this session" row listing finished subagents. You can reopen and message any of them.
7. **`--trust-workspace false`:** This flag now also stops hooks in the repository's `.claude/settings.json` and skills from running — previously it only applied to Claude Code's own trust prompts.
**Affects you if:** You run Claude Code in auto mode, as a subagent, or in a managed/enterprise gateway setup; you have MCP servers with long-running tool calls; you use `claude -p` in CI pipelines; you check exit codes from Claude Code in scripts.
**Adoption effort:** Moderate (security fixes: drop-in upgrade; auto mode + gateway: check env/settings; CI scripts: audit exit code handling; `permissions.denyInsteadOfPrompting`: opt-in config change)
**Primary source:** https://github.com/anthropics/claude-code/releases/tag/v2.1.319
*Quality gate score: 9 (official Anthropic/Claude Code release +3; four concrete security CVE-class fixes + feature changes with specific env var flags +2; GitHub releases.atom primary source +2; Nov 6 window +1; technical audience +1)*

### [MEDIUM] LangGraph SDK 0.4.14 — `strict_resume` in SDK runs API, `tools` and `lifecycle` added to StreamMode
**Source:** GitHub | **Date:** 2026-11-06 | **Link:** https://github.com/langchain-ai/langgraph/releases/tag/sdk%3D%3D0.4.14
**What changed:** `strict_resume` parameter added to `runs.create`, `runs.stream`, and `runs.wait` in the SDK (previously this was only in `langgraph` core, not the SDK client); `tools` and `lifecycle` added as valid values for `StreamMode`.
**TL;DR:** LangGraph SDK 0.4.14 (Nov 6) makes `strict_resume` a first-class parameter in every SDK run method, so Python and TypeScript clients can now enforce strict interrupt-answer semantics without calling into internal langgraph core APIs.
**Developer signal:**
1. **`strict_resume` is now in the SDK:** Previously you had to drop into langgraph core to get strict resume semantics. Now: `client.runs.create(thread_id, assistant_id, ..., strict_resume=True)` — this raises `UnknownInterruptError` on stale or mismatched interrupt IDs rather than silently re-pausing. If you're building human-in-the-loop flows that call the LangGraph SDK (not just the library directly), this is the right way to enable it going forward.
2. **`StreamMode.tools` and `StreamMode.lifecycle`:** Two new values in `StreamMode`. `tools` streams individual tool call events as they happen; `lifecycle` streams graph-level lifecycle events (node start/end, checkpoint). These let you build more granular event-driven UIs without polling graph state.
3. **Context:** This SDK release accompanies langgraph 1.2.20 (Nov 5, covered yesterday) and langgraph-sdk 0.4.13 (Nov 5). The 0.4.14 drop is specifically to surface `strict_resume` and the new StreamMode values to SDK consumers.
**Affects you if:** You call the LangGraph SDK runs API (`client.runs.*`) in Python or TypeScript; you build streaming UIs on top of LangGraph agent runs; you need explicit interrupt semantics in multi-step human-in-the-loop workflows.
**Adoption effort:** Quick (drop-in package upgrade; `strict_resume=True` is opt-in; StreamMode values are additive)
**Primary source:** https://github.com/langchain-ai/langgraph/releases/tag/sdk%3D%3D0.4.14

**[PATTERN] The same release that hardens security is also the one that enables autonomy**
Claude Code v2.1.319 patches four permission-check bypasses on one side — and on the other side ships `permissions.denyInsteadOfPrompting` (turns pauses into denials, keeps the turn running), MCP task background mode (tool calls are now non-blocking), and auto mode gateway changes (server-side check is authoritative). The simultaneous move is: harden the boundary (fewer bypasses), AND make the agent more autonomous within it (fewer pauses, more background work). This is the same pattern that Claude Code v2.0's `--dangerously-skip-permissions` removal followed: remove one escape hatch, add a safer mechanism for the same use case. The implication: Anthropic's internal model of "safe autonomous agent" is converging on "agent that fails fast on ambiguity rather than pausing or falling back."
*Grounded in: Claude Code v2.1.319 security fixes and permissions.denyInsteadOfPrompting (Nov 6)*

**[OPEN QUESTION] What does `permissions.denyInsteadOfPrompting` mean for multi-tier agent systems?**
When Claude Code runs as a subagent inside an orchestrator, `permissions.denyInsteadOfPrompting` means tool calls outside the declared allow set are denied and the turn continues. The orchestrator receives the continuation — but does it know the tool call was denied? The `cancel_reason` field on LangGraph `Run` (SDK 0.4.13, Nov 5) is the closest thing to an upstream-visible denial signal. But in a Claude Code subagent context, there's no equivalent signal the orchestrator automatically sees unless the agent explicitly reports the denial in its output. For multi-tier agent systems, this means tool-call denials are currently invisible to the orchestrator unless you instrument for them. That is a gap: a subagent quietly denied a file read could plausibly continue generating a plausible but incorrect response without the orchestrator knowing what it couldn't see.
*Grounded in: Claude Code v2.1.319 permissions.denyInsteadOfPrompting; LangGraph SDK 0.4.13 cancel_reason on Run (Nov 5)*

**[IF THIS CONTINUES] MCP tasks going background is the first step toward true async agent-to-agent messaging**
MCP tasks in Claude Code v2.1.319 now run in the background: tool call fires, Claude continues, result arrives when the task finishes. This is non-blocking within a turn — Claude Code's existing execution model. The next step, which isn't in this release, would be asynchronous MCP tasks that arrive *between* turns rather than within one. If that lands (MCP tasks that resolve to a future message rather than within-turn tool result), it would be the first native async messaging primitive between a Claude Code session and an MCP server — the core building block for event-driven multi-agent communication patterns. The `/tasks "Earlier in this session"` row (also v2.1.319) hints at growing investment in task-as-first-class-entity, which is a prerequisite for that architecture.
*Grounded in: Claude Code v2.1.319 MCP task background mode and /tasks session history row (Nov 6)*

**[TENSION] Parallel agent workflows need better git UX at the same moment that git UX tooling is fragmented**
OpenHands v1.36.0 adds Bitbucket DC and Azure DevOps template support — these are parallel-agent-at-scale environments. Claude Code v2.1.319 improves subagent and teammate support. Both are pulling toward more parallel agent runs against the same repository. The git UX for parallel agents is not solved: `git worktree` is clunky (hence worktrunk at 11.8k stars gaining 1,800/week), merge conflicts across parallel agent branches are uncharted territory for automated tooling, and there's no standard for how agents signal "I'm done with this worktree." The ecosystem is building parallel agent capability before building the coordination substrate. This is likely fine for single-developer use, but will produce a class of hard-to-debug bugs as teams scale parallel agents without worktree lifecycle management.
*Grounded in: worktrunk v0.81.0 wt merge --branch (Oct 20); Claude Code v2.1.319 MCP background tasks; OpenHands v1.36.0 automation templates (Nov 6)*

**[BUILDER'S ANGLE] worktrunk + permissions.denyInsteadOfPrompting + MCP background tasks = a template for unattended parallel agents**
If you want to run 4 parallel Claude Code agents on 4 git worktrees with no blocking pauses: (1) `wt switch --create agent/task-N` for each agent worktree; (2) set `permissions.denyInsteadOfPrompting: true` in each agent's settings so unknown tool calls don't block; (3) use MCP servers for tools the agent needs — they now run in the background without blocking the turn; (4) use `wt merge --branch agent/task-N` to merge results back without leaving your coordination worktree. That's currently application-layer work. The `/tasks "Earlier in this session"` row suggests a UI for this is coming.
