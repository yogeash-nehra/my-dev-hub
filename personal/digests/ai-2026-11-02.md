```bash

# Create a worktree and start Claude Code in it:
wt switch -c -x claude feat/my-feature

```
**Instead of:** Running `git worktree add ../my-feature feat/my-feature && cd ../my-feature && claude`, then manually deleting the worktree and branch when done — multiplied by four parallel agents.

## API & SDK Changes

### [HIGH] Message Threads (beta) — Claude Messages API
**Source:** Anthropic Platform Release Notes | **Date:** 2026-11-02 | **Link:** https://platform.claude.com/docs/en/release-notes/overview
**What changed:** A new `"thread"` parameter on `/v1/messages` enables server-side conversation state; the first request sends the full conversation with `"thread": {"type": "create"}`, and each subsequent turn sends only new messages with `"thread": {"type": "continue", "previous_message_id": "<prev_id>"}` — the API reconstructs the full context before calling the model.
**TL;DR:** Anthropic's Messages API now supports server-side conversation state in beta (`message-threads-2026-08-12` header required); turns after the first send only new messages, reducing per-turn payload size and keeping TTFT low and steady as a conversation grows — most useful in long agent loops.
**Developer signal:** The SDK thread helper (`client.beta.messages.thread(...)` in Python/TypeScript; similar in C#, Go, Java, PHP, Ruby) is the recommended path — it adds the beta header automatically, sends only new messages on each turn, and replays the full conversation in a new create request when the thread expires (`thread_not_found` 404). For manual use, send `anthropic-beta: message-threads-2026-08-12` on every request of the thread. Critical rules: `system` and `tools` go on the create request only — sending either on a continue request returns a 400 error. `model`, `thinking`, `tool_choice`, `mcp_servers`, and the top-level `cache_control` are "fixed fields" — they must be the same on every turn, or you get `thread_fingerprint_mismatch`. `cache_control` is capped at 4 breakpoints per request when using threads. Your application must maintain its own copy of the full conversation: the API does not guarantee it stored a given turn, and you find out only on the next continue request (or on a 404). Threads expire 5 minutes after the last request and are deleted ≤1 hour after last use. Not ZDR eligible, not HIPAA eligible. Does not work with Message Batches, token counting, compaction, context editing (except `clear_thinking_20251015` with `keep: "all"`), or Inference Hooks.
**Affects you if:** You build multi-turn Claude API integrations — especially long agent loops — where the growing conversation history inflates request payloads and pushes TTFT higher with each turn.
**Adoption effort:** Moderate (add beta header, restructure requests into create vs. continue, and handle 404 replay — or switch to the SDK thread helper which manages all of this)
**Primary source:** https://platform.claude.com/docs/en/build-with-claude/message-threads

## Trends & Emerging Tech

### Server-side conversation state moves into the base API layer
**Source:** Anthropic Platform Release Notes | **Date:** 2026-11-02 | **Link:** https://platform.claude.com/docs/en/build-with-claude/message-threads
**What's happening:** Message threads (launched today in beta) introduce server-managed conversation state as a primitive in the base Messages API — not as a framework feature (LangGraph checkpointers, Pydantic AI turn history) but at the `/v1/messages` level. The design is deliberately minimal: the server holds state for ≤1 hour, the client stays the source of truth, and replay on expiry is the client's responsibility (or the SDK helper's). OpenAI shipped a higher-abstraction version in the Assistants API (deprecated Aug 2026); Anthropic's version is lower-level and composes with prompt caching, streaming, and tool use. Three other major labs have explored similar ideas at varying abstraction levels.
**Why watch this:** If server-side short-term conversation state becomes a standard primitive across model APIs, the value of agent frameworks shifts upward: the low-level glue that keeps conversations alive becomes less differentiating, and framework value accrues to higher-order concerns — multi-agent orchestration, durable long-term memory, branching, structured pipelines, and observability. Watch for: (1) whether threads land in stable after beta, (2) whether other labs ship analogous base-layer primitives, and (3) how LangGraph and Pydantic AI integrate or work around the ZDR exclusion for compliance-sensitive deployments.

**[PATTERN] The platform layer is absorbing complexity from the framework layer**
Today's message threads beta is the third major piece of conversation-management infrastructure Anthropic has moved into the base API this year (compaction-on-demand in September, context editing earlier, and now server-side thread state). Previously, developers had to implement conversation persistence in their agent framework (LangGraph checkpointers, Pydantic AI turn history) or their own code. The beta pushes the hot path — "keep this 50-turn conversation alive without re-uploading it every turn" — into the API itself. Combined with the SDK's new typed session errors (`tool_use_limit_reached_error`, `compaction_limit_reached_error`), the picture is consistent: Anthropic is making the base API more stateful and agent-aware, so frameworks can focus on higher-level orchestration rather than low-level state management.
*Grounded in: Message Threads beta (Anthropic, Nov 2, platform.claude.com/docs); SDK v2.4.0 new session error types (Nov 2 digest); compaction feature referenced in prior digests*

**[OPEN QUESTION] Will the 5-minute idle expiry be a production friction point for "overnight agent" use cases?**
Message threads expire if the agent goes silent for more than 5 minutes — waiting for a human review step, waiting on a slow external tool call, or paused between tasks. The SDK helper auto-replays the full conversation on a `thread_not_found` 404, but that means a 50-turn conversation with a multi-hundred-KB system prompt gets re-uploaded whenever there's a longer pause. Whether this outweighs the benefit depends on how often real agent workflows pause for >5 minutes. Long-running overnight workflows (batch refactoring, slow CI generation, code search across large codebases) may see replay costs that erode the thread's savings. Anthropic hasn't published latency or idle-time distribution data for production agent conversations, and the docs don't address this tradeoff directly. The 1-hour deletion window is generous; the 5-minute idle reset is the binding constraint.
*Grounded in: Message Threads beta — 5-minute idle expiry, thread_not_found 404 on expiry, SDK replay behavior (platform.claude.com/docs/en/build-with-claude/message-threads)*

**[TENSION] Server-side conversation state vs. zero data retention — a new compliance/performance tradeoff**
Message threads are explicitly not ZDR eligible: the thread contents (conversation, system prompt, tools) are held in memory encrypted under a server-managed key for up to 1 hour. Organizations with ZDR enabled cannot use threads at all. HIPAA-covered organizations are also excluded. This creates a compliance/performance tradeoff that didn't exist before: teams in regulated industries that enabled ZDR to satisfy data-handling requirements now face a choice between "lower-latency long-running agents" and "ZDR compliance." As agentic AI expands into regulated verticals (healthcare, finance, legal), this tension will repeat with every new server-side state feature. There is no current ZDR-compatible stateful conversation primitive, and it's unclear whether one is architecturally possible given how ZDR works.
*Grounded in: Message Threads beta — ZDR: not eligible, HIPAA: not eligible (platform.claude.com/docs/en/build-with-claude/message-threads#data-retention)*

**[IF THIS CONTINUES] If every major API adds base-layer conversation state, agent framework differentiation shifts upward**
Today's message threads follow OpenAI's (deprecated Aug 2026) Assistants threads and are concurrent with xAI Grok session IDs. If by 2027 every major model API has a short-term server-side conversation primitive, the ground shifts under agent frameworks: the glue code that keeps conversations alive becomes a solved problem at the platform layer, and framework value accrues to higher-order concerns — multi-agent orchestration, durable long-term memory, conversation branching and forking, structured output pipelines, and observability. LangGraph's graph-centric stateful execution model and Pydantic AI's typed agent contracts are the kinds of differentiators that remain compelling even when the API handles short-term state. The interesting question is whether frameworks will integrate natively with these API primitives (faster, cheaper hot path) or build their own wrappers on top (portable across providers).
*Grounded in: Message Threads beta (Anthropic, Nov 2); OpenAI Assistants API shutdown (Aug 2026, referenced in prior digest); prior xAI changelog entries*
