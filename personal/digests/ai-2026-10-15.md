### casey/just — a sane command runner that replaces Makefile sprawl with a clean, cross-platform Justfile

**Link:** github.com/casey/just | **Stars:** ~35k | **Language:** Rust | **License:** CC0-1.0
**The problem:** `make` wasn't designed as a command runner, and every project ends up with a Makefile full of phony targets, fragile shell quoting, and silent failures that only break on CI. `npm run`, `cargo xtask`, and ad-hoc shell scripts all paper over the same gap differently.
**Why it's today's pick:** With Anthropic's OTel export and Managed Agents scheduled deployments both shipping today, teams are adding more automation scripts to their AI stacks. `just` is the right tool for documenting and running those — it gives you a single `justfile` at repo root, clean argument passing, cross-platform compatibility (no `make` on Windows), and comments that show in `just --list`. If you maintain a Claude Code hook setup, a `justfile` is the cleanest way to document all the `claude` invocations, env-var combos, and build steps alongside your code.
**Try it in 60 seconds:**
```bash
# Install (macOS, Linux, or WSL)
cargo install just
# or: brew install just / apt install just / scoop install just

# In your project, create a justfile:
cat > justfile << 'EOF'
# Run tests with verbose output
test:
    cargo test -- --nocapture

# Format + lint
check:
    cargo fmt --check && cargo clippy

# Build and push Docker image
release tag:
    docker build -t myapp:{{tag}} . && docker push myapp:{{tag}}
EOF

# See all available recipes with descriptions
just --list

# Run a recipe
just test
```
**Instead of:** Maintaining a Makefile with phony targets, a Procfile, a bunch of `npm run` scripts, or a `scripts/` directory full of undiscoverable shell files.
**Watch out for:** `just` is a *command runner*, not a build system — it has no dependency graph (no `make`-style target timestamps). If you need incremental builds, combine it with a real build tool; use `just` only for the human-facing entrypoints.

## [BREAKING] Breaking Changes

### [BREAKING] Claude Code v2.1.300 — `--sandbox` and `--no-sandbox` flags removed from `claude remote-control`; passing either exits with an error
**Source:** anthropics/claude-code GitHub Releases | **Date:** October 14, 2026 | **Link:** https://github.com/anthropics/claude-code/releases/tag/v2.1.300

**What changed:** The `--sandbox` and `--no-sandbox` flags were accepted by `claude remote-control` in prior versions as CLI pass-throughs. As of v2.1.300, passing either flag causes the command to exit with an error instead of silently ignoring or applying the value.

**TL;DR:** Claude Code v2.1.300 (Oct 14) removes the `--sandbox`/`--no-sandbox` CLI flags from `remote-control` — any automation script passing these flags will now break immediately on upgrade; migrate to `sandbox.enabled` in settings.json.

**Developer signal:** Audit any CI, shell scripts, or `Makefile`/`justfile` entries that call `claude remote-control --sandbox` or `claude remote-control --no-sandbox`. Replace them with a `settings.json` (or `.claude/settings.json`) entry: `{ "sandbox": { "enabled": true } }` or `{ "sandbox": { "enabled": false } }`. The CLI flags were redundant once settings-based configuration landed — this is a cleanup, not a behavior reversal — but scripts will fail hard on upgrade rather than silently.

**Affects you if:** You call `claude remote-control` from scripts with `--sandbox` or `--no-sandbox` flags; you maintain CI pipelines that invoke Claude Code remote-control with sandbox arguments; you have shell wrappers around `claude remote-control`.

**Adoption effort:** Quick — swap the CLI flag for a settings.json entry before upgrading to v2.1.300+.

**Primary source:** https://github.com/anthropics/claude-code/releases/tag/v2.1.300
