## Tooling

### [MEDIUM] Claude Code v2.1.328 — /code-review scope narrowed, auto mode on Bedrock/GCP/Azure, mcp_tool hook blocking, 91 bug fixes
**Source:** Claude Code Changelog | **Date:** 2026-11-19 | **Link:** https://code.claude.com/docs/en/changelog
**What changed:** v2.1.328 ships three developer-visible behavior changes alongside new features and 91 bug fixes: (1) `/code-review` on most models now reports only bugs and CLAUDE.md violations — simplification, refactor, and efficiency suggestions moved to `/simplify`; (2) auto mode is now available for Claude Opus 4.6 and Sonnet 4.6 on Amazon Bedrock, Google Cloud's Agent Platform, Microsoft Foundry, and the Claude apps gateway; (3) `mcp_tool` hooks accept `"onFailure": "block"`, matching the behavior of command and HTTP hooks.
**TL;DR:** Claude Code v2.1.328's most developer-impactful change: `/code-review` now scopes to correctness-only; use `/simplify` for cleanup. Auto mode lands on the three major cloud provider gateways for Opus 4.6 and Sonnet 4.6. 91 bug fixes including a zsh `=` word parsing failure and automatic compaction now rebuilding the system prompt properly.
**Developer signal:** (1) **`/code-review` scope change** — if you run `/code-review` in a CI step, pre-commit hook, or automated pipeline and expect it to flag style, simplification, or efficiency issues, that output is now gone. Run `/simplify` instead, or use both in sequence. This is not an API break but it *is* a workflow break for teams that relied on `/code-review` for comprehensive code quality enforcement. Update your review scripts today. (2) **Auto mode expansion** — if you deploy Claude Code on Bedrock, GCP Agent Platform, Microsoft Foundry, or the apps gateway and want your users to get auto mode without setting a permission flag, it's now the default for interactive sessions with no mode configured. If you explicitly want to prevent auto mode, set `disableAutoMode` in your session config. (3) **mcp_tool hook blocking** — if you author MCP tool hooks that need to block action on failure (e.g. a validation hook that must succeed before a write), add `"onFailure": "block"` to the hook definition. Previously only command and HTTP hooks supported this; now all three hook types are consistent. (4) **Code Mode behavior**: UserPromptSubmit hooks no longer fire on script output — if you used these hooks to redact or transform Code Mode script results, migrate to PostToolUse with `updatedToolOutput` instead.
**Affects you if:** You use `/code-review` in automated workflows; you deploy Claude Code on Bedrock/GCP/Azure/apps gateway; you author MCP tool hooks that need to block on failure; you use UserPromptSubmit hooks to transform Code Mode output.
**Adoption effort:** Moderate (audit `/code-review` usage in CI/hooks; check Code Mode UserPromptSubmit hooks; set `disableAutoMode` if needed).
**Primary source:** https://code.claude.com/docs/en/changelog (v2.1.328, Nov 19 entry — fetched directly)

**[OPEN QUESTION] Does a /code-review that only reports bugs actually serve developers better?**
The v2.1.328 change splits `/code-review` (correctness only) from `/simplify` (cleanup). The design intent is clear: separate "is this code wrong" from "could this code be better." But in practice, teams running automated review in CI often want both signals in one pass. The question is whether the split improves signal clarity (fewer false positives from style recommendations conflated with bug reports) or increases friction (now two commands to get the full picture). Early user reactions in the community weren't visible in this scan. Watch for adjustments to the split in future versions — or for a flag to re-enable the combined output.
*Grounded in: Claude Code v2.1.328 /code-review scope change (this digest)*
