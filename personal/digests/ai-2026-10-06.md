## 🏆 Repo of the Day

### NVIDIA/OpenShell — kernel-level, policy-enforced runtime for autonomous AI agents
**Link:** github.com/NVIDIA/OpenShell | **Stars:** ~15,100 (↑ ~5,915 this week) | **Language:** Rust | **License:** Apache 2.0

**The problem:** Running autonomous agents with real system access (file reads, package installs, API calls, credential use) without a kernel-level trust boundary means you're relying entirely on the LLM's judgment and application-layer guards — neither of which is auditable or enforceable.

**Why it's today's pick:** OpenShell is NVIDIA's open-source answer to the sandbox question: it instruments the kernel via Landlock filesystem restrictions and seccomp system-call filtering to enforce a policy on every file access, system call, and network connection an agent makes. Released as v0.1.0 (Sep 25) with a stable release cadence, v0.1.2 (Sep 28) ships Supervisor network fixes and Homebrew installation support. It's gaining 5,915 stars this week — a sustained climb driven by the release rather than a single HN spike. The policy framework includes explicit MCP revision allowlists, which means you can pin exactly which MCP server versions an agent is allowed to call — a unique, directly MCP-aware security primitive no other agent runtime currently ships.

**Try it in 60 seconds:**
```bash
curl -LsSf https://raw.githubusercontent.com/NVIDIA/OpenShell/main/install.sh | sh
openshell sandbox create --name demo
openshell sandbox run --name demo -- python agent.py
```
**Instead of:** Relying on application-layer sandboxes (E2B, Daytona) for isolation, or using Docker alone (which doesn't enforce policy at the syscall level).
**Watch out for:** v0.1.x — the API surface is stabilizing and the sandbox architecture (RFC 0012) is still being implemented across backends; verify Kubernetes Helm chart compatibility with your cluster version before using in production. Windows requires WSL 2.

### [BREAKING] Google Antigravity `antigravity-preview-05-2026` shut down — migration deadline passed Oct 5
**Source:** Google AI for Developers (ai.google.dev) | **Date:** October 5, 2026 (shutdown confirmed) | **Link:** https://ai.google.dev/gemini-api/docs/changelog

**What changed:** The May 2026 preview build of Google's Antigravity agent runtime (`antigravity-preview-05-2026`) was retired on October 5, 2026, as scheduled. Any application passing this agent ID to the Antigravity API now receives errors. The successor is `antigravity-preview-09-2026`, which is a breaking API revision: built-in tool parameter names changed from snake_case to PascalCase (e.g., `file_path` → `FilePath`), and line-range file-edit parameters have a different structure.

**TL;DR:** The May 2026 Antigravity preview is dead as of Oct 5; update your agent ID to `antigravity-preview-09-2026` and rename snake_case built-in tool params to PascalCase or your integration is broken right now.

**Developer signal:** Three actions required depending on how you use Antigravity. (1) **All users:** update the agent ID in your API call or config from `antigravity-preview-05-2026` to `antigravity-preview-09-2026`. (2) **If you use local tool integrations or parse `function_call` responses:** rename built-in tool parameter keys from snake_case to PascalCase throughout your tool-handler code (e.g., `file_path` → `FilePath`, `line_start` → `LineStart`) and adapt any line-range file-edit parsing to the new structure. Run your tool handler test suite before deploying. (3) **If you're a remote output-only client** (you send prompts and read text responses, no function call parsing): updating the agent ID is sufficient — no code changes to your tool handlers are needed. This is not recoverable without migration; the May preview does not fall back or warn, it simply errors.

**Affects you if:** You make direct calls to the Antigravity API (Gemini API function-calling integration); you have automation workflows or CLI scripts that specify the May preview agent ID; you have any code that parses Antigravity `function_call` responses with built-in tool names.

**Adoption effort:** Moderate — agent ID update is trivial; built-in tool parameter renames require auditing every tool handler and field reference in your codebase.

**Primary source:** https://ai.google.dev/gemini-api/docs/changelog

**Why watch this:** This is the transition from "agent security as an afterthought" to "agent security as a first-class engineering requirement." For teams deploying production agents: start treating agent runtimes the same way you treat web application inputs — assume adversarial conditions, enforce least-privilege at the kernel level where possible (OpenShell), and keep all SDK/runtime dependencies at their latest security patch.

**[PATTERN] TOCTOU and concurrent-access bugs are migrating from OS security to agent security**
The Claude Code v2.1.292 notebook/PDF link-swap vulnerability is a textbook TOCTOU (time-of-check, time-of-use) bug: a file is approved for read at time T, then replaced by a different file before the read happens at T+1, returning content outside approved scope. This is one of the oldest vulnerability classes in operating system security — and it's now showing up as a rated advisory in an AI agent runtime. The pydantic-ai v2.53.0 vulnerability (prior digest, GHSA-6fqq-452j-qhrp) was also a concurrent-access bug (semaphore slot held across async task boundaries). Two independent security disclosures in one week, both in the async/concurrent-access class, both from agent runtimes. This is a pattern: agent code executes across async boundaries and time gaps that classic security reviews don't check for. Audit your agent's tool-execution flows for time gaps between permission grant and resource access.
*Grounded in: Claude Code v2.1.292 notebook/PDF TOCTOU fix (this digest); pydantic-ai v2.53.0 GHSA-6fqq-452j-qhrp (Oct 3 digest)*

**[TENSION] Kernel-level sandboxing (OpenShell) vs. application-layer sandboxing (E2B, Daytona) — complementary or converging?**
NVIDIA OpenShell enforces policy at the kernel level (Landlock + seccomp), while E2B and Daytona enforce at the container/process level. These are not substitutes: kernel enforcement cannot be bypassed from within the process; container enforcement can be bypassed if the agent finds a container escape. But kernel enforcement requires the agent to run on a specific kernel (Linux with Landlock support, or WSL2 on Windows) — you can't use it in a hosted sandbox environment where you don't control the host. The tension: cloud-hosted sandboxes (E2B's API model) trade security depth for operational simplicity; kernel-level sandboxes (OpenShell) give you real enforcement but require you to manage the host. This is the classic "managed vs. self-hosted" tradeoff reappearing in agent security. For production: cloud sandboxes are likely to add kernel isolation options (E2B runs on Linux hosts — Landlock is technically available); the question is when, not whether.
*Grounded in: NVIDIA/OpenShell v0.1.2 (this digest); E2B v2.52.1 CVE patches (this digest)*

**[OPEN QUESTION] Does MCP revision pinning in OpenShell's policy framework become an industry security standard?**
OpenShell's policy framework includes MCP revision allowlists — you can declare `server@revision` strings and have the kernel refuse any MCP server version that doesn't match. No other agent runtime or MCP client currently ships this level of server-version control. If an agent's behavior depends on a specific MCP server version (prompt injection defenses, API surface, tool semantics), unauthorized server upgrades are a real attack vector — the runtime should enforce the version contract, not rely on the server operator to maintain it. Open question: will MCP clients (Claude Code, Cline, Cursor) add client-side MCP server pinning as a configuration option, making the allowlist pattern available without needing OpenShell? Or does this remain a kernel-layer-only control? The MCP spec (as of July 2026 stable release) has no version-pinning semantics — this is an OpenShell extension, not a protocol feature.
