## [BREAKING] Breaking Changes

### [BREAKING] OpenAI Assistants API Hard Shutdown — August 26, 2026
**Source:** OpenAI Developer Platform | **Date:** August 26, 2026 | **Link:** https://developers.openai.com/api/docs/deprecations
**What changed:** The Assistants API endpoints (`/v1/assistants`, `/v1/threads`, `/v1/runs`, `/v1/vector_stores`) return hard errors as of today, one year after the original deprecation notice. Thread data is being deleted. No automated migration tool exists.
**TL;DR:** The OpenAI Assistants API is permanently shut down as of August 26, 2026 — every call to its endpoints returns an error immediately, with no grace period and no fallback mode.
**Developer signal:** If any production code still calls `/v1/assistants`, `/v1/threads`, or `/v1/runs`, it is broken right now. The replacement is the **Responses API** (`POST /v1/responses`) for generation and the **Conversations API** for stateful multi-turn threads. The migration is not drop-in: there is no `previous_thread_id` equivalent — you must rebuild conversation state explicitly using either `previous_response_id` chaining (simple cases), manual input item replay (for full context control), or the Conversations API (for persistent threads). Thread data is not exportable after deletion; assistant definitions must be rebuilt manually as system prompts or Responses API calls. If you relied on Assistants for vector store retrieval, you'll need to replicate that with file_search or a self-managed embedding + retrieval layer. OpenAI's official migration guide is at developers.openai.com/api/docs/assistants/migration — read it in full before writing any replacement code.
**Affects you if:** Any service in production calls `/v1/assistants`, `/v1/threads`, `/v1/threads/{id}/runs`, `/v1/threads/{id}/messages`, or `/v1/vector_stores` on the OpenAI API.
**Adoption effort:** Significant — full rewrite of assistant creation, thread management, and run orchestration; no automated migration; thread data not recoverable after deletion.
**Primary source:** https://community.openai.com/t/assistants-api-beta-deprecation-august-26-2026-sunset/1354666

## Tooling

### [HIGH] vLLM v0.28.0 — Kimi-K3 Optimization, Disk KV Cache, Three Breaking Changes
**Source:** vllm-project/vllm GitHub Releases | **Date:** August 26, 2026 | **Link:** https://github.com/vllm-project/vllm/releases/tag/v0.28.0
**What changed:** 584 commits from 270 contributors (76 new) bring Kimi-K3 Decode Context Parallel support with fused FlashKDA kernels, DeepSeek V4 sparse MLA end-to-end (decode, MTP, and DSpark speculative decoding), tiered KV cache with disk offloading, and Model Runner V2 maturation. Three breaking API changes ship simultaneously.
**TL;DR:** vLLM v0.28.0 is a major release with first-class Kimi-K3 and DeepSeek V4 optimizations, disk-backed KV cache offloading, and three hard breaking changes that require a migration audit before upgrading any production deployment.
**Developer signal:** Before upgrading, audit your deployment for three breaking changes: (1) **bitsandbytes is now an out-of-tree plugin** — if you use bitsandbytes quantization, install `vllm[bitsandbytes]` separately; the base package no longer includes it. (2) **Transformers dependency bumped to 5.15.0** — if your environment pins an older Transformers version, update it before upgrading vLLM. (3) **`calculate_kv_scales` and `override_attention_dtype` parameters are removed** — replace with the current dtype configuration documented in v0.28.0 release notes. Additionally, the default `max_num_batched_tokens` has changed from 8192 to **16384** — this increases memory usage at a given batch; if you were at the edge of GPU memory, you may need to explicitly set `--max-num-batched-tokens 8192` to preserve prior behavior. The Blackwell CUDA graph capture default is also now 1024. For Kimi-K3 users, the new Decode Context Parallel support with fused FlashKDA kernels brings significant throughput improvements; enable with the Kimi-K3 configuration docs. For Apple Silicon deployments, Mamba-2 Metal GPU support ships in parallel via llama.cpp (see Quick Hits). New model support added: Muse Glimmer, Ling 3.0 Flash (BF16/MTP/FP8), Dots3 NOTE (multimodal), Interns2mobius.
**Affects you if:** You run vLLM in production with bitsandbytes quantization; you have `calculate_kv_scales` or `override_attention_dtype` in your vLLM config; you run Kimi-K3 or DeepSeek V4 inference and want better performance; you are at the edge of GPU memory and rely on the default batch token count.
**Adoption effort:** Moderate — breaking changes require explicit migration steps, but each is mechanical (install plugin, update package, remove deprecated params, verify memory).
**Primary source:** https://github.com/vllm-project/vllm/releases/tag/v0.28.0

## Trends & Emerging Tech

### The Inference Frameworks Are Now Managing Three Parallel Complexity Fronts
**Source:** vllm-project/vllm GitHub Releases; ggml-org/llama.cpp GitHub Releases; ollama/ollama GitHub Releases | **Date:** August 26, 2026
**What's happening:** Three inference framework releases landing on the same day (vLLM v0.28.0, Ollama v0.33.0 stable, llama.cpp b10632/b10635) each independently add support for overlapping models (DeepSeek V4, Kimi-K3, Mamba-2 hybrids) while also extending into adjacent hardware targets (Vulkan on consumer GPUs, ROCm on AMD, MLX on Apple Silicon, RDMA on Mac clusters). The plugin extraction of bitsandbytes in vLLM v0.28.0 is notable: inference frameworks are starting to draw explicit boundaries between what they natively support and what becomes a third-party plugin — a maturity signal, but one that creates installation complexity for users with non-standard quantization stacks.
**Why watch this:** Three tracks are converging in inference tooling: (1) **MoE model support** has become table stakes — every framework now has first-class DeepSeek V4 and Kimi-K3 support; (2) **Hardware fragmentation is widening** — a single model can now run on CUDA 13, ROCm, Vulkan, Metal, MLX, RDMA, and CPU in the same week's releases; (3) **Distribution discipline is tightening** — semantic versioning (llama.cpp v0.3.0 yesterday), plugin extraction (vLLM bitsandbytes today), stable RC promotion (Ollama v0.33.0 today). This convergence means the choices between frameworks are increasingly about deployment target and plugin ecosystem rather than raw capability coverage. Expect the next differentiation battleground to be KV cache management (tiered/disk offloading shipped in vLLM v0.28.0 today) and quantization diversity.

**[TENSION] vLLM's bitsandbytes plugin extraction signals the start of inference framework API discipline — but breaks existing operator practices**
vLLM v0.28.0 extracts bitsandbytes into an out-of-tree plugin requiring explicit `vllm[bitsandbytes]` installation. This is the right engineering call: quantization libraries have divergent hardware compatibility, divergent update cadences, and diverse fallback behaviors that don't belong in the core library. But it is also a signal that the "batteries-included inference framework" phase is ending. Production deployments that pulled a single Docker image and got everything are now responsible for assembling a plugin stack and managing its compatibility with the base framework version. This mirrors what happened to ML pipelines in the 2019–2021 period — unified libraries (TensorFlow 1.x with everything) fractured into composable pieces (PyTorch + Lightning + Triton + HuggingFace) — and created a taxonomy of "core vs. plugin" that required tooling to manage. Watch whether vLLM's plugin architecture becomes formalized (e.g., a `vllm.plugins` registry), whether other frameworks (llama.cpp's backend system, Ollama's gateway model) follow the same pattern, and whether this opens space for plugin-centric deployment tooling analogous to how pip extras work at the ML platform level.

**[PATTERN] Disk-backed KV cache in vLLM v0.28.0 is the first production-ready tier-3 KV cache — this changes the memory capacity math for reasoning models**
vLLM v0.28.0 ships tiered KV cache with disk offloading: GPU VRAM → CPU RAM → disk. For reasoning models like DeepSeek V4 (which generates long chain-of-thought sequences) and Kimi-K3 (also in v0.28.0), KV cache is the primary memory constraint at large context lengths — not the model weights. With disk offloading, a server with 40 GB GPU VRAM, 256 GB CPU RAM, and a fast NVMe can now serve requests with effective KV capacity well beyond what VRAM alone allows, at the cost of disk I/O latency on cache misses. The practical implication: serving very-long-context or very-long-reasoning-chain requests is no longer strictly bounded by GPU VRAM. The open question is what cache hit rates look like for typical reasoning workloads — if tokens are always novel (as in one-shot reasoning tasks), disk offloading only adds latency. But for applications with repeated prefixes or KV prefix sharing across sessions, the disk tier is immediately useful. This is the infrastructure precondition for affordable large-context deployments; watch whether vLLM adds explicit hit-rate telemetry for the disk tier in v0.29.x.
*Grounded in: vLLM v0.28.0 tiered KV cache with disk offloading (this digest, Tooling); vLLM v0.28.0 Kimi-K3 Decode Context Parallel support (this digest, Tooling)*
