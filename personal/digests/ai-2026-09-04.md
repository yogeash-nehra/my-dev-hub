### evilmartians/lefthook — the git hooks manager that doesn't require a runtime in your project
**Link:** github.com/evilmartians/lefthook | **Stars:** ~8.8k | **Language:** Go | **License:** MIT
**The problem:** Husky requires Node.js in every project (including non-JS ones), pre-commit requires Python, and hand-rolled `.git/hooks/` shell scripts don't survive a fresh clone — so most teams skip quality gates entirely or fight their hook manager more than they write code.
**Why it's today's pick:** At 8.8k stars, lefthook remains under the radar despite being the cleanest answer to "fast, language-agnostic git hooks with no runtime dependency." Today's llama.cpp v0.4.0 story (three breaking changes shipped simultaneously) is a reminder that enforcing pre-commit checks pays off at scale — and lefthook is the fastest path to doing so across Python, Go, Rust, and JS projects from a single binary. Runs hooks in parallel by default, respects staged-files filtering, and installs as a self-contained Go binary with no external deps.
**Try it in 60 seconds:**
```bash
# Install (macOS, Linux, or via go install — no runtime required)
curl -1sLf "https://dl.lefthook.com/latest/install.sh" | bash
# macOS: brew install lefthook
# go: go install github.com/evilmartians/lefthook@latest

# Init in any repo
lefthook install

# Example lefthook.yml — runs lint and format-check in parallel before every commit
cat > lefthook.yml << 'EOF'
pre-commit:
  parallel: true
  commands:
    lint:
      run: ./scripts/lint.sh {staged_files}
    fmt:
      run: ./scripts/fmt_check.sh {staged_files}
EOF
# Lefthook reads {staged_files} and passes only modified files to each command
```
**Instead of:** Husky (Node.js only, sequential by default), pre-commit (Python-only runner), custom `.git/hooks/` scripts that vanish on `git clone`.
**Watch out for:** Windows support works but requires Git for Windows or WSL2 — native PowerShell hook execution is second-class. If your hooks have inter-dependencies, configure explicit `groups` to control parallel execution order.

## [BREAKING] Breaking Changes

### llama.cpp v0.4.0 — Three Breaking Changes in the Stable Major Release
**Primary source:** https://github.com/ggml-org/llama.cpp/releases/tag/v0.4.0

**1. Session/state format version bumped**
Saved KV cache states from v0.3.x are **not forward-compatible** with v0.4.0. If you use `llama-server --save-state` / `--restore-state` or the `llama_state_save` / `llama_state_load` C API to persist sessions between runs, you must regenerate all saved states after upgrading.
**Affects you if:** You run `llama-server` with persistent sessions (chatbots with saved conversation history, prefill caching for long system prompts).

**2. `--tensor-read-lazy` CLI flag renamed to `--lazy-mode` (shorthand: `-lzm`)**
Introduced first in nightly build b10700 (covered in a prior digest) — v0.4.0 codifies it as the stable API surface. Scripts, service definitions, or config files using `--tensor-read-lazy` will silently fail to enable lazy loading (unknown flags may be ignored or cause startup failure depending on your invocation).
**Affects you if:** You start `llama-server` or `llama-cli` with `--tensor-read-lazy` in any script, systemd unit, or Docker CMD.

**3. Non-fused GDN/LID operations disabled by default**
Affects models using Gated DeltaNet (GDN) or Leaky Integrate-and-Decay (LID) layers — primarily the new Qwen3.8-Flash-Next qwen4exp architecture and models built on it. Non-fused ops remain available via a compile-time flag; they are no longer the default because the fused path is now stable. This only affects users who build llama.cpp from source with explicit non-fused op flags.
**Affects you if:** You build llama.cpp from source with non-fused GDN/LID explicitly enabled for qwen4exp-architecture models.

## Tooling

### [HIGH] llama.cpp v0.4.0 — First v0.4.x Stable: Qwen3.8-Flash-Next, ggml v0.23.0, Sparse Flash Attention
**Source:** GitHub Releases | **Date:** September 4, 2026 | **Link:** https://github.com/ggml-org/llama.cpp/releases/tag/v0.4.0
**What changed:** v0.4.0 is llama.cpp's second stable versioned release (following v0.3.0 on August 22) and the first v0.4.x series. New model support: Qwen3.8-Flash-Next (qwen4exp architecture — 125B total, 6B activated per token, Alibaba's August 26 sparse MoE preview) and NVIDIA Nemotron-3-Puzzle-75B-A9B. Core changes: ggml updated v0.22.0 → v0.23.0 (sparse flash attention operators, async RPC APIs, Apple RDMA transport for distributed inference); lazy tensor reading (`--lazy-mode` / `llama_lazy_mode`) to reduce RAM peaks during model loading; sparse flash attention for DeepSeek-V4, GLM, and Qwen4exp architectures; KV cache N-gram history lookup; per-slot server context limits (`--kv-unified-per-slot`); video input via `--video-*` CLI flags; MCP tool policy replaces previous MCP override mechanism; new `mtmd_tokenize_from_parts()` for multimodal tokenization. Three breaking changes — see [BREAKING] section above.
**TL;DR:** llama.cpp v0.4.0 adds Qwen3.8-Flash-Next (125B sparse MoE, 6B activated) and Nemotron-3-Puzzle-75B-A9B support with sparse flash attention, upgrades ggml to v0.23.0, and ships three breaking changes affecting session persistence, CLI flags, and GDN/LID build defaults.
**Developer signal:** Four things to do: (1) Audit any invocation scripts for `--tensor-read-lazy` and replace with `--lazy-mode`. (2) If you use session persistence (save/restore state), regenerate saved sessions after upgrading — old states will be rejected. (3) Enable `--lazy-mode` on large models if you aren't already — lazy tensor loading defers shard reads until needed, which meaningfully reduces peak RAM during model load for 70B+ models and can prevent OOM on memory-constrained systems. (4) To run Qwen3.8-Flash-Next locally: `ollama pull qwen3.8-flash-next` won't work yet (Ollama hasn't shipped an update for it) — use the llama.cpp binary directly with a GGUF from the QwenLM org on Hugging Face and pass the appropriate context limit (`--ctx-size 131072` for the 128K variant). Apple Silicon users benefit from the new RDMA transport for multi-device distributed inference via `llama-server` RPC.
**Affects you if:** You run llama-server with persistent sessions; you have scripts using `--tensor-read-lazy`; you want to run Qwen3.8-Flash-Next or Nemotron-3-Puzzle locally; you build llama.cpp from source with non-default GDN/LID flags; you use Apple Silicon with RPC for distributed inference.
**Adoption effort:** Moderate — address three breaking changes before upgrading; regenerate saved states; update CLI invocations.
**Primary source:** https://github.com/ggml-org/llama.cpp/releases/tag/v0.4.0

### OpenAI Extends Reasoning Effort to Five Levels — More Granular Than the Three-Tier Norm
**Source:** OpenAI | **Date:** September 3, 2026 | **Link:** https://openai.com/index/gpt-6-astra/
**What's happening:** GPT-6 Astra's `reasoning.effort` supports five values: `low`, `medium`, `high`, `xhigh`, and `max` — expanding on the three-value designs from Anthropic (Fable 5.1: `low`/`medium`/`high`) and Google (Gemini 3.8 Flash: `LOW`/`MEDIUM`/`HIGH`). The addition of `xhigh` and `max` as distinct tiers reflects that certain complex tasks — dense legal document reasoning, multi-step scientific analysis — benefit from reasoning depth beyond what `high` provides.
**Why watch this:** If developers report meaningful quality differences at `xhigh` and `max` vs. `high`, expect Anthropic and Google to extend their enums within two to three model cycles. This also creates an immediate cross-lab wiring problem: frameworks like LangChain, LlamaIndex, and LiteLLM that map a single `effort` parameter to each provider's enum will need to add a conditional for `xhigh`/`max` (currently these values have no Anthropic/Google equivalent). Watch whether any agentic framework ships a "best available" effort mapping in the next few weeks.
