### dagger/dagger — automation engine that runs the same way locally, in CI, and from an agent

**Link:** github.com/dagger/dagger | **Stars:** ~16.6k (↑ actively growing) | **Language:** Go | **License:** Apache-2.0
**The problem:** CI pipelines written in YAML break silently, can't be run locally, and require a CI server just to test a change — leaving developers unable to iterate fast and agents unable to run the same pipeline that CI runs.
**Why it's today's pick:** OpenHands v1.35.0 launched Automations with webhook event sources today — the beginning of "agent as pipeline stage." Dagger is the matching piece on the pipeline side: programmable, containerized pipelines written in Go, Python, TypeScript, or Rust that run identically from your terminal, inside an agent, or in GitHub Actions. It had a fresh `v1.0.0-beta.24` release this morning (Nov 3) that cleans up telemetry noise by hiding internal cache volume mounts from users. At 50+ beta releases in the v1 cycle, Dagger is maturing toward GA and remains dramatically underused relative to its capability.
**Try it in 60 seconds:**
```bash
# Install the Dagger CLI
curl -fsSL https://dl.dagger.io/dagger/install.sh | DAGGER_VERSION=1.0.0 BIN_DIR=/usr/local/bin sh
# Run a minimal pipeline module
dagger call -m github.com/shykes/daggerverse/hello@main hello
```
**Instead of:** 400-line GitHub Actions YAML that can only be tested by pushing a commit and waiting 5 minutes; or manually running each step locally and praying CI behaves the same way.
**Watch out for:** Still in beta (v1.0.0-beta.24 today). Some SDK APIs are still stabilizing. The Go SDK is the most mature; Python and TypeScript are further behind. Cold-start times on first container pull can be slow on a fresh machine.

### [HIGH] Claude Code v2.1.317 — Agent SDK hooks, security prompts, OTel enrichment, 70+ fixes
**Source:** GitHub | **Date:** 2026-11-03 | **Link:** https://github.com/anthropics/claude-code/releases/tag/v2.1.317
**What changed:** 70+ additions, fixes, and behavioral changes: `onFailure: "block"` added to Agent SDK hook callbacks (fail-closed policy); a prompt added before web/shell tools send the session's account email to the network; `anthropic.plan`, `anthropic.seat_type`, `anthropic.provider`, `anthropic.custom_base_url` added to OTel metrics/events/spans; a new cost-report endpoint (`GET /v1/organizations/analytics/cost`) on Claude apps gateways with daily IdP group records; `CLAUDE_CODE_DISABLE_NESTED_SESSION_ID=1` env var for self-hosted runners; the Read tool "file unchanged" stub removed; SendMessage delivers to running background agents sooner; subagents now use their own model's default effort level; 50+ bug fixes across cloud, Windows, VSCode, MCP, compaction, and OTel proxy handling.
**TL;DR:** Claude Code v2.1.317 is a 70+-change production-hardening release: fail-closed hook semantics, pre-send email security, OTel enrichment with plan/seat metadata, a gateway cost-report admin endpoint, and over 50 bug fixes spanning compaction, Windows path limits, VSCode parallel tool calls, and OTel proxy timeouts.
**Developer signal:**
1. **Hooks (`onFailure: "block"`):** If you use Agent SDK hook callbacks, a callback that crashes or returns failure now blocks the action instead of silently proceeding. Update your hook error handling — transient failures (network timeouts, rate limits) will now surface as blocked actions. Decide per hook: should a logging hook failure block a write? Set accordingly.
2. **Email security prompt:** Web and shell tools now prompt before sending your account email to the network. For unattended agents in cloud/scheduled contexts, audit which tool calls might trigger this — a hanging prompt will stall an automated run.
3. **Nested session ID:** `claude -p` run inside a session now shares that session's ID and transcript by default. For self-hosted runners that relied on separate IDs, set `CLAUDE_CODE_DISABLE_NESTED_SESSION_ID=1`.
4. **Cost reporting:** The new `GET /v1/organizations/analytics/cost` endpoint on Claude apps gateways returns spend broken down by total, developer, day, or IdP group for a date range. If you run a gateway with `admin:` configured and `admin.identity_retention_days` set, this is usable today for cost dashboards and chargeback.
5. **Read tool change:** The "file unchanged since your last Read" stub is removed. Agents that re-read unchanged files will receive full content every time — a capability improvement, but slightly more context usage for agents doing frequent re-reads.
**Affects you if:** You use the Claude Code Agent SDK with hooks; run agents in unattended/headless or scheduled mode; manage a Claude apps gateway; run self-hosted runner sessions; use OTel to monitor agent activity.
**Adoption effort:** Moderate (review hook `onFailure` semantics for each hook; audit unattended tool calls that might trigger the email prompt; update nested session behavior on self-hosted runners if needed)
**Primary source:** https://github.com/anthropics/claude-code/releases/tag/v2.1.317

## Trends & Emerging Tech

### Agents as pipeline stages: event-driven automation becomes a first-class pattern
**Source:** OpenHands v1.35.0, Anthropic message threads beta (Nov 2) | **Date:** 2026-11-03 | **Link:** https://github.com/OpenHands/OpenHands/releases/tag/v1.35.0
**What's happening:** OpenHands Automations now accept webhook event sources, meaning you can trigger an OpenHands agent from a GitHub PR event, a Bitbucket build, or any HTTP webhook. Combined with yesterday's Anthropic message threads beta (server-side conversation state for up to 1 hour), the primitives are: event fires → agent wakes with persistent context → performs multi-step task → commits result. This is different from "chat-driven" agent workflows; it's a first-class pipeline integration. Claude Code v2.1.317's `onFailure: "block"` hooks and new gateway cost-report endpoint add the policy enforcement and observability layers.
**Why watch this:** As webhook event sources and server-side conversation state become standard primitives, agents can be inserted into CI/CD workflows with the same reliability expectations as a build step. The unanswered question is observability: who monitors the agent step, what are the SLA expectations, and how do you debug a failed agent run mid-pipeline? Claude Code's new OTel additions (`anthropic.plan`, `anthropic.seat_type`) and the gateway cost-report endpoint are early signals that the ecosystem is starting to answer this — but production-grade agent observability is still largely a build-it-yourself problem for now. Watch whether these primitives land in stable releases and whether other orchestration frameworks (LangGraph, Pydantic AI) ship native webhook event sources in the coming weeks.

**[PATTERN] The ecosystem is shipping production-hardening, not raw capability**
Three separate major releases today — Claude Code v2.1.317, OpenHands v1.35.0, Pydantic AI v2.65.0 — all address the same cluster of concerns: reliable agent state management, security policy enforcement, observability infrastructure, and CI/CD integration. Pydantic AI adds ConversationStore revisions and improved error handling. This is not the pattern of a capability race; it is the pattern of an ecosystem that has shipped enough capability to expose production pain points and is now closing them. The interesting question is what the next capability jump looks like after the production infrastructure catches up — and whether the two curves (capability and production-readiness) will stay synchronized this time, or whether capability will sprint ahead again before the infrastructure keeps pace.
*Grounded in: Claude Code v2.1.317 (Nov 3, GitHub); OpenHands v1.35.0 (Nov 3, GitHub); Pydantic AI v2.65.0 (Nov 2, GitHub)*

**[OPEN QUESTION] Does `onFailure: "block"` create a new class of agent reliability failures?**
Claude Code v2.1.317's `onFailure: "block"` for Agent SDK hook callbacks makes failing hooks block the action — a "fail-closed" security posture. This is the right default for policy enforcement, but it creates a new failure mode: a hook that crashes due to a transient issue (network timeout, rate limit, DNS failure in a cloud environment) now blocks the agent's action entirely. Teams using hooks for audit logging or access control will need to decide: is a flaky logging service a valid reason to block an agent from writing code? The answer depends on the hook's purpose (compliance enforcement vs. convenience logging), but neither the release notes nor the SDK documentation currently addresses this tradeoff. This is worth thinking through before shipping agents with strict hooks in production.
*Grounded in: Claude Code v2.1.317 — "Added `onFailure: "block"` for Agent SDK hook callbacks, so a callback that fails blocks the action instead of letting it run" (Nov 3 release notes)*

**[IF THIS CONTINUES] The "agent as pipeline stage" pattern is becoming structurally composable today**
OpenHands v1.35.0 adds webhook event sources; Anthropic added server-side message threads yesterday (1-hour lifetime); Claude Code v2.1.317 adds `onFailure: "block"` hooks and gateway cost reporting. If you assemble these primitives: a CI event fires via webhook → OpenHands agent wakes, resumes its server-side thread → runs the agentic task → hooks enforce policy (fail-closed) → cost lands in the gateway cost report → result is committed back. This is a structurally complete agent pipeline stage — not production-grade yet (observability, SLA enforcement, and retry semantics are still build-it-yourself), but all the primitives exist in released software today. At the current pace of infrastructure additions (roughly two API-layer primitives per week across the major coding agent platforms), agent pipelines with real SLA expectations look achievable within 2-3 months.
*Grounded in: OpenHands v1.35.0 webhook event sources (Nov 3); Anthropic message threads beta (Nov 2 digest); Claude Code v2.1.317 `onFailure: "block"` and `GET /v1/organizations/analytics/cost` (Nov 3)*

**[BUILDER'S ANGLE] Wire OpenHands webhook Automations to your PR-create event for automated code review as a pipeline stage**
OpenHands v1.35.0 ships webhook event sources in Automations. Claude Code v2.1.317 fixes a cluster of cloud session issues (conversation tag loss, compaction on large CLAUDE.md, MCP reconnection). These two things together mean: create an OpenHands Automation triggered by a GitHub "pull_request opened" webhook, have the agent run your code review CLAUDE.md against the diff, post its findings as a PR comment. **[TENSION] Security prompts vs. unattended agent workflows**
Claude Code v2.1.317 adds a prompt before web and shell tools send your account email to the network — a good security control for interactive use, but for unattended agents (scheduled tasks, CI pipeline stages, overnight batch work), a prompt that waits for human approval will hang indefinitely. This is the same tension as `onFailure: "block"` for hooks: security controls designed for interactive sessions create reliability failure modes in unattended deployment. The long-term resolution is probably a configuration layer that lets teams pre-approve specific tool→host combinations, but that feature isn't in v2.1.317. Teams running production agents should audit which tool calls might trigger this prompt before deploying the new version.
*Grounded in: Claude Code v2.1.317 — "Added a check that asks before a web or shell tool call sends your account email address to the network" (Nov 3 release notes)*
