### atuin-sh/atuin — encrypted, searchable, cross-machine shell history

**Link:** github.com/atuin-sh/atuin | **Stars:** ~21.5k (steady, mature) | **Language:** Rust | **License:** MIT
**The problem:** Shell history is per-machine, stored in plaintext, and unsearchable with context — `Ctrl+R` finds commands but not which directory they ran in, what exit code they returned, or when they happened.
**Why it's today's pick:** A quiet day calls for a tool that reliably solves a real friction for anyone who codes across multiple machines — including cloud sessions like Claude Code remote environments, where each session starts with empty history. Atuin replaces `~/.bash_history` / `~/.zsh_history` with a SQLite store that records each command with timestamp, duration, exit code, and working directory, then syncs it end-to-end encrypted across machines via a self-hostable server (or the free hosted sync). The structured history makes queries like "show all `git push` commands that failed, from the `my-dev-hub` directory, in the last 30 days" possible. For teams or individuals using Claude Code cloud sessions, the `atuin import` command lets you pull in historical commands from a local machine into a new session context.
**Try it in 60 seconds:**
```bash
# Install (macOS/Linux)
bash <(curl --proto '=https' --tlsv1.2 -sSf https://setup.atuin.sh)

# Re-launch your shell, then:
atuin search --exit 1          # find all commands that failed
atuin search git push          # find all git push commands with timestamps and dirs
atuin stats                    # show your most-used commands
```
**Instead of:** `Ctrl+R` (incremental search only, no context), `~/.bash_history` (plaintext, per-machine, no metadata), or fish's built-in history (richer than bash but still single-machine).
**Watch out for:** The sync server (Atuin's hosted option, `api.atuin.sh`) stores your history encrypted — Atuin cannot read it — but if that's still a concern, the self-hosted option is a single `docker run` and has been production-stable for years. The import command only imports existing history once; it doesn't retroactively enrich old entries with directory or exit-code context (those fields only populate for commands run after install).

## API & SDK Changes

### [MEDIUM] Claude Code v2.1.283 — enterprise model governance settings, `/doctor prompt-audit`, OTEL MCP tracing, Bedrock Mantle
**Source:** Anthropic (GitHub) | **Date:** September 25, 2026 | **Link:** https://github.com/anthropics/claude-code/releases/tag/v2.1.283

**What changed:** v2.1.283 adds two new managed settings for enterprise model control (`deniedModels`, `availableModelsMatch: "exact"`), a new `/doctor prompt-audit` command to audit CLAUDE.md files and skills for stale model-specific patterns, OTEL logging of MCP tool content (opt-in), Amazon Bedrock's Mantle endpoint as an upstream provider, multiple performance improvements (startup latency, first-reply latency), and approximately 25 bug fixes across SDK sessions, MCP, plugin management, Vim mode, and platform-specific paths.

**TL;DR:** A broad housekeeping release with two new enterprise governance settings (`deniedModels`, `availableModelsMatch: "exact"`), a prompt-auditing tool, OTEL MCP tracing, and significant startup/latency wins.

**Developer signal:** (1) **`deniedModels` managed setting (enterprise admins).** New in `.claude/settings.json` under `managed.deniedModels`: an array of model IDs that are blocked even if `availableModels` would otherwise allow them. Use this when you want to permit a model family broadly but block a specific version — e.g., allow all `claude-*` models but block `claude-haiku-4-5-20251001` due to a known behavior difference. This is additive to (not a replacement for) the existing `availableModels` list. (2) **`availableModelsMatch: "exact"` managed setting (enterprise admins).** Prevents new model releases from automatically entering the allowed set: when a new Anthropic model ships, it stays blocked until an admin explicitly adds its ID to `availableModels`. Previously, new models inherited access if they matched a prefix in the allowed list. For regulated environments where every model change needs a formal review cycle, this is the flag you need. (3) **`/doctor prompt-audit` (all users).** Run `/doctor prompt-audit` (or `/checkup prompt-audit`) to scan your CLAUDE.md files, skills, agents, and commands for patterns known to have been written for older Claude models — things like hardcoded version strings, deprecated tool call formats, or instructions that assume Sonnet 3.x behavior. The audit outputs a list of flagged items with explanations. If you maintain CLAUDE.md files that haven't been reviewed since the Fable/Opus 5.x era, run this first. (4) **OTEL MCP tool content (observability).** Set `OTEL_LOG_TOOL_CONTENT=1` to include MCP tool inputs and outputs in OpenTelemetry span events. Previously, OTEL spans captured tool calls but not their content. Combined with a collector like Honeycomb or Jaeger, this enables request-level tracing of what MCP tools received and returned — useful for debugging multi-step agent workflows where a downstream tool produced unexpected output. (5) **Bedrock Mantle endpoint.** `mantle` is now an upstream provider in the Claude apps gateway, pointing at Amazon Bedrock's Mantle endpoint. If your org runs Claude Code through a Bedrock-based gateway, check whether your enterprise Claude Code deployment should route via `mantle`. (6) **Performance wins.** First-reply latency improved (pattern-compile step now runs while reply streams). `claude -p` startup is faster (interactive UI no longer loaded for piped/programmatic use). First-request latency improved through reused preconnected API connections. Expect a noticeable startup-time improvement on `claude -p` workflows. (7) **`--system-prompt` now accepts both text and `-file` together.** `--system-prompt text -system-prompt-file myfile.md` is now valid — file content prepends the inline text. Previously these couldn't be combined. (8) **Windows PowerShell fix.** The Bash tool no longer allows deletion of drive roots and Windows protected system directories — a meaningful safety fix for Windows Claude Code users running agents with broad file permissions.

**Affects you if:** You manage enterprise Claude Code deployments and need hard control over which model versions are in scope; you maintain CLAUDE.md files or skills written for older Claude models; you instrument Claude Code sessions with OpenTelemetry; you use Claude Code's `-p` flag for scripted/programmatic invocations (startup speedup); you run Claude Code on Windows.

**Adoption effort:** Quick — update Claude Code; then opt-in to `OTEL_LOG_TOOL_CONTENT=1` and `availableModelsMatch: "exact"` as needed; run `/doctor prompt-audit` on existing CLAUDE.md files once after update.

**Primary source:** https://github.com/anthropics/claude-code/releases/tag/v2.1.283

### [NOTABLE] pydantic-ai v2.51.0 — OpenAI GPT-Live as first-class model, cached agent graph, context window tracking
**Source:** pydantic/pydantic-ai (GitHub) | **Date:** September 25, 2026 | **Link:** https://github.com/pydantic/pydantic-ai/releases/tag/v2.51.0

**What changed:** v2.51.0 (released the day after v2.50.0) adds `OpenAILiveModel` for real-time interactions with OpenAI's GPT-Live platform, exposes `context_window_used` on realtime sessions, caches the agent graph instead of rebuilding on every `Agent.run()` invocation, reduces `RunContext` copying overhead in capability hooks, and aligns dated `gemini-3.8-live` identifiers.

**TL;DR:** pydantic-ai adds GPT-Live realtime as a typed model alongside existing Gemini Live support, and the agent graph cache eliminates redundant rebuilds on every run — a latency win for high-frequency agent invocations.

**Developer signal:** (1) **`OpenAILiveModel` enables real-time GPT-Live sessions.** Import from `pydantic_ai.models.openai_live`. The interface mirrors the existing `GeminiLiveModel` — declare it as your agent's model and pydantic-ai handles the WebSocket lifecycle, reconnect, and typed tool binding. If you've already built a realtime agent on Gemini Live with pydantic-ai, the migration surface is a model swap and identifier change. (2) **`context_window_used` on realtime sessions.** Available on `RunResult.usage.context_window_used` for realtime sessions. The field is derived from GPT-Live's reported ratio when available, falling back to response usage data. Useful for monitoring context pressure in long-running realtime sessions where you can't trivially count tokens yourself. (3) **Agent graph cache.** If you're calling `Agent.run()` frequently in a hot path (e.g., per-request in a web server or per-event in a streaming pipeline), v2.51.0 removes the per-invocation graph rebuild. The graph is built once and cached. Benchmark the before/after on your workload — the improvement is larger for agents with complex tool graphs. (4) **Gemini Live compatibility.** `gemini-3.8-live` dated identifiers (e.g., `gemini-3.8-live-001`) are now correctly matched. Connections to Gemini 3.1 Flash Live and 3.8 Live with incompatible configurations are rejected at connection time rather than silently failing mid-session.

**Affects you if:** You use pydantic-ai to build realtime/voice agents; you call `Agent.run()` at high frequency in a server or streaming context; you use Gemini Live models with dated version identifiers.

**Adoption effort:** Quick — update pydantic-ai; use `OpenAILiveModel` for GPT-Live realtime sessions.

**Primary source:** https://github.com/pydantic/pydantic-ai/releases/tag/v2.51.0

**[OPEN QUESTION] How do you version a prompt?**
Claude Code's `/doctor prompt-audit` surfaces prompts written for older models. But "stale" is a detection, not a fix — it tells you a prompt has patterns from older models, not what the correct update is. The underlying problem is that prompt versions are not tracked the same way code versions are: there's no `git diff`, no type system, no test suite that catches behavioral regression when the underlying model changes. Tools like prompt-audit are the detection layer; what's missing is the remediation layer — a way to automatically identify the delta between "prompt written for Sonnet 4.x" and "prompt that works correctly on Fable 5.1" without manual testing on every affected agent. This is an open gap in the prompt engineering toolchain.
*Grounded in: Claude Code v2.1.283 (this digest) — `/doctor prompt-audit` command and its description as scanning for "patterns written for older models"*

**[BUILDER'S ANGLE] pydantic-ai's cached agent graph + OpenAI GPT-Live = a realtime agent with deterministic startup cost**
pydantic-ai v2.51.0 caches the agent graph so `Agent.run()` no longer rebuilds it on every invocation, and adds `OpenAILiveModel` for GPT-Live realtime sessions. Before v2.51.0, a high-frequency realtime agent (one that calls `Agent.run()` per utterance or per event) paid the graph-rebuild cost on every call — unpredictable latency in a realtime context. With graph caching, the first call pays the build cost; subsequent calls do not. Combined with GPT-Live's streaming WebSocket model, the architecture for a pydantic-ai agent that listens to a realtime audio stream and acts on each utterance is now well-defined: one `Agent` object, one `OpenAILiveModel`, and `Agent.run()` called per event with a cached graph. The `context_window_used` field gives you the safety valve to detect when a long-running session is approaching context limits before it fails silently.
*Grounded in: pydantic-ai v2.51.0 (this digest) — `OpenAILiveModel`, cached agent graph, `context_window_used`; pydantic-ai v2.50.0 (Sep 25 digest) — `DecisionModel` for routing*
