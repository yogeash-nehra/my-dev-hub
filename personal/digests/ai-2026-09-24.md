## 🏆 Repo of the Day

### akitaonrails/ai-memory — shared agent memory that follows you across tools, machines, and teammates

**Link:** github.com/akitaonrails/ai-memory | **Stars:** ~8.3k (↑ +1,208 this week) | **Language:** Rust | **License:** MIT

**The problem:** Every agent harness has its own memory silo — handoff context dies when you switch from Claude Code to Codex, or from your laptop to a teammate's machine.

**Why it's today's pick:** ai-memory solves cross-agent context continuity with a typed handoff protocol rather than a convention. It installs as a single self-contained binary, hooks into 20+ agent harnesses (Claude Code, Codex, Cursor, Gemini CLI, OpenCode, Devin, Kimi, Kiro, and others) via lifecycle hooks and MCP, and stores everything in a git-backed markdown wiki — not an opaque vector database. You can `grep` it, edit it by hand, and diff it in version control. The standout design choice: zero-LLM default — capture, full-text search, and retrieval work offline with FTS5; the optional LLM integration (Anthropic, OpenAI, Gemini, Ollama) only adds semantic ranking. Typed handoff semantics mean a "claim-once" protocol prevents two agents doing the same work twice — something teams running parallel agent sessions hit immediately. At 8.3k stars and +1,208 this week, the growth curve is real (trending this week on GitHub); star-history.com was egress-blocked in this scan and momentum is from GitHub Trending data only — validate independently before committing.

**Try it in 60 seconds:**
```bash
# Docker (recommended for production)
docker run -d --name ai-memory -p 127.0.0.1:49374:49374 \
  -v ai-memory-data:/data akitaonrails/ai-memory:latest

# Wire up Claude Code (or any supported harness)
ai-memory install-mcp --client claude-code --apply
ai-memory install-hooks --agent claude-code --apply

# Ask in the next agent session:
# "where did we leave off?"
# "search memory for X"
```
**Instead of:** Manually pasting context summaries between agent sessions, or maintaining agent-specific memory files per tool that quickly diverge.

**Watch out for:** 8.3k stars — actively maintained but not yet at enterprise production scale. Windows support is experimental. The `ai-memory install-hooks` path touches your agent's lifecycle config; review the generated hook config before applying in production pipelines.

## API & SDK Changes

### [HIGH] Anthropic Expanded Refusal Billing — pre-output refusals in `bio`, `frontier_llm`, `reasoning_extraction` now billed
**Source:** Anthropic Platform Release Notes | **Date:** September 24, 2026 | **Link:** https://platform.claude.com/docs/en/release-notes/overview

**What changed:** Pre-stream refusals in three specific categories (`bio`, `frontier_llm`, `reasoning_extraction`) are now billed at the requested model's standard rates. Before today, any refusal that occurred before any output tokens were returned was not billed. The change applies to all platforms (API, Bedrock, Vertex).

**TL;DR:** A Claude Fable 5.1 request that returns `stop_reason: "refusal"` with `stop_details.category: "bio"` (or `"frontier_llm"` or `"reasoning_extraction"`) before producing any output now incurs the full input-token cost at the Fable 5.1 rate ($3/MTok).

**Developer signal:** (1) **Audit your app's use cases if they touch life sciences, AI model discussion, or reasoning-extraction patterns.** The `bio` category covers requests related to bioweapons and CBRN materials; `frontier_llm` covers requests to extract training data, weights, or detailed training procedures from frontier models; `reasoning_extraction` covers attempts to elicit full internal reasoning chains in ways that circumvent safety measures. If your app serves researchers, enterprise users, or includes open-ended question fields where users could probe these areas, your refusal rate in these categories will now accrue costs. (2) **Check your fallback setup.** Anthropic's `fallbacks: "default"` SDK parameter (added in the `fable-5-fallback` beta) handles refused requests by automatically retrying on a fallback model; with today's billing change, a Fable 5.1 refusal now costs the Fable 5.1 input-token rate before the fallback model's charge is incurred. Review the SDK middleware docs to understand total cost impact. (3) **Mid-stream refusals** (stop_reason: "refusal" with some output already returned) were already billed before today — no change there. (4) **Refusals in all other categories** (those with `stop_details.category` outside these three, or with a null category) remain unbilled before output. (5) For cost model updates, see: https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback#how-refusals-are-billed

**Affects you if:** You build on Claude Fable 5.1, Fable 5, Opus 5.5, or Opus 5 and your app surfaces user-generated queries that could touch biomedical research, AI model internals, or reasoning-extraction patterns.

**Adoption effort:** Moderate — no code changes required, but cost projections must be updated; if you expose open-ended user query fields, consider pre-filtering or rate-limiting categories likely to trigger these refusals to bound cost exposure.

**Primary source:** https://platform.claude.com/docs/en/release-notes/overview | https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback#how-refusals-are-billed

## Research

### [MEDIUM] KEX-bench: Coding Agents Solve 56% of Linux Kernel Exploit Tasks Without Reference Code
**Source:** arXiv:2609.25591 (Jang J., Lee G., Lee H., Kim K., Kim J., Jung J., Zhang L.) | **Date:** September 22, 2026 | **Link:** https://arxiv.org/abs/2609.25591

**What changed:** Prior benchmarks for coding agents on security tasks used controlled, synthetic vulnerabilities or relied on agents having access to reference proof-of-concept (PoC) code. KEX-bench introduces the first benchmark using real, published CVEs in production kernels under conditions where agents have no PoC access — forcing agents to reproduce exploit primitives from scratch.

**TL;DR:** On 45 tasks across 40 Linux and Windows CVEs (kernel address leak, instruction-pointer control, heap read/write, arbitrary address write), the strongest agent configuration solves 56.0% of Linux tasks and 5.0% of Windows tasks without a reference PoC, and 68.9% overall when given a reference PoC — numbers that change what "achievable" means for kernel exploit generation.

**Developer signal:** (1) **The 56% Linux solve rate without reference PoC is the headline.** This is the first publicly verified evidence that a frontier coding agent + model combination can, starting from a CVE description alone, generate a working exploit primitive against a real production kernel at majority success rates. For security practitioners building AI-assisted vulnerability research tools: the capability is real, measurable, and benchmarked. (2) **Windows is still hard (5%).** The gap between Linux (56%) and Windows (5%) on the zero-PoC condition reflects the complexity of Windows kernel internals versus the more publicly documented Linux kernel ABI — a real signal for teams deciding which platform to focus agent-assisted research on. (3) **KEX-bench is the eval suite.** The benchmark runs tasks in isolated virtual machines with controlled tools and a deterministic verifier — the hardest bar in the current exploit-generation literature. If you're building security research agents, KEX-bench is the standard to beat. (4) **Dual-use implications:** The same capability that helps security researchers find kernel vulnerabilities can be misused. Responsible disclosure and access controls around these agent configurations are not optional.

**Affects you if:** You build AI-assisted vulnerability research tools; you operate kernel or OS-level security tooling where agent-assisted exploit generation is in scope; you need to know what frontier coding agents can actually do in security contexts.

**Adoption effort:** Moderate to evaluate (KEX-bench VMs required); results are immediately relevant to anyone using coding agents for security research.

**Primary source:** https://arxiv.org/abs/2609.25591

**Source:** Anthropic (GitHub) | **Date:** September 24, 2026 | **Link:** https://github.com/anthropics/claude-code/releases/tag/v2.1.282

**Developer signal:** (1) **Auto mode classifier changed.** If you run Claude Code with `--api direct` and telemetry disabled (the common configuration for enterprise CI), auto mode now uses the server-side classifier by default instead of the client-side classifier. **Affects you if:** You use Claude Code's `--continue`/`--resume` flags in multi-session agent pipelines; you run Claude Code in auto mode with telemetry disabled; you use extended thinking with slash commands; you have custom skills in `anthropic-skills` or `claude-ai` namespaces.
