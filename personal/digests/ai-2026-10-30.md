### nektos/act — run GitHub Actions workflows locally, without pushing to CI first
**Link:** github.com/nektos/act | **Stars:** ~60k (steady long-term growth) | **Language:** Go | **License:** MIT
**The problem:** Every Actions workflow change requires a push to discover whether it works — slow, noisy in CI history, and impossible to debug interactively.
**Why it's today's pick:** A watchlist pick on a light trending day — but genuinely still underused. `act` intercepts GitHub Actions trigger events locally, runs jobs in Docker containers mirroring the Actions runner environment, and reports pass/fail in your terminal. As Claude Code and other agents start generating and modifying CI workflows, `act` becomes the local validation step before any agent-authored pipeline lands in your repo. It's been around for years but most teams still don't use it.
**Try it in 60 seconds:**
```bash
# macOS
brew install act

# Linux / WSL
curl https://raw.githubusercontent.com/nektos/act/master/install.sh | sudo bash

# Run the push event on your repo
act push
```
**Instead of:** Committing a typo to `.github/workflows/`, waiting for the runner to pick it up, watching it fail 3 minutes later, and pushing a fix commit.
**Watch out for:** Some Actions are hard to replicate locally — GitHub's hosted runners expose secrets, GPUs, and artifacts the local Docker environment can't easily match. For complex pipelines, `act` catches 80% of issues; the remaining 20% still need a real run.

## Tooling

### [NOTABLE] Claude Code v2.1.314 — workspace write guard, IdP group routing, idle compaction, hook output cap
**Source:** GitHub Releases (anthropics/claude-code) | **Date:** 2026-10-30 | **Link:** https://github.com/anthropics/claude-code/releases/tag/v2.1.314
**What changed:** Seven distinct developer-facing changes landed alongside several bug fixes; highlights are a new opt-in write security flag, group-based upstream routing in the Claude Apps Gateway, idle compaction for long conversations, and a hook output cap.
**TL;DR:** v2.1.314 adds `permissions.blockWritesOutsideWorkingDirectories` (prevents agent writes outside declared workspaces), group-based IdP routing for Claude Apps Gateway upstreams, idle conversation compaction at 200K+ tokens in VS Code and Claude Desktop, and a 10,000-character cap per hook output.
**Developer signal:**
- **`permissions.blockWritesOutsideWorkingDirectories`**: When enabled, Write, Edit, and NotebookEdit calls to paths outside the configured working directories are refused in every permission mode. Set this flag in any deployment where Claude runs as a service, handles multi-project sessions, or where unexpected writes to `/etc`, `~/.ssh`, or system paths would be a concern. Not on by default — opt in explicitly.
- **Claude Apps Gateway — `groups` list on upstreams**: Assign an upstream to a list of IdP groups; only developers in those groups are routed there, including on failover. This enables role-based model routing without a separate proxy layer — e.g., "send `platform-team` to the high-quota upstream, everyone else to the standard pool."
- **Claude Apps Gateway — `guardrail_trace` on Bedrock upstreams**: Logs which Bedrock guardrail filter fired and its category, without logging the matched text. Useful for compliance audits — you can see guardrail activity without retaining the content that triggered it.
- **Idle compaction (VS Code + Claude Desktop)**: Sessions idle with 200K+ tokens and an expired prompt cache now automatically compact to a summary. On your next message, the compaction summary is used instead of the full context. Reduces "session too long" friction for persistent long-running coding sessions; no opt-in required.
- **Hook output cap**: Each hook's output is capped at 10,000 characters. If a PreCompact hook returned very large output (e.g., a full project context dump), that previously caused compaction to loop or fail — this cap fixes it. Review any hook that produces verbose output; truncate or filter before the 10k cap cuts it.
- **`claude -p` startup errors**: Non-interactive mode (`claude -p`) now prints startup errors to stderr and exits with code 1 instead of silently succeeding. Scripts that shell out to `claude -p` and check the exit code will now correctly detect misconfiguration errors at startup.
- **Bedrock many-images fix**: Sessions that included many images in their context no longer fail every turn or fail `/compact` with "400 Input is too long." Older images are removed automatically before compaction proceeds.
**Affects you if:** You run Claude Code in enterprise or multi-user deployments; you use the Claude Apps Gateway with Bedrock guardrails; you have persistent long-running sessions in VS Code or Claude Desktop; you call `claude -p` from scripts; you use PreCompact hooks with large output.
**Adoption effort:** Quick (upgrade Claude Code; opt in to `blockWritesOutsideWorkingDirectories` in `settings.json` if desired; review hooks for output size; no code changes required for other fixes).
**Primary source:** https://github.com/anthropics/claude-code/releases/tag/v2.1.314

## Trends & Emerging Tech

### Claude Code's enterprise hardening is accelerating — every release adds an enterprise-facing control
**Source:** GitHub Releases (anthropics/claude-code) | **Date:** 2026-10-30 | **Link:** https://github.com/anthropics/claude-code/releases/tag/v2.1.314
**What's happening:** v2.1.314 adds workspace write guards, IdP group routing, Bedrock guardrail tracing, and idle compaction. v2.1.312 (Oct 27) added OIDC `user_id_claim` support for gateway authentication. v2.1.311 (Oct 26) added skills analytics for Claude Tag. Three consecutive releases in four days have each added at least one enterprise access-control or observability feature alongside the usual bug fixes. The pattern is unmistakable: the code itself ships features for individual developers, but each release also ships something that only matters if you're deploying Claude Code at organization scale.
**Why watch this:** If this trajectory holds, Claude Code will become self-sufficient for enterprises that currently layer a separate auth proxy, observability stack, or write sandbox on top. The open question is whether the enterprise features stay in the CLI or migrate to the Anthropic platform (a managed Claude Code-as-a-service). Either path ends with significantly more lock-in at the "developer tooling" layer of the stack — worth tracking before a production dependency is deep.

**[PATTERN] Claude Code's workspace security model is converging on a containerization-like boundary**
`blockWritesOutsideWorkingDirectories` in v2.1.314 is the third workspace-scoping control added in the past two weeks — alongside per-directory skills (v2.1.312) and the `sandbox.excludedCommands` description fix (v2.1.314). Each tightens the agent's operational boundary: skills are scoped to the directory they're found in, commands can be excluded by pattern, and now writes are blockable outside declared workspace roots. This converges toward the same model as a container: a declared namespace of permitted resources, with everything outside it denied by default. The gap versus a real container runtime is still significant (no syscall isolation, no network namespace), but the permission surface is narrowing with each release.
*Grounded in: Claude Code v2.1.314 (blockWritesOutsideWorkingDirectories, sandbox.excludedCommands clarification); Claude Code v2.1.312 (per-directory skills)*

**[OPEN QUESTION] Why is `blockWritesOutsideWorkingDirectories` opt-in rather than the default?**
The new flag in v2.1.314 is not enabled by default — you have to set it explicitly. If writes outside the working directory are dangerous enough to warrant a named permission flag, the safer default would be to block them unless the user opts out. The most likely explanation is backwards compatibility: existing setups that intentionally write to paths outside the workspace (dotfiles, shared config directories, system paths in CI) would break. But this raises a question for anyone building on Claude Code: if the safe posture requires opt-in, how many production deployments are currently running without it? A "default to safe, break-glass opt-out" model would be more defensible.
*Grounded in: Claude Code v2.1.314 release notes (blockWritesOutsideWorkingDirectories flag behavior)*

**[BUILDER'S ANGLE] IdP group routing in the Claude Apps Gateway enables tiered-access multi-model deployments without a proxy**
The new `groups` list on Gateway upstreams in v2.1.314 means you can now declaratively route specific IdP groups (e.g., `platform-engineers`, `contractors`, `free-tier`) to different Claude model upstreams — including on failover. Combined with the `guardrail_trace` on Bedrock upstreams, a builder could construct a "model tier by org role" policy entirely in Claude Code configuration: premium users get the high-quota Bedrock upstream with guardrail logging; trial users get the rate-limited upstream with stricter guardrails; and the gateway handles the routing without a separate auth proxy layer. This becomes particularly powerful for companies deploying Claude Code to mixed-trust internal teams where different roles should get different model access levels.
*Grounded in: Claude Code v2.1.314 (groups list on upstreams, guardrail_trace on Bedrock upstreams)*

**[IF THIS CONTINUES] Idle compaction at 200K tokens implies persistent Claude Code sessions are the emerging production pattern**
The idle compaction feature in v2.1.314 automatically summarizes conversations that exceed 200K tokens and sit idle with an expired prompt cache. This feature only matters if users regularly accumulate 200K+ token sessions — which implies sustained, multi-hour or multi-day coding sessions that outlive the 5-minute prompt cache TTL. Six months ago, this use case was rare. Anthropic shipping a dedicated compaction trigger for it suggests it's common enough to warrant a friction-reduction feature. If session longevity continues increasing, the next architectural question becomes: how do you checkpoint, resume, and version-control long-running agent sessions the same way you'd version-control code? That's a category of tooling that doesn't really exist yet.
*Grounded in: Claude Code v2.1.314 (idle compaction at 200K+ tokens in VS Code and Claude Desktop)*
