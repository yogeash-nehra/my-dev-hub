### nektos/act — run your GitHub Actions workflows locally before you push

**Link:** github.com/nektos/act | **Stars:** ~58k (↑ steady, 2.5k added in October) | **Language:** Go | **License:** MIT
**The problem:** You push to CI, wait three minutes for the runner to spin up, and discover the workflow fails on step one because of a missing env var or a container image difference you can't reproduce locally.
**Why it's today's pick:** Codex 0.164.0 adds an Amazon Bedrock setup wizard and enterprise MCP authentication — both are features teams will want to test in CI before rolling out. `act` lets you run the full GitHub Actions workflow locally (same container, same env, same secrets) before pushing, catching configuration drift between your machine and the runner before it reaches CI. With Codex and Claude Code increasingly being deployed via CI/CD pipelines (not just developer workstations), having a way to test the full workflow locally before pushing is the kind of friction-reducer that saves hours per week. Act also integrates well with tools like `lefthook` (Oct 23 Repo of the Day) — you can run `act push` from a pre-push hook to validate CI passes before the branch even leaves your machine.
**Try it in 60 seconds:**
```bash
# Install (macOS)
brew install act

# Install (Linux)
curl https://raw.githubusercontent.com/nektos/act/master/install.sh | sudo bash

# Run the default push event for your repo's workflow
act push

# Run a specific workflow file
act -W .github/workflows/ci.yml
```
**Instead of:** Pushing speculative commits to see if CI passes, then amending, pushing again, and polluting the branch history with fix-ci commits. Act runs the same Docker container GitHub uses, so what passes locally passes on CI.
**Watch out for:** Large GitHub Actions runners (macOS, Windows) require pulling multi-GB images on first run. For most Linux workflows, `act -P ubuntu-latest=catthehacker/ubuntu:act-latest` gives you a trimmed image that starts in seconds. Secrets must be provided explicitly via `-s SECRET_NAME=value` or a `.secrets` file — act does not read from the GitHub Secrets UI.

### [MEDIUM] OpenAI Codex 0.164.0 — enterprise MCP auth via org grants, numbered prompt slots, image previews
**Source:** GitHub Releases | **Date:** 2026-10-23 | **Link:** https://github.com/openai/codex/releases
**What changed:** Released Oct 23 — not surfaced in prior scan cycles (Oct 23 digest focused on pydantic-ai and Claude Code; Oct 24 digest didn't catch it). Key additions: ten numbered slots (1–0) for saving reusable prompts and slash commands, callable from a keyboard menu — the first in-session prompt library in Codex. Enterprise MCP authentication via eligible Codex account grants or dedicated sign-in, including OAuth clients that require secrets — the first first-party coding agent to handle org-level OAuth for MCP tools rather than per-developer API keys. Image previews in the fullscreen transcript on Kitty/Sixel-capable terminals. Amazon Bedrock setup wizard now on by default, appearing automatically when AWS credentials are detected. Multiple bug fixes: failed compaction no longer leaves partial summaries in history; Windows HTTPS/WebSocket connections handle proxy auth with signed-in user's Negotiate/NTLM credentials; sandbox checks stricter for case-variant metadata paths on macOS.
**TL;DR:** Codex 0.164.0 adds enterprise MCP OAuth (org identity delegation, not per-dev keys), 10 reusable numbered prompt slots, and inline image previews — a substantive Thursday release that was overshadowed by Anthropic's busy week.
**Developer signal:** **Enterprise MCP auth**: If your organization runs MCP servers that require enterprise-level OAuth (SAML-federated, SSO-linked, or secrets-bearing OAuth clients), Codex 0.164.0 is when you can start using those servers without distributing API keys to each developer. Check your Codex account under enterprise grants to see which MCP servers are eligible — the release notes describe OAuth clients that "need secrets" as the primary target. This is the first time any major first-party coding agent has handled this at the org-identity layer. **Numbered prompt slots**: Open Codex, use the keyboard menu shortcut, and map your most-used prompts or slash commands to slots 1–0. This replaces copy-pasting from a notes file at the start of each session. **Image previews**: If your terminal supports Kitty graphics protocol or Sixel (Ghostty, WezTerm, Kitty, certain recent versions of iTerm2), the Codex fullscreen transcript now renders images inline — useful for agents that produce architecture diagrams or test output charts. **Bedrock setup**: If you run Codex against Amazon Bedrock, the setup wizard now appears automatically when credentials are detected; no more hunting through settings menus.
**Affects you if:** You use enterprise MCP servers requiring org-level OAuth; you run frequently-repeated prompts in Codex sessions; you're in a Kitty or Sixel-capable terminal; you run Codex against Amazon Bedrock.
**Adoption effort:** Quick (upgrade to 0.164.0; check enterprise account grants for MCP auth eligibility).
**Primary source:** https://github.com/openai/codex/releases

## Trends & Emerging Tech

### The agent infrastructure layer is consolidating while the runtime layer fragments
**Source:** GitHub Trending weekly (Oct 25, 2026) | **Date:** 2026-10-25 | **Link:** github.com/trending?since=weekly
**What's happening:** Four of the top 15 trending repos this week solve the same cluster of problems one layer above the agent runtimes: persistent cross-vendor memory (akitaonrails/ai-memory, 13.5k stars), fleet management across machines (stablyai/orca, 105k), codebase knowledge graphs for agents (Graphify-Labs/graphify, 135k), and CLI-based agent tooling bridges (HKUDS/CLI-Anything, 57k). None of these is from a major lab. Meanwhile the runtime layer is fragmenting further: Claude Code, Codex, Gemini CLI, OpenCode, Cline, Cursor all have active development. The infrastructure layer is consolidating around interoperability; the runtime layer is diversifying. Developers increasingly need tools that work across runtimes rather than being locked to one.
**Why watch this:** When the infrastructure layer consolidates around cross-cutting concerns (memory, fleet management, codebase indexing), the developer's switching cost between runtimes drops. If ai-memory, orca, and graphify become the defaults in their respective niches, moving between Claude Code and Codex stops requiring any behavioral change from the developer — the memory follows them, the knowledge graph is already built, the fleet manager handles the session. That's a structural shift in how coding agents get evaluated: you pick the runtime that's best for the task, not the one you're locked into.

**[PATTERN] Cross-vendor agent infrastructure is being built by neutral third parties, not the labs**

Anthropic, OpenAI, and Google each ship their own agent runtimes (Claude Code, Codex, Gemini CLI), but none of them ships persistent cross-vendor memory, fleet management, or codebase knowledge graphs as built-in features. This week's trending repos fill those gaps for all three simultaneously: akitaonrails/ai-memory supports 20+ agent harnesses, stablyai/orca manages Claude Code sessions alongside others, Graphify-Labs/graphify connects to any agent that supports MCP. The pattern is familiar from cloud computing: AWS, GCP, and Azure each have native auth; Okta handles federated identity across all three. Cross-cutting concerns tend to be solved by neutral parties, not by the infrastructure providers who compete on the features inside their own boundary. That structural advantage is real: a lab that ships its own memory feature has a commercial interest in making switching agents costly. An independent tool has the opposite interest.
*Grounded in: akitaonrails/ai-memory (Oct 25 GitHub Trending), stablyai/orca, Graphify-Labs/graphify trending data (GitHub Trending weekly, Oct 25)*

**[TENSION] Rapid release velocity vs. operational stability in fast-moving dev tooling**

akitaonrails/ai-memory shipped 8 releases in October, including 3 on a single day (Oct 25). The release artifacts contain only SHA256 checksums — no per-version changelogs. This creates real tension for teams evaluating it as team infrastructure: high release velocity signals active development and healthy adoption, but the absence of changelogs makes it difficult to assess what changed between v3.2.3 and v3.2.5, or to pin a version with confidence. This pattern is common in fast-moving dev tools and resolves in one of two ways: the project adds CHANGELOG.md discipline as it matures, or it implicitly adopts a "pin to latest" contract. Teams considering ai-memory for production use should track the GitHub commits between releases rather than waiting for formal changelogs.
