## 🏆 Repo of the Day

### mksglu/context-mode — stops tool output from eating your agent's context window

**Link:** github.com/mksglu/context-mode | **Stars:** ~23.5k (↑ +1,482 this week, #7 overall GitHub Trending weekly) | **Language:** TypeScript | **License:** ELv2 (Elastic License v2 — source-available, not OSI open-source)
**The problem:** Every file read, web fetch, and shell command dumps raw output straight into context — one Playwright page snapshot is 56 KB; twenty GitHub issues are 59 KB. After 30 minutes, 40% of an agent session's context is consumed by tool responses, not actual work. Existing compaction helps later, but doesn't stop the bleed as it happens.
**Why it's today's pick:** With Claude Code v2.1.275 shipping claude.ai skill/plugin sync to terminal (today's digest), the ecosystem of MCP tools agents can reach is expanding rapidly — and so is the context-bloat problem. context-mode attacks it at the source: it intercepts tool calls, runs them in subprocesses, and returns only stdout to the context window. "315 KB → 5.4 KB: 98% reduction" is the headline number, backed by a session SQLite store with BM25 full-text search so agents can retrieve prior decisions after compaction without re-reading everything. Supports 17 platforms: Claude Code, Codex CLI, Gemini CLI, Cursor, Cline, OpenCode, Kiro, Zed, Antigravity, and others. star-history.com was egress-blocked in this scan; trending rank and weekly growth are from GitHub Trending data only — validate momentum independently before committing.
**Try it in 60 seconds:**
```bash
# Claude Code (one command)
/plugin marketplace add mksglu/context-mode

# All other platforms (npm)
npm install -g context-mode

# First command to see the payoff
ctx_stats    # shows context bytes saved this session and per-tool breakdown
```
**Instead of:** Watching your agent hit the compaction ceiling, lose track of which files it was editing, and restart work it already completed.
**Watch out for:** ELv2 license prohibits using context-mode as a hosted SaaS or embedding it in a competing product — for personal dev use it's fine; check the license before building on it in a commercial product. The tool relies on your agent correctly using the `ctx_*` MCP tools rather than raw file/web tools, which may require prompt guidance or hooks to enforce.

## [BREAKING] Breaking Changes

### [BREAKING] Claude Code v2.1.277 — `TaskOutput` tool removed; migrate to `Read` tool
**Source:** Anthropic (GitHub) | **Date:** September 18, 2026 (15:47 UTC) | **Link:** https://github.com/anthropics/claude-code/releases/tag/v2.1.277

**What changed:** The deprecated `TaskOutput` tool is fully removed in v2.1.277. Claude previously used `TaskOutput` to read the output of background tasks (processes launched with Task tool calls). That tool is now gone — Claude reads background task output using the `Read` tool instead. The `taskOutputMaxChars` setting in `.claude/settings.json` and the `TASK_MAX_OUTPUT_LENGTH` environment variable no longer have any effect and can be removed.

**TL;DR:** `TaskOutput` tool removed in Claude Code v2.1.277 — agent code, scripts, and hooks that reference or depend on `TaskOutput` must switch to using the `Read` tool; `taskOutputMaxChars` / `TASK_MAX_OUTPUT_LENGTH` are now inert.

**Developer signal:** (1) **Audit your agent code, orchestration scripts, and any custom hooks for `TaskOutput` references.** If you call `TaskOutput` in your own code or check for it in tool-use response parsing, those calls will now return errors. Switch to using the `Read` tool to read the output file path returned by the `Task` tool. (2) **Remove `taskOutputMaxChars` from your `.claude/settings.json`.** The setting is silently ignored; leaving it in place won't break anything but creates confusion. Remove `TASK_MAX_OUTPUT_LENGTH` from any CI/environment configs for the same reason. (3) **If you built custom tooling around the old `TaskOutput` behavior** (chunked reading, output pagination), redesign around `Read` — which can read specific line ranges via `offset`/`limit` parameters. (4) **Also in v2.1.277:** `AGENTS.md` fallback support — Claude Code now reads `AGENTS.md` in projects that have no `CLAUDE.md`, configurable under `/config` → "Project instructions." This is not currently available on Bedrock, Vertex, or Foundry. (5) Gateway proxy improvements: `CLAUDE_GATEWAY_PROXY_IS_EGRESS_BOUNDARY=1` is a new env var for gateways whose only egress is a forward proxy (sends the hostname to the proxy rather than resolving locally); upstream configs now accept an optional `headers:` map for static headers to proxies in front of a provider.

**Affects you if:** You use the `Task` tool in agent workflows and read its output with `TaskOutput`; you set `taskOutputMaxChars` or `TASK_MAX_OUTPUT_LENGTH` in any environment or config; you run Claude Code behind a forward proxy with Claude apps gateway.

**Adoption effort:** Moderate — remove `taskOutputMaxChars`/`TASK_MAX_OUTPUT_LENGTH` (no-ops but confusing to leave); replace `TaskOutput` calls with `Read` (code change required for any agent or script that uses the background-task output pattern).

**Primary source:** https://github.com/anthropics/claude-code/releases/tag/v2.1.277

**Source:** Google (Gemini API / Antigravity changelog) | **Date:** September 17–18, 2026 | **Link:** https://ai.google.dev/gemini-api/docs/changelog

**Developer signal:** (1) **Who needs to act:** If you use `environment: "remote"` and only consume `output_text` or `model_output` steps, you just need to update the agent string to `antigravity-preview-09-2026` — nothing else changes for you. If you run tools locally (`local_environment`) or parse `function_call` steps from the response, your integration is breaking — the tool parameter names have changed. (2) **Rename all snake_case parameters in your function_call parsing to PascalCase.** Example: `file_path` → `FilePath`, `start_line` → `StartLine` — check the updated Antigravity agent docs for the full parameter name table. (4) **Add `find_by_name()` / `grep_search()`** to any tool catalog you're manually maintaining for this agent. (5) **Hard deadline: October 5, 2026.** After that, calls to `antigravity-preview-05-2026` will fail. Add this to your sprint backlog now.

**Affects you if:** You call the Google Gemini API Antigravity agent, especially if you use `local_environment` or parse `function_call` response steps; you maintain any wrapper or integration layer around Antigravity's built-in tools.

**Adoption effort:** Moderate — update the agent string (quick); rename `snake_case` → `PascalCase` in all function_call parsing (moderate code change); update file-edit handling from full-rewrite to line-range model (moderate code change).

### [MEDIUM] pydantic-ai v2.45.0 — `DynamicToolset` optimized per durable run; MCP server sessions persistent per run; GPT-5.6 variants on Bedrock Converse
**Source:** Pydantic (GitHub) | **Date:** September 17, 2026 | **Link:** https://github.com/pydantic/pydantic-ai/releases/tag/v2.45.0

**What changed:** `DynamicToolset` resolution previously occurred once per agent unit (each individual LLM call); it now resolves once per durable run (the full agent execution lifecycle). MCP server sessions were also previously maintained per unit; they now persist for the full durable run — meaning an MCP session is opened once at the start of a run and reused across all units within it, rather than torn down and re-established on every LLM call. Additionally: GPT-5.6-sol, GPT-5.6-luna, and GPT-5.6-terra are now supported on Bedrock Converse; Bedrock now correctly passes `xhigh` effort levels when supported; tool history is preserved in `MCPSamplingModel`; a new `TypeSafeModel` is added for TypeSafe's Jev integration.

**TL;DR:** pydantic-ai v2.45.0 reduces per-LLM-call overhead by shifting `DynamicToolset` resolution and MCP session lifecycle from per-unit to per-durable-run, and adds GPT-5.6-sol/luna/terra on Bedrock Converse.

**Developer signal:** (1) **If you use `DynamicToolset`**, behavior has changed: resolution runs once per run, not per LLM call. This means dynamic toolset logic that was implicitly "re-evaluated on every call" now runs once and caches the result for the run. If your toolset logic had side effects or was intentionally dynamic per-call, review the new behavior. For most users, this is a welcome optimization (fewer redundant resolution calls). (2) **If you use MCP servers in pydantic-ai**, your MCP sessions now persist for the full agent run rather than reconnecting on every unit. This is a significant latency improvement for MCP-heavy agents (removes repeated TCP handshakes / auth exchanges per LLM call) but means any MCP server state from earlier in the run is visible to later tools — verify this is acceptable for your use case. (3) **Bedrock Converse:** Add `gpt-5.6-sol`, `gpt-5.6-luna`, or `gpt-5.6-terra` as the model string to use these variants via the Bedrock Converse interface. `xhigh` effort level now correctly routes on Bedrock where supported. (4) **Legacy `httpx` imports** from `pydantic_ai.mcp` are removed — if you imported from that path directly (unlikely but possible), update to the new import paths.

**Affects you if:** You use `DynamicToolset` with side-effecting or truly per-call-dynamic resolution logic; you use MCP servers in pydantic-ai agents (behavior change in session lifecycle); you use Bedrock Converse and want GPT-5.6 variants or correct xhigh effort routing.

**Adoption effort:** Quick — update version; review DynamicToolset and MCP session behavior if your toolsets have per-call side effects.

**Primary source:** https://github.com/pydantic/pydantic-ai/releases/tag/v2.45.0

OpenHands and other open-weight agents are converging on similar "project instruction file" patterns, though under varied filenames.

**Why watch this:** If `AGENTS.md` becomes the canonical cross-agent instruction file (the way `.editorconfig` is for editor configuration), project maintainers will start adding it to repos the way they add `.gitignore` — and the content of that file becomes a first-class engineering artifact that shapes how all AI agents interact with the codebase. The next question is whether the spec for what `AGENTS.md` should contain gets standardized, or whether each agent interprets it in its own way (divergence risk). Agents that support only their own proprietary file format — `CLAUDE.md`, `CURSOR_RULES`, `.cline/rules` — will face adoption pressure to converge or add aliases.

**[TENSION] Two competing philosophies for the context-overflow problem: runtime interception (context-mode) vs. API-level compaction (Messages API `compact-2026-09-04`)**
context-mode solves context overflow by intercepting tool calls at runtime and preventing bloat from entering the context in the first place — a "stop it before it hits" model. The Messages API on-demand compaction (`compact-2026-09-04` beta, released September 14 — just outside today's window) solves the same problem by summarizing messages after the fact under developer control, returning a signed `compaction` block that replaces the raw messages on subsequent requests. These are genuinely different philosophies: context-mode requires agents to use the `ctx_*` tools (a behavioral change); API compaction works on any conversation but requires the developer to decide when to compact and handle the compaction block. The interesting design question: should context management be an agent skill (like context-mode), an API primitive (like the new compaction endpoint), or a model behavior (like Claude Code's built-in auto-compaction)? The current answer is: all three, with no coordination between them. Expect convergence pressure as the patterns mature.
*Grounded in: context-mode (this digest, Rising Dev Tools + Repo of the Day); Messages API on-demand compaction (`compact-2026-09-04` beta, September 14 — near-miss this digest)*

**[OPEN QUESTION] When an AI agent (Touch ID) replaces a developer's conscious approval decision for tool calls, what is the actual trust model?**
Codex v0.155.0's Touch ID approval for MCP requests is ergonomically elegant — biometric confirmation instead of a typed passphrase for each tool call. But Touch ID confirms "the person whose fingerprint this is approved this action at this moment" — it doesn't verify that the person understood what action they were approving. Approving a Claude or Codex MCP tool call is not like approving a payment (a single, clearly scoped action); it's approving a tool execution whose downstream effects may be non-obvious (an MCP call that writes to a database, modifies a remote system, or sends a message). The risk: ergonomic approval prompts train users to approve quickly rather than evaluate. The more they approve with Touch ID, the less they read what they're approving. This matters especially as coding agents are given access to more powerful MCP servers (billing APIs, infrastructure management, external communication channels). The right behavior is probably for agents to provide a clearer natural-language summary of what a given tool call will do at the moment of approval — before the biometric prompt, not after.
