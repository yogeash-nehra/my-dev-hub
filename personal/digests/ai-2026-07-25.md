## [BREAKING] Breaking Changes

### [BREAKING] vLLM v0.26.0: TeleChat, Persimmon, and Fuyu Model Support Removed

**Source:** vLLM GitHub Releases | **Date:** July 25, 2026 | **Link:** https://github.com/vllm-project/vllm/releases/tag/v0.26.0

**What changed:** vLLM v0.26.0 removes support for three model families present in v0.25.0: TeleChat (China Telecom), Persimmon (EleutherAI), and Fuyu (Adept AI). Any vLLM deployment config pointing at these models will fail to load after the upgrade.

**TL;DR:** vLLM v0.26.0 drops TeleChat, Persimmon, and Fuyu — grep your configs before upgrading, or stay pinned to v0.25.0.

**Developer signal:** Before upgrading from v0.25.0 to v0.26.0, grep your deployment configs, model loading code, and any CI test fixtures for `TeleChat`, `Persimmon`, and `Fuyu`. If found: either delay the upgrade and file a vLLM issue tracking migration alternatives, or swap to a supported model family first. TeleChat serves primarily regional (China Telecom) enterprise use cases; Persimmon and Fuyu are more common in research inference setups than production. No migration path or replacement recommendations are documented in the v0.26.0 release notes. If none of these appear in your configs, the removal has zero impact on your upgrade path — proceed directly to the security and performance benefits in the Tooling section.

**Affects you if:** Your vLLM inference config, model loading code, or CI fixtures reference a TeleChat, Persimmon, or Fuyu model.

**Adoption effort:** Moderate (migrate models before upgrading) / Quick (if you don't use these models).

**Primary source:** https://github.com/vllm-project/vllm/releases/tag/v0.26.0

## Tooling

### [HIGH] vLLM v0.26.0: DeepSeek-V4 Kernel Optimizations, Pickle Deserialization Vuln Patched, Inkling Model Family, Rust Frontend Expands

**Source:** vLLM GitHub Releases | **Date:** July 25, 2026 | **Link:** https://github.com/vllm-project/vllm/releases/tag/v0.26.0

**What changed:** v0.26.0 is a full major-cycle release over v0.25.0 (411 commits, 212 contributors, 61 newcomers). Key deltas from v0.25.0: (1) **Security** — pickle deserialization vulnerability eliminated via diskcache replacement; concurrent sparse-invariant race fixed that bypassed a prior CVE remediation; resource bounds validation added on derender endpoints; regex compilation timeout guards added. (2) **Performance** — DeepSeek-V4 routing kernel: +2.94% E2E TPOT improvement; fused topk_bias operation: 1.5–2× kernel speedup; redundant operation removal: +1.8% E2E TPOT. (3) **New model support** — Inkling model family with piecewise CUDA graphs, Hopper FA4 attention, speculative decoding, LoRA, and NVFP4 quantization. (4) **API additions** — `head_dtype` parameter for fp32 lm_head on generation models; `bad_words` in completions; `logprob_token_ids` exposure; `num_cache_creation_tokens` population. (5) **Endpoint plugins framework** introduced. (6) **Rust frontend** — multimodal video/audio support, Seed-OSS tool parsing, native vllm-bench port. (7) **KV offloading** matured with tiered storage, object-store secondary tier with workload identity. (8) **Transformers 5.13.0** integration (Olmo/Olmo2, MistralLarge3, HunyuanVL migrations). (9) **Removals** — TeleChat, Persimmon, Fuyu (see Breaking section).

**TL;DR:** vLLM v0.26.0 (411 commits, 212 contributors) delivers +2.94% E2E TPOT on DeepSeek-V4 workloads, patches a pickle deserialization vulnerability and a CVE-bypass race condition, adds the Inkling model family, and extends the Rust frontend with multimodal capability.

**Developer signal:** Five action items for vLLM operators: (1) **Security — highest priority**: v0.26.0 patches a pickle deserialization vulnerability (a class of vulnerability more typical of general Python services than inference servers) and a CVE-bypass race condition in sparse model handling. If you run vLLM in a shared or internet-facing environment, these patches alone justify the upgrade on an accelerated timeline — treat it like any critical security release. (2) **DeepSeek-V4 operators**: the routing kernel, topk_bias fusion, and redundant op removal together deliver roughly 4–7% total throughput improvement on V4 workloads. Upgrade without waiting if you serve DeepSeek-V4-Flash or V4-Pro at scale. (3) **Model removal check first** (see Breaking section): grep for TeleChat, Persimmon, and Fuyu before upgrading — these fail after the upgrade with no fallback. (4) **New `head_dtype` parameter**: if you run generation models where lm_head precision matters (some fine-tuned or research setups use bf16 lm_head explicitly), the new `head_dtype` parameter gives you direct control; verify the previous implicit behavior matches your expectations before upgrading. (5) **Endpoint plugins framework**: a new extension point for attaching custom logic to vLLM endpoints — relevant for teams currently running a proxy or middleware layer on top of vLLM's native server for auth, routing, logging, or request transformation. The surface is new; docs are likely sparse; worth prototyping before committing production middleware to it (see Horizon for caveats on Rust frontend migration).

**Affects you if:** You serve LLMs with vLLM, especially DeepSeek-V4 models; you run vLLM in shared or internet-facing environments; you use TeleChat, Persimmon, or Fuyu model families; you maintain custom proxy/middleware on top of vLLM.

**Adoption effort:** Moderate — security patches justify an accelerated upgrade cycle, but the model removal requires a config check first; net-new API features are opt-in.

**Primary source:** https://github.com/vllm-project/vllm/releases/tag/v0.26.0

## Trends & Emerging Tech

### Windowed-MTP: Speculative Decoding's KV Cache Tax at Million-Token Context Has a Fix — And It's Surprisingly Simple

**Source:** arXiv | **Date:** July 2026 | **Link:** https://arxiv.org/abs/2607.21535

**What's happening:** A new arXiv paper (2607.21535, Alagappan Valliappan) proposes Windowed-MTP — applying StreamingLLM-style sliding window attention plus attention sinks to the MTP draft head only in speculative decoding, while leaving full-attention verification intact. At 1M token context, the MTP draft head normally reads the entire KV cache at every draft step, so its cost grows linearly with context and can dominate total inference cost. Windowed-MTP cuts this to a fixed window, capping draft overhead regardless of context length. Across three architecture families, the paper reports +28% to +44% reduction in per-decode-step cost at 1M context. No associated code repository is linked; author institution is not confirmed from a recognized top lab.

**Why watch this:** vLLM v0.26.0 (this digest, Tooling) added comprehensive Inkling model support including speculative decoding with Hopper FA4 kernels, meaning the ecosystem for testing this technique is expanding rapidly. If Windowed-MTP holds up under independent reproduction, it becomes directly applicable to anyone running MTP-based speculative decoding on million-token workloads — which is a growing use case as Claude Opus 5, Kimi K3, and other 1M-context models proliferate. The critical unknown: whether the sliding window on the draft head materially degrades draft token acceptance rates at long context. The paper focuses on step-cost reduction; a reduction in acceptance rates could partially or fully offset the throughput gains. Worth tracking for a follow-up implementation in vLLM or llama.cpp.

### Kimi K3 Open Weights Are 48 Hours Away — With a 1.4TB MXFP4 Footprint

**Source:** Multiple sources (Kimi platform, tech coverage) | **Date:** July 25, 2026 | **Link:** https://www.techi.com/kimi-k3-open-weights-inference-economics/

**What's happening:** Kimi K3's open weights drop July 27 at 00:00 UTC under a Modified-MIT-style license. New detail confirmed today: the MXFP4-quantized weights require approximately 1.4TB of fast GPU memory before runtime buffers or KV cache. The model is 2.8T total / ~32B active parameters using Kimi Delta Attention (KDA) — a hybrid linear/full attention mechanism — with a 1M context window and native visual understanding. MXFP4 quantization is optimized for Blackwell GPU architecture. This is the first open-weights model in the 3T parameter class.

**Why watch this:** 1.4TB MXFP4 is a new hardware floor for frontier-tier open weights. For most teams, that means renting Blackwell cluster time or using the Kimi API — 8× H200s deliver ~700GB VRAM, making even that insufficient without further quantization at the cost of quality. The Modified-MIT license is developer-friendly (fine-tuning and redistribution rights), but the hardware bar makes this a data center play rather than a local-AI story for most teams. The key deployment question: whether KDA's linear attention hybridization degrades gracefully at production context lengths (50K–200K tokens, not 1M), since most real-world workloads don't run at the million-token ceiling the architecture is designed around. Verify short-context quality on your task distribution before committing to a K3-based deployment path.
