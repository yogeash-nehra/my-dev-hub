### dagger/dagger — automation engine that runs the same pipeline locally, in CI, or directly in the cloud
**Link:** github.com/dagger/dagger | **Stars:** ~16.5k (↑ steady growth through 2026) | **Language:** Go | **License:** Apache-2.0
**The problem:** Your CI/CD pipeline runs one way on GitHub Actions and a different way locally — shell scripts, environment differences, and "it works on CI but not my machine" gaps eat hours. Dagger lets you write your pipeline as code (Go, Python, TypeScript, or Rust) and run it identically in every environment.
**Why it's today's pick:** Claude Code v2.1.310 ships enterprise custom roles for cloud sessions and a cloud environment setup script chooser — teams are starting to treat Claude Code in the cloud as a production deployment, not just a dev tool. When you're wiring Claude Code cloud sessions into a release workflow, having a pipeline tool that behaves identically locally and remotely matters. Dagger's v1.0.0-beta.20 (Oct 22) also quietly switched its own LLM API clients to the OpenAI Responses endpoint — a signal the project is paying attention to the AI tool ecosystem. It's approaching v1.0 GA after two years in beta.
**Try it in 60 seconds:**
```bash
# Install
curl -fsSL https://dl.dagger.io/dagger/install.sh | sh

# Run a simple pipeline (in any directory)
dagger call --help

# Or install the Dagger Dev Kit for your language:
# Go:         go get dagger.io/dagger@latest
# Python:     pip install dagger-io
# TypeScript: npm install @dagger.io/dagger
```
**Instead of:** Writing bash scripts that work differently across macOS, Linux, GitHub Actions, and CircleCI — or maintaining a separate Dockerfile-based CI setup that can't run locally without special flags.
**Watch out for:** v1.0.0 is still in beta (beta.21 dropped this week). The API is stable but a few edges remain — check the changelog before upgrading between beta versions. First run is slow (pulls the Engine container); subsequent runs are fast.

## API & SDK Changes

### [MEDIUM] Claude Code v2.1.310 — Monitor tool on Bedrock/Vertex/Foundry, gateway compatibility fix, enterprise cloud roles
**Source:** GitHub Releases | **Date:** 2026-10-23 | **Link:** https://github.com/anthropics/claude-code/releases/tag/v2.1.310
**What changed:** Three meaningful capability additions: (1) The Monitor tool and plugin monitors are now available on Bedrock, Vertex, and Foundry, and when telemetry or nonessential traffic is disabled — previously Monitor was unavailable in these environments. Long foreground sleeps are also blocked there now. (2) Requests no longer fail silently behind gateways and compatible servers that reject the `effort-2025-11-24` beta header or mid-conversation system messages — Claude Code retries without them. (3) Enterprise custom roles can now control access to Claude Code cloud sessions and Remote Control; enabling either in admin settings now requires confirmation and lists which custom roles are affected.
**TL;DR:** Claude Code v2.1.310 brings Monitor to Bedrock/Vertex/Foundry, fixes silent failures behind corporate proxy gateways, and adds enterprise role-based access control for cloud sessions.
**Developer signal:** **Monitor tool on cloud providers:** If you run Claude Code on Bedrock, Vertex AI, or Azure Foundry, the Monitor tool now works — update to v2.1.310 and verify your plugin monitors fire correctly. Long `sleep` calls in foreground processes are also now blocked in these environments, matching the behavior you get locally. **Gateway fix:** If you've seen Claude Code fail behind a corporate proxy with no clear error, this is likely the cause — the `effort-2025-11-24` beta header was being rejected. Upgrade and the retry logic handles it automatically. **Enterprise cloud roles:** Owners can now scope who in the organization can start Claude Code cloud sessions and use Remote Control — check your Enterprise admin settings to configure this before it silently defaults to unrestricted access. Also notable: file read prompts now show the real path when a symlink is involved (useful if your workspace uses symlinked config directories), and Linux users on Ubuntu with AppArmor restrictions will now see a clear message explaining how to lift the user namespace restriction that blocks the bubblewrap sandbox from starting.
**Affects you if:** You run Claude Code on Bedrock, Vertex, or Foundry and want the Monitor tool; you use Claude Code behind a corporate gateway/proxy; you are a Claude Enterprise admin managing cloud session access.
**Adoption effort:** Quick (upgrade; check enterprise admin settings for cloud roles).
**Primary source:** https://github.com/anthropics/claude-code/releases/tag/v2.1.310

## Tooling

### [MEDIUM] pydantic-ai v2.61.0 — structured citations, thinking guardrails, kimi-k3.1-pro, InputGuardrail hardening
**Source:** GitHub Releases | **Date:** 2026-10-23 | **Link:** https://github.com/pydantic/pydantic-ai/releases/tag/v2.61.0
**What changed:** The day after v2.60.0's major feature release, v2.61.0 ships hardening and a meaningful new capability. **Citations:** `TextPart` now carries structured citations (#7434); citations from Bedrock, OpenRouter, and xAI are normalized and replayed to the provider that produced them (#7750, #7752); the Vercel AI adapter also preserves them (#9639). **Thinking guardrails:** Models that can't disable thinking now receive the lowest thinking level they accept when `thinking=False` (#11036); a warning fires when a provider-specific thinking override silently conflicts with the `thinking=` parameter (#10231). **Security:** `InputGuardrail` now redacts the user's own prompt in fail-open paths (#10841), closing a path where an unhandled guardrail exception could leak the prompt to the model. **New models:** `kimi-k3.1-pro` and `kimi-k3.1-pro-highspeed` model names are added (#11173). Also: `LocalStack` now shares one container within `async with agent:` rather than spawning fresh ones per run, fixing resource waste in test suites.
**TL;DR:** pydantic-ai v2.61.0 adds structured citations in TextPart (normalized across Bedrock/OpenRouter/xAI), closes a guardrail fail-open security path, and adds kimi-k3.1-pro model names.
**Developer signal:** **Citations:** If you build applications where model responses need to trace back to sources (RAG, document Q&A), update to v2.61.0 and explore `TextPart.citations` — Bedrock, OpenRouter, and xAI citations are already normalized, so provider-switching preserves citation structure. **Thinking guardrails:** If you pass `thinking=False` to a model that can't actually disable thinking (e.g., some Anthropic extended thinking models), the behavior was previously undefined — now it sends the minimum allowed thinking level. If you pass provider-specific thinking configs at a broad scope (e.g., in a model default), you'll now get a warning when it silently overrides a narrower `thinking=` setting. Review your model configuration if you use extended thinking. **InputGuardrail:** If you have custom guardrails with fail-open exception handling, update immediately — the previous behavior could expose the user's prompt to the model on a guardrail error. Check `#10841` for the exact fix. **LocalStack:** If you run AWS integration tests with `LocalStack`, you're no longer spawning a new container per `async with agent:` — shared container reduces test setup time.
**Affects you if:** You build RAG or citation-heavy applications on pydantic-ai; you use extended thinking with `thinking=False`; you have custom InputGuardrail implementations; you test with AWS LocalStack.
**Adoption effort:** Quick (upgrade); review InputGuardrail exception handling if you have custom guardrails.
**Primary source:** https://github.com/pydantic/pydantic-ai/releases/tag/v2.61.0

## Trends & Emerging Tech

### Agent protocol handshake benchmarking is becoming a research category
**Source:** arXiv search result | **Date:** ~2026-10-23 | **Link:** https://arxiv.org/abs/2610.30151 *(unverified — arxiv.org DNS blocked)*
**What's happening:** A paper (arXiv:2610.30151, surfaced via search but not directly fetched) claims to be the first empirical, phase-decomposed benchmark of connection setup in the three major agent protocols: MCP (in its 2025 initialize and 2026 discover eras), A2A, and ACP. This follows at least two other protocol comparison papers in the last 60 days (arXiv:2606.31498 on governance gaps; arXiv:2505.02279 on the survey of all four protocols). ACP's development is also reported to be winding down, with its assets moving to A2A under the Linux Foundation.
**Why watch this:** Protocol handshake overhead doesn't sound like a big deal until you're running multi-agent systems where hundreds of tool calls happen per task. If MCP's 2026 discover-era handshake is meaningfully more efficient than the 2025 initialize era, that's an argument for updating servers to the current spec now rather than when you have a performance problem. The convergence on benchmarks for protocol overhead (rather than just capability comparison) suggests the community is starting to optimize at a layer below model performance — a sign of the space maturing past "which model is smartest" toward "which architecture is fastest."

**[OPEN QUESTION] Are structured citations in pydantic-ai the beginning of a response provenance layer?**
pydantic-ai v2.61.0 adds structured citations to `TextPart`, with normalization already built for Bedrock, OpenRouter, and xAI. Citations in model responses — which source, which passage — are technically straightforward when the model returns them, but they've historically been a per-provider inconsistency: some models return them, most don't, and the format varies. By normalizing them at the framework layer and replaying them to the provider that produced them, pydantic-ai is building a citation passthrough contract. The open question: if citations become a standard field in `TextPart`, do other frameworks (LangGraph, agno) follow? And if they do, does this become the basis for a practical audit trail for agent decisions in production?
*Grounded in: pydantic-ai v2.61.0 TextPart citations (#7434, #7750, #7752)*

Two products from competing labs are converging on the same UX conventions — model discovery, hooks for pre/post tool events, context management, IDE integration. Either way, the gap between "Claude Code user" and "Gemini CLI user" is shrinking in terms of learned behaviors.
*Grounded in: Gemini CLI v0.67.0-nightly.20261024 models command (#29880) and hook timeout migration fix (#29899)*

**[IF THIS CONTINUES] pydantic-ai's citation normalization predates a general developer need**
