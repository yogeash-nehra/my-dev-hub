### [BREAKING] Claude Opus 4.5 deprecation — `claude-opus-4-5` retires January 22, 2027
**Source:** Anthropic Platform Release Notes | **Date:** 2026-11-23 | **Link:** https://platform.claude.com/docs/en/release-notes/overview
**What changed:** Anthropic announced that `claude-opus-4-5` and `claude-opus-4-5-20251101` will retire from the Claude API on January 22, 2027. After that date, any request to either model ID returns an error.
**TL;DR:** `claude-opus-4-5` retires in ~8 weeks (Jan 22, 2027) — migrate to `claude-opus-5-5` before then; migration guide lists 4 known breaking changes between the two models.
**Developer signal:** You have roughly 8 weeks from today. The official migration guide is at `platform.claude.com/docs/en/models/opus-5-5/migration-guide`. Anthropic's docs flag four breaking changes between Opus 4.5 and Opus 5.5: (1) thinking controls changed, (2) forced tool use behavior changed, (3) tool definitions that worked on Opus 4.5 may return 400 errors on Opus 5.5 — test your complete tool schema against the new model in a staging environment before cutover. (4) Prefix checks that were warned on Opus 4.5 are now enforced. If you're using `claude-opus-4-5` as a default in an SDK initialization or as a hardcoded model string anywhere, update it now. The pinned version `claude-opus-4-5-20251101` also retires; pinned versions do not automatically forward to a newer model on retirement — they error.
**Affects you if:** You call the `claude-opus-4-5` or `claude-opus-4-5-20251101` model ID anywhere in your codebase, config files, or infrastructure; you use a SDK default that resolved to Opus 4.5.
**Adoption effort:** Moderate (update model IDs, test against 4 known breaking changes, migrate any thinking/tool-use patterns that differ between 4.5 and 5.5).
**Primary source:** https://platform.claude.com/docs/en/release-notes/overview (fetched directly); migration guide: https://platform.claude.com/docs/en/models/opus-5-5/migration-guide

## API & SDK Changes

### [MEDIUM] Enterprise Frontier Safeguards (beta) — ZDR for frontier models with Sealed Safety Data in customer's own cloud
**Source:** Anthropic Platform Release Notes | **Date:** 2026-11-23 | **Link:** https://platform.claude.com/docs/en/release-notes/overview
**What changed:** Anthropic launched Enterprise Frontier Safeguards in beta on Claude Platform, Claude Platform on AWS, and Claude Models on Google Cloud (Anthropic managed). It enables Zero Data Retention for eligible organizations using Claude Fable 5.2 and Mythos 5.2 by storing encrypted copies of prompts and responses ("Sealed Safety Data") in a bucket in the customer's own cloud account — not on Anthropic infrastructure.
**TL;DR:** Enterprise orgs can now use frontier models (Fable 5.2, Mythos 5.2) under ZDR by opting into Sealed Safety Data in their own cloud bucket — the first time ZDR has been available for Claude's most capable models.
**Developer signal:** Previously, Zero Data Retention required using older or less-capable models; Fable 5.2 and Mythos 5.2 required 30-day retention and were unavailable under ZDR unless Anthropic authorized it. This beta changes that for eligible orgs. The tradeoff: Sealed Safety Data is stored in the customer's own cloud bucket, so the customer is now responsible for managing that data's retention and access. Workspaces on Anthropic-managed storage are not eligible — you need to be on customer-owned storage. The two new webhook event types (`external_storage.failed` and `external_storage.recovered`) allow you to monitor your storage bucket's availability. Contact the Anthropic account team to inquire about eligibility; this is not self-serve from the Console yet.
**Affects you if:** You build applications on Claude Fable 5.2 or Mythos 5.2 and have enterprise contracts requiring Zero Data Retention or customer data residency; you operate in regulated industries (healthcare, finance, government) where data storage location matters.
**Adoption effort:** Significant (requires account team engagement, customer-owned cloud storage setup, and integration of the new webhook events for storage health monitoring).
**Primary source:** https://platform.claude.com/docs/en/release-notes/overview (fetched directly)

**Source:** Anthropic Platform Release Notes | **Date:** 2026-11-23 | **Link:** https://platform.claude.com/docs/en/release-notes/overview
**What changed:** Two new webhook event types added for organizations using customer-owned storage: `external_storage.failed` (fires when the customer's bucket fails the daily health check) and `external_storage.recovered` (fires when it passes again). Added alongside the Enterprise Frontier Safeguards beta.
**TL;DR:** If you use customer-owned storage with Anthropic, wire up `external_storage.failed` and `external_storage.recovered` webhooks to get alerted when your bucket goes unreachable — otherwise model requests that depend on it will silently fail.

If you're running Enterprise Frontier Safeguards (Sealed Safety Data), a failed storage bucket means model requests may fall back or fail — you want to be paged on `external_storage.failed` before users notice. The `.recovered` event lets you clear alerts automatically. These join the existing `external_key.failed` and `external_key.recovered` events (added Nov 16) which cover customer-managed encryption key failures.
**Affects you if:** Your organization uses customer-owned storage with the Anthropic platform; you are setting up Enterprise Frontier Safeguards.
**Adoption effort:** Quick (add two webhook handlers).

### [MEDIUM] Pydantic AI v2.71.0 — `PeerNetwork` → `PeerConnection` rename (breaking), ToolBridge for prompt-cache-stable large tool sets
**Source:** Pydantic AI GitHub Releases (via releases.atom) | **Date:** 2026-11-18 (5 days outside the 24h window; not found in Nov 22 digest scan) | **Link:** https://github.com/pydantic/pydantic-ai/releases/tag/v2.71.0
**What changed:** `PeerNetwork` renamed to `PeerConnection` (a breaking compatibility change); new `ToolBridge` helper added that presents a fixed three-tool surface (`tool_search`, `tool_describe`, `tool_call`) to keep the prompt cache stable when you have large or frequently-changing tool sets; `anthropic_previous_message_id` setting added for Anthropic message thread support. Prior release v2.70.0 (Nov 17) fixed two high-severity security advisories in Pydantic AI Harness: GHSA-m4cr-m4qc-9hh3 and GHSA-5m5q-5qj4-gx9h.
**TL;DR:** Pydantic AI v2.71.0 renames `PeerNetwork` → `PeerConnection` (update your code), adds `ToolBridge` for prompt-cache-friendly large tool sets, and v2.70.0 fixed two high-severity Harness CVEs — upgrade if you're on anything below 2.70.0.
**Developer signal:** (1) **Breaking rename**: Any code that imports or instantiates `PeerNetwork` will fail after upgrading to v2.71.0. Find all usages with `grep -r "PeerNetwork" .` and replace with `PeerConnection`. The semantics are identical — it's a pure rename. (2) **ToolBridge**: If you build agents with large or dynamically-changing tool catalogs, `ToolBridge` solves a real prompt-caching problem: previously, adding or removing a tool invalidated the cached system prompt. `ToolBridge` wraps your tool set behind three stable meta-tools so the cache prefix never changes. This is particularly relevant if you're using Anthropic message threads (the new `anthropic_previous_message_id` setting) and want caching benefits on tool-heavy agents. (3) **CVEs**: GHSA-m4cr-m4qc-9hh3 and GHSA-5m5q-5qj4-gx9h are both rated high-severity in Pydantic AI Harness. If you use the Harness component (not just bare `Agent`), upgrade to v2.70.0 minimum today. Details not yet public per standard embargo timelines — upgrade first, read later.
**Affects you if:** You use `PeerNetwork` anywhere in your codebase; you build pydantic-ai agents with large or dynamic tool catalogs and care about prompt cache efficiency; you use pydantic-ai Harness in production (CVEs apply to this component).
**Adoption effort:** Moderate (rename `PeerNetwork` → `PeerConnection` throughout codebase; evaluate `ToolBridge` adoption; immediate upgrade required for CVEs in Harness component).
**Primary source:** https://github.com/pydantic/pydantic-ai/releases/tag/v2.71.0 (via releases.atom, fetched directly); CVE advisories: github.com/pydantic/pydantic-ai/security/advisories
