## [BREAKING] Breaking Changes

### [BREAKING] PydanticAI v2.67.0 — three compat-note items are hard breaks for affected code
**Source:** GitHub (pydantic/pydantic-ai v2.67.0) | **Date:** 2026-11-10 | **Link:** https://github.com/pydantic/pydantic-ai/releases/tag/v2.67.0
**What changed:** PydanticAI v2.67.0 ships 20+ compatibility notes. The three that are hard breaks (silent failures or new exceptions thrown):

1. **OpenAI continuation blocked without `history_digest`:** `openai_previous_response_id` continuation is now refused if the referenced response has no `history_digest`. Code that continues OpenAI Responses API chains without digest validation will raise an error at runtime.
2. **`CapabilityCreation` now refuses below `'operator'` authority:** Calls to create capabilities in a directory below `'operator'` authority level now raise. Any code that creates capabilities in user-level or agent-level directories without elevating authority will fail.
3. **Native-tool settings moved to `provider_settings`:** Provider-specific native-tool fields that were passed inline must now go under `provider_settings`. Existing code using the old shape sends malformed requests silently or raises, depending on the provider.

**TL;DR:** Three PydanticAI v2.67.0 compat notes that require code changes: OpenAI continuation without `history_digest` raises, `CapabilityCreation` authority enforcement is now strict, and native-tool provider settings moved to `provider_settings`.
**Developer signal:** Before upgrading to v2.67.0, grep your codebase for `openai_previous_response_id` — any continuation chain must include a `history_digest`; add one or catch the new error. Grep for `CapabilityCreation` and audit the `directory` argument against your authority model — user-level directory paths need to be elevated to `'operator'`. For native-tool settings, move any inline provider-specific fields (e.g., `cache_control` on Anthropic tools, `parallel_tool_calls` on OpenAI) under `provider_settings`. The pydantic-ai changelog uses the phrase "compatibility note" for all 20+ items; not all require action — these three do.
**Affects you if:** You continue OpenAI Responses API sessions across turns using `openai_previous_response_id`; you create capabilities in non-operator directory paths; you pass provider-specific fields to native tools inline.
**Adoption effort:** Moderate (audit three code patterns, update each)
**Primary source:** https://github.com/pydantic/pydantic-ai/releases/tag/v2.67.0

The URL validation fix is security-relevant: if you're setting Bedrock/Vertex/Google Cloud configuration from user-supplied strings (org ID, region, model), upgrade now — the old code silently wrote malformed values into request paths. The fix raises an `AnthropicError` immediately instead.
**Affects you if:** You query the Admin API analytics endpoints; you configure Claude Tag Slack channels via the API; you set Bedrock/Vertex/Google Cloud configuration from dynamic or user-supplied values.

Combined with Fable 5.2's computer_toolset_20260801 (desktop control) and DIYgod/pinky (phone control, Nov 10 digest), the primitive set for a "whole environment" agent is assembling: browser + desktop + phone + home — each layer now has an MCP server with human-approval semantics.
**Why watch this:** The convergence is worth tracking for two reasons. First, it means agent-testing surfaces are expanding: developers building home automation workflows now have a programmatic way to verify device state and trigger automations via Claude without writing Home Assistant scripts. How operators scope, audit, and revoke MCP server access in multi-attachment sessions is an open question none of the current tools address. The model coming from an MCP server rather than a crafted prompt is structurally better than prompt injection, but it still runs at whatever authority level the HA access token carries.

**[OPEN QUESTION] What happens to OpenAI-chain agents in PydanticAI when history_digest is missing?**
PydanticAI v2.67.0 blocks `openai_previous_response_id` continuation without a `history_digest`. The Responses API was OpenAI's answer to multi-turn state management without client-side conversation history, and teams using it via PydanticAI may have built stateful agents that assume continuation always works. The breaking change is well-motivated (without history_digest, the continuation chain can silently diverge), but the migration path isn't obvious from the changelog: does PydanticAI generate history_digest automatically in future turns, or must developers explicitly capture and pass it? If it must be explicit, any framework that wraps PydanticAI-on-OpenAI will also break until updated. The scope of the blast radius depends on how many PydanticAI-based agents use OpenAI Responses API for state rather than the full conversation-history pattern.
*Grounded in: PydanticAI v2.67.0 `openai_previous_response_id` compat note (this digest, Breaking Changes)*
